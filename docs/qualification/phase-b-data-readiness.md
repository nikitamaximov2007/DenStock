# PRO-STOR Phase B: готовность данных

Что нужно сделать с содержанием базы до того, как публичный каталог начнёт
показывать покупателям реальные цены и русские названия.

Всё ниже посчитано на ИЗОЛИРОВАННОЙ копии снимка продакшена. Продакшен не
менялся и во время работы к нему не было ни одного подключения.

| Приложение снимка | `a5c014621c3689340bfe699216e03bb0b88d7472` |

## 1. Что происходит сразу после апгрейда

Миграция ставит всем карточкам безопасное `price_provenance = unverified`:
125 987 из 125 987. Это правильно (лучше «Уточнить цену», чем недоказанное
число), но означает, что до классификации витрина не покажет НИ ОДНОЙ цены.

Классификацию делает штатный конвейер цен, второй формулы не заводилось.

## 2. Классификация цен

Правило сертификации на `7d708e4`: цену подтверждает только СОБСТВЕННАЯ
положительная оптовая цена позиции каталога. Цена замены остаётся справкой:
она не доказывает цену отдельно продаваемой сущности.

```
цена клиента = оптовая USD × 105 × 1,40, до целого рубля ROUND_HALF_UP
```

### Главное число

**Ни одна цена не должна измениться.** Сертификация 125 863 карточек проходит
БЕЗ изменения числа: сохранённая цена уже равна канонической формуле. Проверено
применением штатного пересчёта на копии: `К изменению рекомендованных цен: 0`,
сравнение со снимком дало `prices_changed = 0`.

Сертификация и пересчёт это разные вещи, и здесь нужна только первая.

## 4. Что требует решения человека (38 строк)

`in_stock_price_review.csv` — только детали В НАЛИЧИИ, у которых цена не
сертифицируется автоматически.

| Категория | Строк | Что это |
| --- | ---: | --- |
| UNVERIFIED | 24 | цена помечена ручной в связи с каталогом BRP |
| SOURCE_MISSING | 3 | своей оптовой цены нет нигде |
| NOT_APPLICABLE | 10 | карточка вообще не связана с каталогом поставщика |
| VALID_MANUAL_EXCEPTION | 1 | уже подтверждено владельцем |

Внутри 24 UNVERIFIED есть важное деление, оно видно в колонках
`replacement_formula_price_rub` и `price_equals_replacement_formula`:

* **16 позиций** — текущая цена В ТОЧНОСТИ равна цене, посчитанной от оптовой
  цены ЗАМЕНЫ. Вопрос владельцу один: считать ли цену замены авторитетной для
  этой детали. Если да — цена не меняется, только подтверждается.
* **8 позиций** — текущая цена не равна ни своей (её нет), ни цене по замене.
  Это старые цены, посчитанные когда-то от РОЗНИЧНОЙ цены. Здесь нужно
  отдельное решение по каждой.

## 7. Минимальный порог содержания до Phase B

Требовать перевода всех 125 985 публичных карточек не нужно и незачем:
покупатель ищет то, что можно купить сегодня.

**Обязательно (без этого не включать):**

1. Выполнить сертификацию цен (0 изменений цены) — после неё 788 из 825
   деталей в наличии показывают число, 37 показывают «Уточнить цену».
2. Разобрать 38 строк `in_stock_price_review.csv`. Даже если решение не
   принято ни по одной, запускаться можно: непроверенные цены не показываются.
3. Подтвердить русские названия для **104 повторяющихся названий** — это
   покрывает **400 из 825** деталей в наличии примерно сотней решений.

**Желательно до запуска:**

4. Оставшиеся HIGH и MEDIUM черновики: вместе с пунктом 3 это **267 названий
   и 563 из 825 деталей** (68%).

**После запуска, по мере сил:**

5. 262 названия, встречающиеся у одной детали и требующие ручного перевода.
6. Каталог аналогов без остатка (125 160 карточек) — переводить постепенно
   или не переводить вовсе: он и так находится по артикулу.

Порог для решения «включаем»: **цены сертифицированы + 104 повторяющихся
названия подтверждены**. Это единственные пункты, без которых витрина выглядит
пустой для русскоязычного покупателя.

## 8. Рабочий процесс оператора

Новый интерфейс не нужен, всё существует:

1. «Склад» → «Быстрые действия» → найти деталь по артикулу (или открыть
   карточку детали).
2. «Таможенные данные» детали: вписать русское название из
   `ru_translation_suggestions.csv`, поставить галочку **«Русское название
   подтверждено»**, сохранить.
3. Название сразу становится искомым — и внутри DenisStock, и на витрине,
   пересчёта и переиндексации нет.
4. Цена: числовая цена показывается покупателю сама, если провенанс
   `formula_certified` или `valid_manual_exception`. Проверять руками нечего.

**Зафиксированный пробел (не чинил, отдельное решение):** подтвердить ручную
цену как `VALID_MANUAL_EXCEPTION` из интерфейса нельзя. Сервис
`certify_valid_manual_price_exception` существует и покрыт тестами, но экрана
у него нет: сейчас это делает администратор из `manage.py shell` по id детали.
Для 38 строк это приемлемо; если таких решений станут сотни, нужен экран.

## 10. Продакшен не менялся

К продакшену не было ни одного подключения: работа шла на уже снятом дампе.
Все записи (подтверждение исключения, сертификация) сделаны на изолированных
копиях `phaseb` и `phaseb_after` в контейнере PostgreSQL 16 на рабочей машине.
После сертификации на копии сверено со снимком: изменённых цен 0, остатки,
продажи и цены в строках проведённых продаж совпадают побайтово.

## 11. Как воспроизвести

```
docker run -d --name pb -e POSTGRES_PASSWORD=pb -e POSTGRES_USER=pb \
    -p 127.0.0.1:55552:5432 postgres:16
pg_restore -d prodsnap --no-owner --no-privileges <snapshot>.dump
createdb phaseb --template prodsnap
DATABASE_URL=postgres://pb:pb@127.0.0.1:55552/phaseb python manage.py migrate
DATABASE_URL=... python scripts/qualification/phase_b_price_provenance.py \
    --out docs/qualification/phase-b --confirm-isolated --expect-database phaseb
DATABASE_URL=... python scripts/qualification/phase_b_russian_names.py \
    --out docs/qualification/phase-b --confirm-isolated --expect-database phaseb_after
```

Оба скрипта отказываются работать без `--confirm-isolated`, с базой не на
loopback и с базой, имя которой не совпадает с `--expect-database`. Ошибиться
и попасть в продакшен ими нельзя.

# Public Catalog Stage 2: final PostgreSQL 16 qualification

Branch `codex/public-catalog-stage2-final-qualification`. Stage 1 base is
`12398646a515765aa6af4b2b9f0c77ad4fd23c0c`. The evidence below was taken on the
qualification code at `17cd85cbddc7cf5efd6c01c0b6ac2c4a7c70f9cf`; the only later
commit adds this document and a design note. Production Search code
(`apps/catalog/search.py`) and the Stage 2 migrations are unchanged since
`0cf7b2b`.

Everything ran against a disposable local PostgreSQL 16 bound to loopback.
No production database, backup or connection was used, and nothing was
deployed or merged.

## Qualification history

Three earlier problems are kept on record here, because each one made
qualification numbers look valid while measuring the wrong thing.

1. **Invalid exact probes (first corpus).** The generator stored six-digit
   names such as `BEARING DRIVE 000001`, but the report probed five-digit
   names such as `BEARING DRIVE 00001`. Those probes were not exact rows.
   Search correctly fell through to its substring and fuzzy tiers, so the
   "exact EN" and "exact RU" timings (192 ms and 777 ms) measured broad
   capped fuzzy workloads. Those numbers are archived in
   `public-catalog-stage2-review-remediation.md` and are not evidence.
2. **`bearng` shadowed by an article.** Commit `f6fa1e9` seeded the ranking
   fixture with article `BEARNG-01`. Its normalized value `BEARNG01` starts
   with `BEARNG`, so the typo `bearng` was answered by the article-prefix
   tier and never reached fuzzy search. Commit `9fb7acc` renamed the article
   to `BERRNG-01` and added isolated exact probes (`QUALIFICATION EXACT EN
   NAME`, `УНИКАЛЬНОЕ ТОЧНОЕ РУ НАЗВАНИЕ`) that no other row shares.
3. **End-to-end matrix measured pagination, not search.** The 1/20/50 matrix
   searched the same 50 parts every time and let `page_size` cut the page
   down, so the search never actually returned 1 or 20 parts. Commit
   `17cd85c` gives each size its own family of names with no shared
   trigram, and asserts the search total itself.

The corrected fixture and preflight are what every table below rests on.
Before any benchmark ran, the harness put each term through the real service
and refused to measure one that did not land on its intended target and tier.

Reading the table:

* Every identifier tier and every name equality, prefix and substring tier is
  index-served and executes in hundredths of a millisecond. The planner
  chose the B-tree `varchar_pattern_ops` index for article equality and
  prefix, and the trigram GIN indexes for substring and name predicates.
* **Case 7.** 112,494 of the 125,000 English names contain `BEARING`, so
  `'BEARNG' <% UPPER(name)` is true for about 90% of the table. A parallel
  sequential scan is the correct plan at that selectivity. The filter
  removed 4,169 rows per loop across 3 loops, which is the ≈12,500 GASKET
  names. The time goes into scoring, grouping and sorting 112,494
  candidates before `LIMIT 300`.
* **Case 10.** Same shape, on the Russian side, served by the confirmed-only
  partial index. The planner estimated 1,123 candidate rows against 112,494
  actual, so the `HashAggregate` ran with 5 batches and spilled 1.6 MB to disk
  under the stock 4 MB `work_mem`. The Bitmap Heap Scan branch is not
  parallel. Both explain the ≈4× per-candidate cost against case 7.
* **Case 12.** The cap filled at the prefix tier, so substring and fuzzy were
  skipped (7 statements). The preceding exact-name check rechecked 12,500
  rows: equality on `UPPER(name)` is served by the trigram GIN index, and
  every GASKET name shares the query's trigrams. That cost 3.4 ms.
* Cases 7 and 10 are deliberately adversarial: 90% of the catalog shares the
  mistyped word. The fuzzy-scaling table below measures the same tier at
  realistic candidate counts.

### Fuzzy cost against real candidate counts

The same fuzzy tier, timed through the same public call, on typos whose
candidate sets differ by two orders of magnitude. Candidates were counted with
the application's own operator and threshold.

| Typo | Intended word | Fuzzy candidates | n | Median ms | p95 ms |
|---|---|---:|---:|---:|---:|
| `qualifcation` | QUALIFICATION | 1 | 30 | 5.576 | 6.435 |
| `gaskt` | GASKET | 12,500 | 30 | 40.975 | 42.271 |
| `bearng` | BEARING | 112,494 | 30 | 129.926 | 136.666 |

Cost is a fixed ≈5 ms floor for the other tiers plus roughly 1-3 µs per
genuine candidate. It is bounded by the number of names that really resemble
the typo, and it never exceeds the size of the table. Nothing here is
pathological. Tightening it further, for example with a candidate cap or an
ordered GiST index, would change result semantics and is a product decision,
not a qualification fix. It is recorded in `docs/design/public-catalog-search.md`.

## RU confirmed-only plan

Both Russian paths enforce confirmation in SQL, before any scoring:

* ORM tiers (case 9 SQL): `WHERE (UPPER("customs_name_ru"::text) LIKE
  UPPER('%ТОЧНОЕ РУ%') AND "customs_name_ru_confirmed")`. The plan is a
  Bitmap Index Scan on `actions_partcustomsinfo_ru_upper_trgm` with
  `Recheck Cond: ((upper((customs_name_ru)::text) ~~ '%ТОЧНОЕ РУ%'::text) AND
  customs_name_ru_confirmed)`.
* Fuzzy tier (case 10 SQL): `WHERE ci.customs_name_ru_confirmed AND
  UPPER(%s) <% UPPER(ci.customs_name_ru::text)`. The plan is a Bitmap Index
  Scan on the same index, `Index Cond: (upper((customs_name_ru)::text) %>
  'ПРОКЛАТКА'::text)`, `Recheck Cond: customs_name_ru_confirmed`.

Under the normal planner, both use the partial index `… USING gin
(upper((customs_name_ru)::text) gin_trgm_ops) WHERE customs_name_ru_confirmed`.
The 12,500 unconfirmed rows overlap the confirmed text, and they are not in
that index, so they cannot become candidates. `НЕПОДТВЕРЖДЕННАЯ ПРОКЛАДКА`
returns 0 hits.

## GUC safety

`pg_trgm.word_similarity_threshold`, server default `0.6`, measured by the
harness and pinned by PostgreSQL tests:

| Scenario | After search |
| --- | --- |
| brand-new backend, autocommit | search OK |
| brand-new backend, inside `atomic` | search OK |
| autocommit | 0.6 |
| inside `atomic`, after search / after block | 0.6 / 0.6 |
| nested `atomic`, inner / outer / after | 0.6 / 0.6 / 0.6 |
| error inside the fuzzy query, autocommit | `ProgrammingError` raised; 0.6 after |
| error inside the fuzzy query, inside `atomic` | `ProgrammingError` raised; 0.6 inside and after |

No leakage in any shape.

One latent edge, documented and pinned rather than changed. A brand-new
backend has not loaded `pg_trgm`, so the setting does not exist yet: before
any trigram use, `current_setting(…, true)` returns NULL. Called on its own,
first, inside an outer transaction, the private `_fuzzy_rows` raises
`unrecognized configuration parameter` from its "read previous value" step.
This was reproduced directly. The public `search_part_ids` never reaches that
state. The name-partial tier has the same four-character floor as the fuzzy
tier and always runs first, and merely planning its `LIKE` against the
trigram GIN index loads `pg_trgm` (the setting reads `0.6` straight after).
It is not a defect on any reachable path, so Search code was not changed. The
invariant is pinned by
`test_fresh_backend_fuzzy_search_in_autocommit_and_inside_atomic` and recorded
in the design document. Reading the setting with `missing_ok` would harden
the private helper; that is a candidate follow-up.

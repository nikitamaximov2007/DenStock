# PRO-STOR: локальная квалификация для VPS с 2 ГБ RAM

База: кандидат ботов `5de614169b123eeebcd1c7e1aca5104a02c14897`.
Ветка оптимизации: `codex/prostor-bots-2gb`. Production не изменялся.
Это квалификация кода и синтетической нагрузки, а не замена приёмки
Telegram/MAX на реальных тестовых аккаунтах.

## Причины и исправления

1. У web было 3 независимых sync worker, у catalog-web 3 threaded worker.
   По локальному сравнению 100 запросов к web после нагрузки занимали
   315,9 МиБ с прежними 3 sync worker и 240,9 МиБ с 2 gthread worker по
   2 thread. Разница 75 МиБ в этом стенде. Но на каталоге из 125 тысяч
   позиций сочетание 2 x 2 в смешанной нагрузке заполнило лимит 2 ГБ и
   использовало 37 МиБ swap. Новый default: web 1 x 4, catalog-web 1 x 4.
   Healthcheck и таймауты сохранены. Это сравнение
   linux/amd64 под эмуляцией на Mac, поэтому абсолютные МиБ не переносятся
   на VPS без проверки.
2. Отправка одного 10 МиБ вложения раньше собирала multipart как цельные
   `bytes`, делая несколько полных копий. Измеренный пик дополнительных
   Python allocations составил около 30 МиБ. Новый `MultipartBody` передаёт
   сегменты по 64 КиБ с известным `Content-Length`; отдельный тест через
   настоящий локальный HTTP-сервер проверяет длину и отсутствие chunked.
3. Входящие Telegram/MAX вложения повторно копировались через `ContentFile`.
   Проверка уже полученных байтов теперь выполняется без этой копии. Фото
   MAX-альбома после проверки переносятся во временные анонимные файлы;
   одновременно в Python не удерживаются все 12 сжатых фото. Файлы
   закрываются при выходе обработчика. Исторические вложения по-прежнему
   сохраняются в `private_media` и входят в штатный подписанный бэкап.
4. Четыре параллельных декодирования WEBP по 16 млн пикселей подняли
   контейнер фотообработки до 1 096 МиБ, хотя сжатый файл был мал. Декодирование
   теперь сериализовано одним PostgreSQL advisory lock для web и обоих ботов.
   На SQLite действует локальный lock. Это ограничивает пик без отключения
   проверки полного декодирования и без изменения качества файлов.
5. Отдельная публикация в каталоге допускала источник 40 млн пикселей. Две
   такие операции в лимите 2 ГБ довели общий cgroup до 2 048 МиБ и до
   407 МиБ swap, хотя OOM не было. Предел публикации снижен до 16 млн
   пикселей: конечная публичная копия и так не превышает 1200 пикселей по
   длинной стороне. Более крупный исходник остаётся во внутренней карточке;
   для публикации сотрудник уменьшает копию. Регрессионный тест проверяет
   отказ до построения rendition.
6. Обработчик Telegram раньше продвигал offset даже при `DatabaseError`
   во время приёма update. Общий lock декодирования добавляет ещё одну
   операцию БД, поэтому этот путь исправлен: ошибка БД оставляет update
   непрочитанным, worker после восстановления повторит его. Тест проверяет
   неизменный offset и успешную последующую обработку; старые `uncertain`
   отправки не повторяются.

## Методика

Локальный Docker Desktop, образы `linux/amd64` под эмуляцией на ARM Mac.
Общий Linux cgroup для PostgreSQL 16, web, catalog-web, Caddy, процессов с
загруженным кодом двух ботов и синтетического фотообработчика:
`memory.max=2048 MiB`, `memory.swap.max=512 MiB`.
Запускались реальные Django/Gunicorn процессы и PostgreSQL со всеми 190
миграциями на отдельной тестовой БД. Сначала она была пустой, затем в неё
добавлены 125 тысяч синтетических позиций каталога. Синтетические PNG/WEBP имели
4000 x 4000 пикселей, JPEG около 7,2 МиБ, публикация каталога тестировалась
на 16 и 40 млн пикселей. Никаких production данных, токенов и сообщений.
Скрипт `scripts/qualification/prostor_2gb_photo.py` измерял cgroup, RSS/PSS,
swap, OOM и завершение дочерних процессов. Отдельный монитор измерял общий
cgroup, а не сумму RSS, чтобы не считать общие страницы несколько раз.

| Сценарий | Результат | Пик общего cgroup | Swap |
| --- | --- | ---: | ---: |
| 100 PNG по 16 млн пикселей, 4 процесса до ограничения | 100/100 | отдельно не снимался | 0 |
| 100 JPEG, 4 процесса, альбомы до 12 | 100/100 | отдельно не снимался | 0 |
| 100 WEBP, 4 процесса до ограничения | 100/100 | один фото-контейнер 1 096 МиБ | 0 |
| 8 WEBP по 40 млн пикселей, 4 процесса, прежний допуск | 8/8 | 2 048 МиБ | 407 МиБ |
| 8 WEBP по 16 млн пикселей, 4 процесса, ограниченная публикация | 8/8 | 1 170 МиБ | 0 |
| Финальная смешанная нагрузка: 100 клиентских WEBP, 8 публикаций, 100 текстов каждого бота, 100 повторов MAX, 1000 HTTP | все операции прошли | 1 688 МиБ | 0 |
| 100 JPEG около 7,2 МиБ, 4 процесса, альбомы до 12, плюс 100 текстов каждого бота | все операции прошли | 1 403 МиБ | 0 |
| Каталог 125 тысяч позиций, 2 x 2 worker, 400 поисковых запросов | 400/400 HTTP 200 | 1 587 МиБ | 0 |
| Тот же каталог, 2 x 2, поисковые запросы плюс WEBP, публикации и тексты ботов | все операции прошли | 2 048 МиБ | 37 МиБ |
| Каталог 125 тысяч позиций, 1 x 4 worker, 400 поисковых запросов | 400/400 HTTP 200 | 1 102 МиБ | 0 |
| Тот же каталог, 1 x 4, поисковые запросы плюс WEBP, публикации и тексты ботов | все операции прошли | 1 896 МиБ | 0 |

В финальной смешанной нагрузке web/catalog ответили 1000/1000 HTTP 200,
p95 80 мс, максимум 124 мс. Telegram handler вернул 100 синтетических
ответов; MAX записал 100 уникальных ответов в тестовый outbox и не добавил
дублей после 100 повторов тех же событий. Внешние Bot API не вызывались.
Локальные web, catalog-web и процессы загрузки кода ботов перезапущены,
оба HTTP healthcheck вернулись в healthy; число записей о миграциях
PostgreSQL осталось 190, а тестовых MAX записей 105 до и после рестартов.
В общем cgroup не возникло OOM, дочерние процессы фотообработчика
завершились, память после нагрузки вернулась к 792 МиБ. До нагрузки
полный набор процессов занимал около 808 МиБ.
В прогоне с 125 тысячами позиций фотообработчик 100 WEBP вырос с 126 до
525 МиБ (+399 МиБ), а обработчик 8 публикаций с 135 до 618 МиБ (+483 МиБ).
Это прирост отдельных cgroup четырёх синтетических процессов, не расход
одной фотографии и не величины для суммирования с общим пиком.
Во втором этапе каталог содержит 125 тысяч синтетических позиций. При 1 x 4
поиск и веб-страница вернули 400/400 HTTP 200 за 58,3 с; в смешанном прогоне
400/400 за 64,8 с, p95 для точного поиска 1,86 с, широкого 2,04 с,
поиска с опечаткой 2,16 с, веб-страницы 20 мс. Это медленнее 2 x 2:
смешанный прогон занял 42,6 с, но использовал swap. У тестовых процессов
фото не осталось сирот, а память после нагрузки вернулась к 1 010 МиБ.
Счётчик OOM/OOM kill остался нулевым. Модель не воспроизводит реальные
Telegram/MAX HTTP API и host-процессы VPS.

## Проверки кода

Полный pytest на кандидате `065b73b` до точечного переноса production
healthcheck: **6736 passed, 298 skipped,
7 failed**. Все семь failed test ID совпали с неизменённым исходным
кандидатом (`6728 passed, 298 skipped, 7 failed`); новых падений нет.
Это проверки ценовых подписей, экрана отмены ремонта, AI renderer,
устаревшего ожидания mount MAX и снимка Caddy. Полный набор не объявляется
зелёным. Профильные тесты фото и ботов: 130 passed, 2 skipped на SQLite;
176 passed на PostgreSQL 16;
на PostgreSQL отдельно проверен откат Telegram offset при `DatabaseError`.
Точечный перенос healthcheck покрыт отдельным тестом с настоящим Django
HTTP и политикой `Host` публичного каталога. `ruff check .`,
`djlint templates --check`, `manage.py check` и `makemigrations --check`
прошли. Новых миграций нет.

## Постоянные службы и ИИ-поддержка

Новый read-only снимок production 12 ноября: RAM 1967 МиБ всего,
`MemAvailable` 735 МиБ; swap 511 МиБ, занято 359 МиБ; диск свободно
4095 МиБ. Все шесть контейнеров работали, основные healthcheck были healthy.
Последующее SSH-соединение завершилось ошибкой, поэтому дальнейшие запросы
к VPS остановлены. Снимок фиксирует один момент, а не длительный пик.

| Служба | Production 12 ноября | Локальный 2 ГБ стенд после запросов |
| --- | ---: | ---: |
| web | 171 МиБ | 152 МиБ при 1 x 4 |
| catalog-web | 170 МиБ | 147 МиБ при 1 x 4 и 125 тысячах позиций |
| PostgreSQL | 235 МиБ | 81 МиБ на синтетической БД |
| Telegram bot | 64 МиБ | 95 МиБ, код загружен без polling |
| MAX bot | 70 МиБ | 91 МиБ, код загружен без webhook |
| Caddy | 20 МиБ | 19 МиБ |
| Telegram egress proxy | 14 МиБ по systemd | не входил в cgroup |
| AI proxy | 19 МиБ по systemd | не входил в cgroup |
| Docker daemon, containerd, ОС | входят в общий MemAvailable | не входили в cgroup |

ИИ-поддержка вызывает внешний Codex CLI, локальной модели нет. Веб-код
использует существующий `AI_SUPPORT_ENABLED` (по умолчанию `false`) и не
создаёт отдельный постоянный Django worker. Внешний launcher запускается
socket activation на запрос. Отдельный `denstock-ai-proxy.service` с sing-box
был активен и занимал 19 МиБ по `MemoryCurrent`. Выключение одного флага web не освободит
заметную постоянную память; отключать production proxy без подтверждения
использования и отдельного разрешения нельзя. История ИИ сохранена.

В одинаковом локальном образе сравнили импорт кода реально работающих
ботов `e359488` и кандидата: Telegram 78,4-78,9 против 79,9 МиБ
(прибавка около 1 МиБ), MAX 81,6-81,8 против 80,9-81,3 МиБ
(уменьшение около 1 МиБ). Это сравнение кода в простое, без polling и
webhook; абсолютные значения из эмуляции не переносятся на VPS.

Healthcheck web/catalog использует ограниченный Python `http.client`,
не создаёт shell-процессы; профильный тест прошёл. Число дочерних процессов
в локальной фото-нагрузке вернулось к нулю.

## Бюджет и границы вывода

В финальном изолированном cgroup PostgreSQL + web + catalog-web + процессы,
загрузившие код Telegram/MAX + Caddy занимали около 1 008 МиБ после прогрева
базы из 125 тысяч позиций. Пик смешанной нагрузки 1 896 МиБ оставил
152 МиБ до лимита 2 048 МиБ; после завершения осталось 1 010 МиБ.
Прирост на пике составил около 888 МиБ. При пустой БД аналогичный прогон
давал 1 688 МиБ и 360 МиБ резерва; эти числа не заменяют итоговый тест.
Cgroup учитывает файловый кэш и память
контейнеров, но не ОС Docker Desktop и действующие host proxy. Боты в
стенде обработали синтетические тексты отдельным процессом; idle-процессы
не выполняли настоящий polling или webhook. Каталог имитирован по числу
строк, но распределение реальных артикулов и запросов может отличаться.

При 400 поисковых запросах к каталогу на 125 тысяч позиций локальный
прирост общего cgroup над прогретой базой составил около 94 МиБ. Если этот
прирост перенести на измеренный production baseline, останется примерно
640 МиБ `MemAvailable`; это оценка, не измеренный показатель будущего VPS.
При предельной смешанной нагрузке локальный прирост составил 888 МиБ.
Текущий production baseline оставил бы отрицательный расчётный резерв,
а свободного swap было около 152 МиБ. Этот сценарий нельзя объявить
безопасным для VPS. Общий PostgreSQL lock разрешает только одно тяжёлое
декодирование фото одновременно; дополнительные фотооперации должны ждать,
а старые `uncertain` не повторяются автоматически. Локальный стресс дал
ноль OOM, ноль процессов-сирот, возврат памяти к baseline и без дублей
синтетических MAX-ответов, но не доказывает поведение на VPS при длительном
совпадении пиков ОС, БД, поиска и фото.

## Диск и выпуск

Четыре образа кандидата `linux/amd64` занимали около 104 МБ каждый с
общими слоями; общий сжатый архив занял 98 МБ. На production было
4095 МиБ свободно. Консервативная оценка для архива и четырёх полных
образов без учёта общих слоёв: около 514 МБ; последняя полная копия
занимала около 93 МБ. Свободный диск не доказывает, что будущий рост
логов или фото не уменьшит резерв перед деплоем. Не
удалять прошлые образы для отката, актуальные подписанные бэкапы и фото.
MAX-альбом может временно занять до 120 МиБ анонимными файлами (12 фото
по 10 МиБ); они закрываются после обработки. Два одновременных альбома
требуют до 240 МиБ временного места плюс место долговременного хранения.
`docker system df` показал 4,3 ГБ образов и 7,9 ГБ build cache в учёте Docker;
эти логические размеры нельзя вычитать из свободного места повторно.
Ничего на VPS не удалять. Сборку образов делать вне VPS.

Остаются блокеры релиза ботов: полное чтение внешнего бэкапа назад и его
изолированное восстановление, ручная приёмка MAX сотрудника в DEV,
проверка старых bot-образов без source attestation и решение по семи
известным падениям полного pytest. Снимок RAM и диска получен, но
предельный стресс не оставляет безопасного расчётного запаса на VPS.
Production-деплой, миграции и перезапуски здесь не выполнялись.

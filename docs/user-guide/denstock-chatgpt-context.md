# DenisStock ChatGPT Knowledge Base

Этот файл загружается в ChatGPT как база знаний. Он описывает ТОЛЬКО реально
существующие функции системы DenisStock. Отвечая пользователю, опирайся строго
на этот документ.

## Product summary

DenisStock - веб-система складского учёта запчастей (авто, снегоходы,
квадроциклы, катера, яхты) для небольшого бизнеса. Главный сценарий: при
звонке клиента за секунды найти деталь, увидеть количество, цену и ячейку
хранения. Система ведёт каталог, приход (поступления/партии), остатки по
ячейкам, журнал движений, резервы, продажи, ремонт, возвраты, списания,
инвентаризацию, отчёты, статистику, пользователей с ролями и бэкапы.

Для полной сверки ящика используется workflow «Склад» - «Инвентаризация» -
«Пересчёт участка». Пользователь выбирает canonical S-D ящик, а документ
захватывает все его активные дочерние ячейки. Сканирование и dry-run
только сохраняют факт и не меняют остатки. После явного применения изменения
проводятся одной транзакцией через inventory service; партии выбираются явно,
если у детали несколько источников. Активный пересчёт блокирует складские
операции в этих ячейках, а завершённый apply можно безопасно повторить.
Для повседневной проверки любой активной ячейки в её карточке есть
«Пересчитать ячейку». Это режим того же SectionRecount из одной target
Location: общий snapshot, fingerprint, durable lock, batch allocation и atomic
apply. Один скан добавляет одну единицу; количество можно исправить или удалить,
поиск работает по артикулу и названию. После завершения dry-run показывает
«Было», «Насчитано» и дельту. Изменения создаются только отдельным подтверждением
и только как необходимые ADJUST-дельты; при полном совпадении движений нет.
Интерфейс русскоязычный, работает в браузере, есть мобильное меню.
Левое меню сохраняет свою прокрутку и при обычных внутренних GET-переходах
обновляет центральный контент с поддержкой Back/Forward. Это progressive
enhancement: прямой URL, обновление страницы и работа без JavaScript остаются
обычными полными Django-страницами; POST и файлы не загружаются частично.

## Actual navigation map

Логотип PRO-STOR открывает Главную (`/`). В sidebar отдельно находятся единый Поиск (`/search/`) и
ИИ-поддержка (`/ai-support/`). Ниже
расположены независимые раскрывающиеся группы с прямыми ссылками на ежедневные
функции:

- Склад: Остатки, Ячейки, Поступление, Перемещение, Инвентаризация,
  Быстрые действия, История.
- Продажи: Продажи, Резервы, Возвраты покупателей.
- Ремонты: Ремонты, Возвраты из ремонта.
- Отчёты: Сводка, Продажи по клиентам, Складские действия / Таможня,
  Статистика.
- Настройки: Цены, Пользователи, Бэкапы.

У ограниченных ролей недоступные подпункты и пустые группы не показываются.
Все доступные группы по умолчанию раскрыты; состояние каждой группы и
прокрутка sidebar сохраняются локально. Активная группа всегда раскрыта.
Внутренние вкладки используют существующие прямые URL:

- Каталог: Все детали, BRP, Polaris.
- Склад дополнительно сохраняет внутреннюю вкладку Списания.
- Поступление: документы, Партии поставок, Приёмка сканером.
- Инвентаризация: Инвентаризация ячейки и Сверочные документы.
- Продажи: Продажи, Резервы, Возвраты покупателей.
- Ремонты: Ремонты, Возвраты из ремонта.
- Отчёты: Сводка, Продажи по клиентам, Складские действия / Таможня,
  Статистика.
- Настройки дополнительно сохраняют внутреннюю вкладку
  Инструменты / Нераспознанные и внутреннюю вкладку Справочники.

Общий Поиск детали и общий read-only Сканер объединены в одно универсальное
поле `/search/`. Старый `/scanner/` переводит введённый код в поиск.
Специализированные scanner endpoints не изменены. Отдельного scanner-поля
в шапке нет.

Ниже существующие функции и GET URL сгруппированы тематически. Эти заголовки
не являются отдельными группами sidebar:

Функции домена «Обзор»:
- Главная (/) - все: KPI-плитки, «Требует внимания» (низкие остатки,
  карантин), «Быстрые действия».
- Поиск детали (/search/) - все: единый ручной и scanner-first поиск по
  названию/OEM/штрихкоду/серийнику/
  внутреннему номеру/технике; показывает физический остаток, доступность,
  резерв, карантин, количество по ячейкам, цены и партии. Единый resolver
  используется поиском, сканером, BRP/Polaris, приёмкой, действиями и
  пересчётом ячейки. Приоритет: exact, barcode, alias, name. Replacement и
  superseded явно подписываются и никогда не заменяют exact identity.
- Сканер (/scanner/) - совместимый старый GET/POST-вход, который переводит
  код в `/search/?q=...`. JSON resolver `/scanner/resolve/` и специальные
  scanner flows сохранены. CR/LF удаляются, неоднозначность требует выбора.
  Изменяющие склад POST защищены durable request token и блокировкой строк;
  повторный Enter не создаёт вторую операцию.
- ИИ-поддержка (/ai-support/) - read-only текстовый консультант для всех
  рабочих ролей через ephemeral Codex CLI с серверной авторизацией ChatGPT.
  Отдельный API key и usage-based API не используются. Провайдер не имеет
  tools, SQL, shell, web search и доступа к mutation services. Для каждого
  вопроса локальный детерминированный retrieval выбирает релевантные документы
  из `docs/ai-support/`, тип вопроса и безопасный контекст текущей страницы.
  HTML, query, cookies и скрытые поля не передаются. Пользователь может
  приложить один безопасно перекодированный JPG/PNG/WEBP скриншот только после
  отдельного согласия. Ручное обращение передаёт менеджеру только явно
  выбранные сообщения, скриншот и allowlisted диагностику, а не весь разговор.
  UI немедленно показывает вопрос и «ИИ анализирует вопрос...», защищает от
  дубля и позволяет повторить failed-запрос. Production использует отдельный
  audited Linux launcher и pinned Codex CLI 0.142.5.

Функции домена «Каталог»:
- Детали (/parts/) - все смотрят; создание/правка: Администратор, Руководитель
  (кнопка «Добавить деталь»). Создание спрашивает три поля: название, артикул,
  рекомендуемая цена; обязательно только название, остальное подставляется (единица
  «Штука», количественный режим, категория «Добавлено вручную»). Совпадение
  артикула показывается, но не запрещается. Остатка карточка не создаёт.
  Полная карточка - в правке: категория, производитель, режим учёта
  (Поштучный/Количественный), цены, минимальный остаток, OEM/штрихкоды,
  применимость, фото, печать этикетки.
- Публичный каталог PRO-STOR (отдельный процесс и хост) показывает покупателям
  только подтверждённое: аналог после «Подтвердить» (снимается «Снять с
  каталога», связь на складе остаётся), фото только после «Опубликовать» с
  выбранным источником и отметкой «На фото именно эта деталь». Страница
  проверки фото: /parts/public-photos/. Решают администратор и руководитель.
  Публичные фото - пережатые копии без EXIF в базе; внутренние файлы media
  публичный процесс не видит.
- BRP-каталог (/brp/) - все смотрят: справочник дилерского прайса BRP
  (~126 тысяч позиций), НЕ остатки. Поиск по номеру BRP/заменам/описанию;
  статусы OBS/USE/VIN/LIQ/UCP (легенда видна на странице: OBS - снято с
  производства, USE - была замена номера, VIN - винтажный склад с доставкой
  25$, LIQ - последние остатки у завода, UCP - уточняется); цена клиента =
  оптовая цена USD x общий текущий курс x (1 + наценка BRP/100), итог округляется
  до ЦЕЛОГО рубля (ROUND_HALF_UP, копеек в цене нет; настройки:
  /directories/price-settings/, админ и руководитель). «Создать карточку» (админ/руководитель) создаёт только
  карточку (не количество); «Учесть наличие» (роли склада) открывает черновик
  «Инвентаризации начальных остатков» (документ поступления от поставщика
  «Стартовый ввод»): остаток появится после «Провести поступление».
- Единый курс и отдельные наценки BRP/Polaris принимают дробные значения с
  точкой или запятой и хранятся как Decimal без округления до целого.
- Polaris-каталог (/polaris/) - все смотрят: отдельный справочник дилерского
  прайса Polaris, НЕ остатки. Поиск по part_number, superseded_number,
  названию и штрихкоду склада. Цена для клиента считается по общему текущему курсу
  и отдельной наценке Polaris: оптовая цена USD x курс x (1 + наценка/100), ROUND_HALF_UP до целого
  рубля. Exact part_number важнее superseded_number; source цены может быть
  связанная позиция, но identity остаётся exact. Если один номер есть в BRP и
  Polaris, общий поиск показывает оба варианта и не выбирает каталог молча.
- Партии (/batches/) - Администратор, Руководитель, Кладовщик (кладовщик без
  закупочных сумм): технический приход с валютой, доп. расходами и landed cost.
- Справочники (/directories/) - категории, производители, единицы, виды/марки/
  модели техники, поставщики. Правка: Администратор, Руководитель.

Функции домена «Склад» (Администратор, Руководитель, Кладовщик; Наблюдатель -
только просмотр экземпляров/лотов/движений/остатков):
- Экземпляры (/inventory/) - поштучные детали со статусами.
- Лоты (/inventory/lots/) - количественный учёт.
- Движения (/inventory/movements/) - журнал всех операций, только чтение.
  В таблице показывается exact-артикул, а не `лот #...`: snapshot связанного
  действия имеет приоритет, затем exact BRP material_no / Polaris part_number /
  основной неаналоговый номер карточки. Количество и рубли отображаются целыми
  через Decimal ROUND_HALF_UP, без изменения значений в БД.
- Остатки (/inventory/balance/) - live-срез из `StockLot` и `PartItem`,
  агрегированный по exact part identity + ячейка: физически, доступно, резерв,
  карантин. `StockBalance` остаётся пересобираемым кэшем, не source of truth.
- Поступление (/receipts/) - документ прихода РЕАЛЬНОЙ поставки: черновик ->
  позиции (деталь, количество, цена ₽, ячейка) -> «Провести поступление».
  Кнопка «+ Новая деталь» (только Администратор/Руководитель) создаёт
  карточку и возвращает в черновик с подстановкой. Первичный ввод из
  «Инвентаризации ячейки» в этом списке НЕ показывается (его документы -
  IC-номера в разделе «Инвентаризация»).
- Приёмка сканером (/scanner/receiving/) сохраняет прежний поток экземпляров:
  ITEM:/DS-номер или серийник -> скан ячейки -> «Подтвердить». Обычные
  exact-артикулы идут в session-очередь: повторные сканы увеличивают количество,
  обновление страницы очередь не теряет, до проведения склад не меняется.
  Закреплённая ячейка хранится отдельно от остатка: после нулевого остатка она
  предлагается повторно и не означает фиктивное количество. Одна текущая ячейка
  назначается автоматически, несколько требуют явного выбора с показом
  физического остатка/резерва/доступного. Кнопка «Изменить ячейку» использует
  единый поиск активных ячеек и позволяет выбрать другую. Архивная или запрещённая
  закреплённая ячейка не назначается автоматически. Новый exact из BRP или Polaris
  без остатка позволяет выбрать активную ячейку и при проведении создаёт карточку
  и первый лот; /receipts/ не пополняется. Очередь сгруппирована
  по ячейкам, каждая группа проводится отдельно и атомарно через ADJUST_IN с
  `document_type=found_addition`. Уникальный серверный token не допускает
  двойного POST. BRP replacement / Polaris superseded используются только как
  price source; identity остаётся exact. Совпавшие номера BRP/Polaris требуют
  выбора производителя. Неизвестный во всех каталогах код ничего не создаёт.
- Перемещение (/scanner/move/) принимает ITEM barcode, заводской barcode и
  нормализованный номер детали. Для bulk показывает live-источники по ячейке и
  состоянию, разрешает частичное количество. Целевая ячейка выбирается через
  единое поле «Новая ячейка» с поиском по существующим активным кодам; ручной
  ввод и сканер работают в этом же поле. Текущая, архивная и запрещённая для
  хранения ячейки не предлагаются и повторно отклоняются backend. Резерв не
  перемещается, карантин сохраняет состояние. Операция атомарна, блокирует строки, пишет один
  `StockTransfer` с exact snapshot и одну или несколько строк `StockMovement`,
  связанных `document_type=stock_transfer`. Уникальный token защищает от
  повторного POST. Исторические `InventoryCountingLine` не переписываются.
- Инвентаризация ячейки (/inventory/counting/) - Администратор, Руководитель,
  Кладовщик: выбрать место -> пикать всё содержимое подряд (скан + Enter) ->
  система группирует одинаковые номера, распознаёт склад, затем BRP/Polaris ->
  «Завершить пересчёт» -> «Создать черновик документа» (позиции BRP/Polaris становятся
  карточками автоматически) -> «Провести инвентаризацию». Остаток пишется по
  адресу только при проведении; скан и черновик склад не меняют. Результат
  проведения - документ инвентаризации IC-... в разделе «Инвентаризация»
  (первичный ввод), НЕ поступление: в /receipts/ он не отображается.
  Строки получают цены клиента из пересчёта (итог документа = «Стоимости
  ячейки», в документе это «Оценка за ед.»); вводить себестоимость не нужно,
  запасная цена - только для строк без цены. Режим
  первичного ввода: проведение ДОБАВЛЯЕТ остаток, одну ячейку дважды проводить
  нельзя (удвоится). Строки «Требует разбора» блокируют создание документа.
  Счётчики: «Позиций» - уникальные номера, «Событий сканирования» - сырые
  вводы сканера, «Итоговое количество» - сумма по столбцу «Количество»
  (ручные правки, отмены и удаления
  учитываются), «Стоимость ячейки» - сумма количество x цена клиента в целых
  рублях; «Деталей» и «Стоимость» видны и в списке пересчётов. Плитка
  «Стоимость ячейки» кликабельна: окно «Расчёт стоимости ячейки» показывает
  по строкам количество × цена = сумма и «Итого» (равно плитке); строки с
  ценой 0 видны и помечены «цена 0». В окне есть «Сортировка»: по сумме
  (по умолчанию сначала дорогие), количеству, цене, номеру, исходный и
  обратный порядок; сортировка не меняет итоги и главную таблицу. При «Завершить пересчёт» карточки и
  документ получают те же эффективные цены, что показывал пересчёт
  (пример: 250000059 создаётся с 484 ₽ от замены 250000418, не с 0). Счётчик
  «Найдено в складе» из сводки убран (путал физическое наличие с наличием
  карточки), источник строки виден в таблице. Дубликаты номеров в прайсе BRP
  решаются в пользу ненулевой оптовой цены; точное совпадение номера важнее
  совпадения по замене. Для Polaris exact part_number важнее superseded_number.
  Если у точного номера оптовая цена 0, цена клиента берётся из связанной замены или
  source-позиции с ценой (строка остаётся привязанной к отсканированному
  номеру). После реимпорта прайса незавершённые черновики
  подхватывают исправленные привязки и цены сами - пересканировать ячейку
  не нужно (проведённые сессии не переписываются).
  На странице сессии есть «Описание ячейки» («Сохранить описание») - заметка
  о содержимом, правится в любой момент, остатки не трогает. Незавершённый
  черновик (до «Завершить пересчёт») можно удалить из списка: кнопка
  «Удалить» с подтверждением; удаляются сессия, сканы и строки, остатки не
  меняются. Завершённые/сконвертированные/проведённые сессии не удаляются -
  они остаются в истории для аудита.
- Адрес места хранения: S - стеллаж, D - выдвижной ящик снизу вверх,
  C - ячейка. Пример: S01-D03-C08. Уровень L, зоны и B/K/X в новых адресах
  не создаются. Legacy code/barcode после явного migration mapping остаётся
  alias той же physical Location; scanner показывает текущий canonical адрес.
- Склад (/warehouse/) - структура ячеек, создание мест, этикетки ячеек.
  Администратор или руководитель может в карточке существующей ячейки нажать
  «Переименовать ячейку»: изменяется только её код, а `StorageLocation.pk`,
  остатки, лоты, экземпляры, движения и документы остаются на месте. История
  переименований видна в карточке. Старый code и auto-barcode остаются
  historical aliases той же ячейки; после операции нужно распечатать новую этикетку. Если
  старый код позже становится текущим кодом другой ячейки, старый alias сохраняется
  в аудите, но выключается из поиска. Текущий код всегда имеет приоритет, а старый
  redirect автоматически не оживает после следующего освобождения кода. Автоматический штрихкод
  `LOC:<код>` меняется вместе с кодом; произвольный пользовательский штрихкод
  остаётся стабильным.
  Та же операция доступна из страницы пересчёта ячейки и после сохранения
  возвращает в тот же пересчёт с живым новым кодом.
  Для canonical S-D ящика есть отдельное «Переименовать ящик»: preview и atomic
  apply обновляют drawer и все child cells с сохранением их IDs и stock history.

Функции домена «Операции»:
- Ручная текущая цена (BrpPartLink/PolarisPartLink price_source=MANUAL) НЕ
  является постоянным override: refresh_linked_part_prices пересчитывает и её,
  а источник связи переводится в CALCULATED, поскольку цена больше не ручная.
  Вписанное значение остаётся в manual_customer_price_rub для аудита.
  Отсутствующая или неположительная оптовая цена текущую цену не переписывает.
  Курс и наценка берутся из ValuationSettings/BrpPricingSettings. Исторические
  снимки (SaleLine, RepairIssueLine, CustomsOrderLine) не меняются никогда.
- Складской адрес показывается в операторском виде 1-3-8 (стеллаж-ящик-ячейка).
  Это ТОЛЬКО представление и ввод: StorageLocation.code, barcode, PK, привязки
  лотов и деталей, остатки и исторические снимки адреса не менялись. Источник
  формата один: apps.warehouse.addresses.short_address / normalize_address_input,
  плюс StorageLocation.short_code и шаблонный фильтр short_address для снимков.
  Ввод, поиск и сканирование принимают обе формы; legacy S-L адреса короткой
  формы не имеют и показываются без изменений.
- Экран подтверждения отмены продажи и ремонта показывает предпросмотр возврата
  (деталь, количество, ячейка) по каждой строке, включая раскладку по нескольким
  ячейкам. Источник один и тот же и для предпросмотра, и для самой отмены:
  apps.returns.services.cancellation_allocations - разойтись они не могут.
  Ячейку задаёт строка документа, а не текущая ячейка карточки детали.
- Выбор клиента в продаже, ремонте и быстрых действиях отсортирован по
  свежести последнего ЗАВЕРШЁННОГО документа (продажа или ремонт), свежие
  первыми; без истории - ниже, между собой по имени; отменённые и черновые
  документы наверх не поднимают. Общий источник порядка:
  apps.customers.services.customers_by_recent_activity.
- Действия со склада (/inventory/actions/) - быстрый сканерный расход:
  действие по умолчанию «Не выбрано» (не «Продажа»), без выбора любая операция
  отклоняется на сервере сообщением «Выберите действие» и склад не меняет;
  скан номера -> карточка с остатками по ячейкам (физически/зарезервировано/
  доступно) -> если ячеек несколько, выбрать ячейку списания -> Продажа /
  Резерв / Ремонт + количество + «Клиент / комментарий» -> «Провести
  действие». В строке корзины сотрудник вводит вес брутто и нетто в ГРАММАХ
  и выбирает область применения (Гидроцикл, Квадроцикл, Снегоход, Лодочный
  мотор, Катер); запомненные значения карточки подставляются автоматически.
  Хранение остаётся каноническим: PartCustomsInfo.gross_weight_kg /
  net_weight_kg, Decimal(8,3), килограммы. Продажа и ремонт без веса и
  области применения не проводятся (они таможенные источники), резерв
  не ограничен. Значения запоминаются в карточке только успешным проведением.
  Таможенный минимум 0.03 кг применяется ТОЛЬКО при выгрузке и запомненный
  вес не меняет. Продажа и ремонт списывают остаток сразу (создаются проведённые
  документы), резерв держит доступность (отмена/продажа - в «Резервах»).
  Больше доступного в ячейке провести нельзя. Права: продажа/резерв -
  админ, руководитель, продавец; ремонт - плюс кладовщик.
  Scanner-first операции используют строгую identity: только exact-артикул
  или штрихкод реальной карточки. BRP replacement, Polaris superseded,
  аналоги и источники цены не становятся операционными кандидатами.
  Read-only поиск может показать их отдельно как «Возможные связанные номера».
- Отчёт действий (/inventory/actions/report/) - единый журнал действий со
  сканера с фильтрами (даты, тип, клиент, номер, ячейка), итогами и кнопкой
  «Экспорт в Excel для таможни»: источник - строки проведённых продаж
  и завершённых ремонтов, как в отчёте «Продажи и ремонты».
  Они группируются по сохранённой исторической таможенной версии и exact номеру;
  возвраты и отмены гасят соответствующий расход. Сохранённые значения версии
  имеют приоритет; пустые поля достраиваются из загруженных каталогов
  поставщика по exact-артикулу: EN-название и оптовая цена USD из прайса
  (у aftermarket - дилерская цена), RU-название словарём от EN,
  производитель по доказанной связи с каталогом. Пустая страна BRP
  автоматически заполняется значением КАНАДА по правилу компании, без
  изменения версии. Явная страна имеет приоритет. Polaris, aftermarket и
  другие бренды этот fallback не получают. Рублёвые цены не подставляются.
  Ручные поля: трекинг, веса, область применения, страна не-BRP брендов.
  Неполные поля, включая веса, не блокируют экспорт и не исключают
  исторические строки.
- Форма «Таможенные данные детали» спрашивает у оператора пять вещей: русское
  название, отметку «Название подтверждено», вес брутто, вес нетто и область
  применения. Английское название и оптовую цену USD система берёт из каталога
  поставщика, производителя - из связи карточки; пустая страна получает
  КАНАДА только у BRP, явная страна сохраняется. Всё это
  записывается в карточку при сохранении. Неподтверждённое русское название
  остаётся незаполненным полем; отсутствующий вес не блокирует экспорт.
  После сохранения открывается
  следующая незаполненная деталь того же отчёта.
- Таможенные заказы (`/customs-orders/`) фиксируют реальное включение
  канонических строк продаж, ремонтов и `OrderedPart`. Идентичность строки:
  `(source, source_id)`, не артикул и не дата. В отчёте назначенная строка
  остаётся видимой серой и содержит ссылку на точный заказ; `unassigned=1`
  запрашивает только неназначенные строки на сервере.
- Выбор заказа строит неизменяемый хронологический префикс свободных строк с
  tie-break `(occurred_at, source, source_id)`. Браузер передаёт только
  крайнюю строку и подписанный снимок показанного набора. Финализация заново
  проверяет снимок, current USD/RUB из `ValuationSettings`, цены и уникальную
  membership в одной транзакции. Изменение состава, курса или уже назначенная
  строка откатывают заказ целиком.
- `CustomsOrder` и `CustomsOrderLine` являются frozen snapshots. Сумма строки
  равна `wholesale_usd × effective_quantity × fx_rate`, без 40% markup.
  XLSX заказа строится только из этих снимков, имеет «Оригиналы» и «Аналоги»
  и сохраняет текущий общий шаблон, Arial 12, wrap, форматы веса и зелёный
  артикул `OrderedPart`.
- Резервы (/sales/reservations/) - создают Администратор, Руководитель,
  Продавец: черновик -> позиции -> «Активировать»; далее «Продать из резерва»
  или «Отменить». Активный резерв уменьшает «Доступно».
- Продажи (/sales/sales/) - Администратор, Руководитель, Продавец: черновик ->
  позиции с ценой -> «Провести продажу» (списывает склад, фиксирует выручку/
  себестоимость/прибыль). Отмены проведённой продажи нет: только возврат.
- Заявки клиентов (/customer-requests/) - внутренний список обращений из
  публичного каталога для Администратора, Руководителя и Продавца. Заявка
  самостоятельна: она не создаёт Customer, Reservation, Sale, платёж или
  складское движение. Статусы: Новая -> В работе -> Выполнена; Новая и В
  работе можно отменить. Снимок `price_seen` это текущая цена при отправке, не
  фиксированная цена и не обязательство. Для каждой позиции хранятся ссылка на
  PartType, количество, единица и identity-снимок. Согласие хранит версии
  политики и согласия, цель и время принятия; окончательное юридическое
  содержание и сроки хранения требуют отдельного legal review. Клиент
  отправляет заявку из корзины публичного каталога («Отправить заявку»):
  позиция без остатка уходит как запрос о поставке, повторное нажатие не
  создаёт вторую заявку. Номер заявки из 8 символов (например 5F3A9C21)
  видят и клиент, и сотрудник (первая колонка списка, заголовок карточки).
  Пока база в режиме только для чтения (обслуживание, авария), заявки не
  принимаются. В боковом меню у пункта «Заявки клиентов» стоит счётчик заявок
  со статусом «Новая»; при нуле значка нет.
- Русский поиск - только по ПОДТВЕРЖДЁННОМУ русскому названию
  (`PartCustomsInfo.customs_name_ru` при `customs_name_ru_confirmed`).
  Неподтверждённый автоперевод не ищется и не показывается. Регистр и «ё»
  сворачиваются в Python (`apps.core.search_text.fold_search_text`) и хранятся
  в `search_name_ru`, поэтому поиск не зависит от локали базы; слова
  многословного запроса ищутся в любом порядке. Опечатки в кириллице требуют
  кластера, где CTYPE считает кириллицу буквами; `manage.py ops_check` об этом
  предупреждает.
- Телефон - единая запись `+7 900 123-45-67` во всех полях телефона
  (карточка клиента, резерв, продажа, ремонт, публичная заявка). «+7»
  подставляется само, ведущая «8» заменяется на него, вставка `89001234567`,
  `79001234567`, `+79001234567` и `9001234567` даёт одну запись. Приводит к
  канону СЕРВЕР (`apps.core.phones.canonical_phone_text`), маска в браузере
  только помогает вводить. Иностранный номер остаётся как ввели: чужой формат
  не угадывается. Уже сохранённые номера не переписываются и не мигрируют.
  Поиск по телефону не зависит от записи (`normalize_phone`).
- Ремонт (/repairs/orders/) - Администратор, Руководитель, Кладовщик,
  Продавец: «Провести (выдать в ремонт)» списывает детали без выручки.
- Возвраты (/returns/) - проводят Администратор, Руководитель, Кладовщик.
  Создаются ТОЛЬКО из карточки проведённой продажи или ремонта кнопкой
  «Оформить возврат». Деньги продажи не меняют.
- Списания (/write-offs/) - Администратор, Руководитель, Кладовщик: причина
  (брак/потеря/утилизация/неликвид/прочее) -> позиции -> «Провести (списать)».
- Инвентаризация (/stocktaking/) - Администратор, Руководитель, Кладовщик.
  Два вида документов: «Первичный ввод ячеек» (IC-документы из пересчёта
  сканером, позиции заполнены автоматически: номер, название, ячейка,
  количество, оценка за ед., сумма оценки) и «Сверка остатков» (по ячейке,
  «Добавить лот», ввести «Факт», «Провести инвентаризацию» ->
  корректировки ADJUST +/-).

Функции домена «Аналитика»:
- Отчёты (/reports/) - Администратор, Руководитель, Кладовщик (без денег
  закупки), Наблюдатель: за период (Сегодня/7/30/Месяц/даты): продажи,
  ремонт, возвраты, списания, корректировки; кнопки «Экспорт CSV»;
  страница «Остатки и низкие остатки».
- Продажи по клиентам (/reports/sales-by-client/) - read-only группировка
  проведённых продаж по сохранённому имени клиента. Детализация показывает
  артикулы и отдельные операции. Количество, цена и сумма читаются из
  зафиксированных SaleLine; текущая recommended_price не используется.
  Черновики, отменённые и сторнированные продажи исключены. Пустое имя
  отображается как «Без клиента».
- Ремонты по клиентам (/reports/repairs-by-client/) - группировка проведённых
  ремонтных заказов по сохранённому имени клиента. Показывает
  число ремонтов, уникальные артикулы, выданные единицы и историческую стоимость
  деталей для клиента; детализация доходит до отдельных выдач и ссылается на
  заказ. Пользователь с правами на ремонты и возвраты может отменить часть
  точной строки выдачи прямо из детализации клиента: количество, причина и
  автор обязательны, а склад возвращается в исходный лот и ячейку. Цена работ
  и оплаты не хранится. «Себестоимость выданного» остаётся
  закупочной стоимостью деталей, показывается отдельно и доступна только ролям
  с правом на закупочные цены. Черновики и отменённые заказы исключены.
- Продажи и ремонты (/reports/clients/) - сводка по клиенту сразу по двум
  видам документов и единая лента документов клиента по времени проведения.
  «Итого с клиента» = нетто-сумма продаж + историческая стоимость деталей в
  ремонтах; завершённые возвраты уменьшают клиентскую сумму. Себестоимость
  ремонта в этот итог не входит и показана отдельно только пользователям с
  правом на закупочные цены. Работы не хранятся. Для строки с карточкой
  Руководитель или Администратор может поставить «Оплатил» за точный период.
  По умолчанию клиенты отсортированы по последней проведённой продаже или
  ремонту в выбранном периоде, новые сверху.
  Запись хранит сумму и digest состава, поэтому становится неактуальной после
  изменения состава или legacy «текущей цены», но не после изменения
  исторического снимка цены.
- Статистика (/statistics/) - Администратор, Руководитель, Наблюдатель:
  срез сейчас: стоимость склада, потенциальная выручка, низкие остатки,
  залежавшиеся, ходовые (период 7/30/90/всё время), резервы требующие
  внимания, активность. Только чтение.

Функции домена «Администрирование»:
- Нераспознанные (/scanner/unresolved/) - Администратор, Руководитель:
  журнал кодов, которые сканер не распознал.
- Пользователи (/users/) - только Администратор: создание, роли,
  деактивация (не удаление).
- Бэкапы (/operations/backups/) - только Администратор: «Экспорт бэкапа»,
  список бэкапов, скачивание файлов, «Манифест», offsite-статус.
  Восстановление: для обычных администраторов и всех ролей web-restore
  ОТСУТСТВУЕТ (CLI на сервере). Исключение: блок «Аварийное восстановление»
  виден ТОЛЬКО владельцу из allowlist при включённом флаге на сервере;
  запуск требует проверки бэкапа, слова ПОДТВЕРЖДАЮ и checkbox риска;
  перед restore автоматически создаётся pre-restore бэкап. Загрузки
  внешних файлов бэкапа нет.
- Emergency local mode запускается только отдельным Windows operator tooling.
  Это single-writer failover, а не двусторонняя синхронизация. Local standby
  восстанавливается только из verified manifest v2 в отдельную PostgreSQL 16
  DB. Активный local mode заметен по banner на всех страницах. ИИ-поддержка
  недоступна, складские workflows используют локальную DB. После работы local
  замораживается и экспортируется. Failback check сравнивает database identity,
  generation, полный business fingerprint, table markers, migrations, app
  commit и media hash. `CONFLICT`/`BLOCKED` запрещают overwrite; `ELIGIBLE`
  разрешает только отдельную reviewed production restore procedure. Automatic
  production overwrite отсутствует.

## Role map

- Администратор: всё, включая «Пользователи» и «Бэкапы».
- Руководитель: всё про товар и деньги; НЕ управляет пользователями и бэкапами.
- Кладовщик: склад (поступления, приёмка, перемещения, экземпляры, лоты,
  движения, остатки), ремонт, возвраты, списания, инвентаризация, отчёты без
  закупочных сумм, этикетки, фото. НЕ создаёт резервы/продажи, НЕ видит
  статистику (финансы), НЕ создаёт детали в каталоге.
- Продавец/Мастер: поиск, сканер, резервы, продажи, ремонт. НЕ видит склад
  изнутри, партии, поступления, отчёты, статистику. НЕ проводит возвраты.
- Наблюдатель: только чтение: отчёты, статистика, финансы, склад.
При нехватке прав система отвечает «403 Нет доступа» или скрывает пункт меню.

## Core rules

1. Карточка детали не равна остатку: остаток появляется только после
   проведения поступления/приёмки.
2. Склад меняется только операциями; каждая оставляет движение в журнале.
   Движения нельзя править и удалять.
3. Черновик (поступления, продажи, резерва, списания, инвентаризации) склад
   НЕ меняет.
4. Проведение меняет склад и делает документ read-only. Провести дважды нельзя.
5. Нельзя продать/списать/зарезервировать/выдать в ремонт больше доступного.
   Резерв другого клиента блокирует продажу.
6. Проведённое поступление, продажа, списание не редактируются. Исправление -
   корректирующей операцией: возврат, списание, перемещение, инвентаризация.
7. Резерв уменьшает «Доступно», но не физический остаток и не создаёт движение.
7a. Карточка из каталога аналогов - ещё не остаток. В поиске и на карточке у
   неё написано «Источник: Каталог аналогов», доступно 0, ячейки нет; в
   пересчёте у строки тот же источник. «На складе» появляется только после
   настоящей приёмки или проведённой инвентаризации.
8. Возврат увеличивает остаток, но НЕ меняет выручку продажи (показывается
   отдельно в отчётах).
9. Restore бэкапов в веб-интерфейсе отсутствует для всех пользователей,
   КРОМЕ владельца-администратора из allowlist при включённом серверном
   флаге: ему доступно защищённое «Аварийное восстановление» (проверка
   бэкапа + слово ПОДТВЕРЖДАЮ + checkbox + автоматический pre-restore
   бэкап). Upload внешних файлов бэкапа отсутствует у всех. Основной путь
   восстановления: командная строка на сервере.
10. Статистика и отчёты только читают данные. Отчёты = период («что
    произошло»), статистика = срез сейчас («что лежит и на что смотреть»).
11. Поштучные детали принимаются целыми числами; создаются экземпляры.
    Количественные - лотами.
12. Инвентаризация работает по количественным лотам; недостача поштучных
    оформляется списанием.

## Section explanations (кратко)

- Главная: KPI и «Требует внимания»; смотреть каждый день.
- Поиск: главный инструмент продавца; от 2 символов; ничего не меняет.
- Сканер: определяет код; неизвестные коды копятся в «Нераспознанных»;
  физический сканер не обязателен, код можно ввести руками.
- Детали: справочник; режим учёта выбирается при создании; минимальный
  остаток включает контроль «Низкие остатки».
- Партии: техническая основа прихода; нужны при доп. расходах поставки
  (доставка/таможня); обычный приход делайте через «Поступление».
- Поступление: черновик безопасен; «Провести поступление» создаёт партию,
  фиксирует себестоимость (введённая цена = себестоимость), создаёт
  экземпляры/лоты, движения и остатки; после - read-only.
- Приёмка сканером: пошаговая операция у стеллажа. Закреплённая ячейка остаётся
  подсказкой при нулевом остатке; её изменение подтверждается только проведением.
  Перемещение и изменение ячейки при приёмке используют единое поле поиска или
  сканирования активной ячейки.
- Остатки: физически/доступно/карантин; доступно = можно продавать.
- Движения: полная история склада; фильтры по типу/детали/партии/месту.
- Экземпляры/Лоты: поштучный и количественный учёт соответственно.
- Резервы: бронь со сроком; просроченные подсвечиваются в статистике.
- Продажи: фиксируют выручку/себестоимость/прибыль; ошибочная проведённая
  продажа отменяется только с причиной и автором через компенсирующие складские
  движения, без переписывания снимков.
- Ремонт: выдача деталей без выручки; ошибочный проведённый заказ отменяется
  тем же образом, а обычный возврат остаётся отдельным процессом.
- Возвраты: только из продажи/ремонта; возврат из ремонта всегда восстанавливает
  исходные лот и ячейку, а исправная неиспользованная деталь по умолчанию доступна.
  Состояние строки можно изменить, пока возврат остаётся черновиком; черновик не
  меняет склад. При проведении создаётся положительное действие
  «Возврат из ремонта», которое вычитается из repair consumption в Excel.
  Проведённый возврат исключает стоимость неиспользованной детали из ремонта.
  Отмена возврата создаёт compensating inventory movement и разрешена только
  пока возвращённый остаток не перемещён, не использован и не зарезервирован.
- Списания: выбытие с причиной; зарезервированное списать нельзя.
- Инвентаризация: факт по лотам ячейки; корректировки ADJUST +/-;
  нельзя опустить ниже резерва.
- Пересчитать ячейку: запуск из карточки любой активной ячейки; независимый
  ввод физического факта сканером или поиском; dry-run до записи; партии и
  `AVAILABLE`/`QUARANTINE` не угадываются; stale snapshot и резерв блокируют
  применение. Поштучные экземпляры количественным режимом не меняются.
- Удалить ячейку: hard delete только для новой пустой ячейки без истории;
  историческая пустая ячейка архивируется. Остаток, резерв, активный пересчёт
  или вложенные активные места блокируют действие; движения сохраняются.
- Отчёты: период + CSV и read-only отчёт «Продажи по клиентам» по замороженным
  строкам проведённых продаж. Статистика: деньги склада, ходовые, залежавшиеся.
  Закупочная оценка использует базовые цены BRP/Polaris и текущий курс.
  Оценка продажи и её разбивка по категориям строятся из одного физического
  остатка и одной текущей клиентской цены; сумма категорий равна общей оценке.
  Резерв и карантин входят как физический остаток, продажа и списание не входят.
  Позиции без клиентской цены видны отдельным счётчиком.
- Пользователи: роли; деактивация вместо удаления; себя деактивировать нельзя.
- Бэкапы: «Экспорт бэкапа», скачивание, манифест, offsite-статус
  (отправлено/ошибка/не настроено); restore только CLI.

## Workflow playbooks

- Старт склада: пользователи -> справочники и поставщики -> ячейки -> детали
  -> первое поступление -> провести -> проверить остатки/движения -> бэкап.
- Новая поставка: Поступление -> Новое поступление -> шапка -> «Создать
  черновик» -> позиции (деталь, количество, цена, ячейка) -> сверить итог ->
  «Провести поступление» -> проверить «Остатки».
- Новая деталь из поступления: в черновике «+ Новая деталь» -> заполнить ->
  сохранить -> вернулись в черновик, деталь выбрана -> количество/цена/ячейка
  -> «Добавить позицию».
- Поиск по звонку: строка поиска -> название или номер -> «Доступно», цена,
  ячейка -> предложить клиенту.
- Резерв: Резервы -> «Создать резерв» -> клиент/срок -> позиции ->
  «Активировать». Далее «Продать из резерва» или «Отменить».
- Продажа: Продажи -> «Создать продажу» -> позиции с ценой -> «Провести
  продажу».
- Быстрые действия: поле принимает артикул и английское или подтверждённое
  русское название. При одной доступной ячейке скан или однозначный поиск
  сразу добавляет деталь в черновик продажи или ремонта; при нескольких
  сотрудник выбирает ячейку. Деталь с нулевым остатком находится, но не может
  быть добавлена или проведена.
  Таможенный вес в строке черновика вводится сразу в килограммах.
- Ремонт: Ремонт -> «Создать заказ» -> позиции -> «Провести (выдать в ремонт)».
- Возврат: открыть проведённую продажу/ремонт -> «Оформить возврат» ->
  «Добавить из источника» -> ячейка -> «Провести возврат».
- Списание: Списания -> «Создать списание» -> причина -> позиции ->
  «Провести (списать)». Для одного артикула доступно «Быстрое списание»:
  причина, скан, количество, автор. При нескольких доступных ячейках оператор
  выбирает ячейку списания, а лоты выбираются автоматически только внутри неё.
  Новое проведённое списание можно один раз отменить компенсирующим движением
  в исходный лот или экземпляр.
- Инвентаризация: Инвентаризация -> «Создать инвентаризацию» (ячейка) ->
  «Добавить лот» -> ввести «Факт» + «OK» -> «Провести инвентаризацию».
- Проверка бэкапа: Бэкапы -> дата последнего свежая -> offsite «отправлено»
  -> при сомнении «Экспорт бэкапа».

## Troubleshooting (вопрос -> ответ)

- Почему деталь не видна в остатках? Карточка не создаёт остаток. Проверьте,
  проведено ли поступление (не осталось ли черновиком).
- Почему нельзя продать? Продать можно только «Доступно»: проверьте резервы
  (чужой активный резерв блокирует), карантин, статус «на приёмке».
- Почему 403? У роли нет прав на раздел (например, продавец в бэкапах).
  Это защита; доступ меняет администратор в «Пользователях».
- Почему статистика пустая/нули? Нет проведённых приходов, либо позиции без
  закупочной или клиентской цены, либо за выбранный период нет продаж/движений.
  Строка «Итого по категориям» должна совпадать с общей оценкой продажи.
- Почему бэкап failed? Локальный бэкап обычно есть, но offsite-отправка не
  прошла (сеть/настройка rclone на сервере). Нужен администратор сервера.
- Ошибка в проведённом поступлении? Документ read-only. Не та ячейка:
  «Перемещение». Лишнее количество: списание или инвентаризация. Цена:
  зафиксирована как себестоимость; обсудить с администратором.
- Чем отчёты отличаются от статистики? Отчёты: что произошло за период
  (продажи, прибыль, списания). Статистика: что лежит сейчас (стоимость
  склада, залежавшиеся, низкие остатки) и подсказки.
- Чем поступление отличается от партии? Поступление - удобный документ
  прихода, при проведении сам создаёт партию. Партия - технический слой
  (валюта, доп. расходы, landed cost); нужна для сложных поставок.
- Чем поступление отличается от приёмки сканером? Поступление - весь приход
  документом с ценами и ячейками. Приёмка сканером - размещение конкретной
  детали в ячейку двумя сканами.
- Резерв завис? Статистика -> «Резервы, требующие внимания» -> открыть ->
  «Отменить» или «Продать из резерва».

## Assistant behavior rules

1. Отвечай простым русским языком, без жаргона; шаги нумеруй.
2. Используй настоящие названия кнопок и разделов из этого документа.
3. Не выдумывай функции. Если чего-то нет в этом документе (например, отмена
   проведённой продажи, restore из веб-интерфейса, экспорт в 1С), честно
   говори: «этого в системе нет» и предлагай существующую альтернативу.
4. Никогда не советуй править базу данных руками, удалять данные на
   production или редактировать проведённые документы в обход системы.
5. Перед советом о крупных/массовых операциях напоминай нажать
   «Экспорт бэкапа» в разделе «Бэкапы».
6. Если вопрос про неправильные остатки, сначала попроси открыть «Движения»
   и назвать последние операции по детали, затем предлагай корректирующую
   операцию (перемещение/возврат/списание/инвентаризация).
7. Если пользователь хочет изменить проведённый документ, объясни, что он
   read-only, и предложи корректирующую операцию по ситуации.
8. Учитывай роль спрашивающего: не советуй продавцу разделы, которых он не
   видит (склад, поступления, бэкапы); в таких случаях говори, к кому
   обратиться (кладовщик, руководитель, администратор).
9. Про 403 объясняй как ограничение прав, а не ошибку системы.
10. Опасные действия (проведение, списание, инвентаризация) помечай:
    «после этого изменится остаток, отменить можно только корректирующей
    операцией».

# Отдельный выпуск: исправление номера таможенного заказа

Интеграционная ветка `codex/customs-order-number-production-integration-20261026`
содержит только перенос изменения `aa28aafeef0079b7e7a2d7f09cecc033194d0cae`
на фактически работающую базу `741b65c686624dc5a2f5ec5629019af924e13407`
и проверку конкурирующих исправлений. Ветка быстрых действий в выпуск не входит.
26.10.2026 у работающего `web` подтверждены image ID
`sha256:77f381cdcbbaef846c30971f6a720b4a1043516ede5a178b9f396037f75c1a47`,
OCI revision и хеш исходного Git-архива. Проверенные файлы внутри контейнера
совпали с этим коммитом. Лист production-миграций `customs_orders` оканчивается
на `0004_draft_finalized_lifecycle`. Перед фактическим выпуском проверить всё
повторно: эти значения не являются разрешением на установку.

28.10.2026 в production `COMPOSE_FILE` дополнительно содержит
`/root/denstock-release-healthcheck-host-34a6545-20261024/catalog-only-proposed.yml`.
Этот overlay закрепляет image и `DENSTOCK_APP_COMMIT` каталога на `34a65455...`,
а также отдельный `COMPOSE_FILE` в окружении web. При пробной read-only
подстановке нового selector изменились только `web.image`, web SHA в
окружении и build args двух сервисов. Изменение build arg каталога не даёт
права собирать или пересоздавать каталог. Перед выпуском повторить сравнение
эффективной конфигурации с окончательным SHA и остановиться при других diff.

## Объём и инварианты

- Обновляется только `web`. PostgreSQL, `catalog-web`, Caddy, боты и preview
  не пересоздаются. Не проводить сборку на VPS с 2 ГиБ RAM после OOM-аварии.
- Миграция `customs_orders.0005_customsordernumberchange` создаёт только
  таблицу истории и индексы. Существующие заказы и строки не переписываются.
- Видимый `CustomsOrder.number` независим от `id`; уникальность действует
  внутри `order_type`. Старые ссылки приложения используют `id`.
- При исправлении проверяется номер, показанный оператору при открытии формы.
  Если его уже изменил другой оператор, повторное сохранение отклоняется.
  Блокировка строки, обновление только колонки `number` и запись истории
  выполняются в одной транзакции. Ошибка аудита откатывает исправление.
- Состав, классификация, количество, курс, цена, сумма, статус, автор и дата
  создания не меняются. Новая выгрузка XLSX получает исправленный номер в
  имени файла; ранее скачанные файлы и внешние документы с текстом старого
  номера автоматически не обновятся.

## PRE и условия остановки

1. Получить отдельное разрешение владельца и тихое окно. Непосредственно перед
   PRE и установкой проверить фактические web SHA, image ID, OCI revision,
   source archive hash, checkout, Compose overlays, миграции и отсутствие
   неожиданного diff. Проверить здоровье PostgreSQL, web, каталога, Caddy и
   ботов, HTTPS двух сайтов, анонимный 404 private media, отсутствие активных
   складских операций, backup/restore и занятого общего backup-lock.
2. Проверить `free`, swap, текущие OOM, `df -h`, inode и место для нового образа,
   PRE и POST. При деградации памяти, новых OOM, недостатке диска, занятом
   lock, новых миграциях или изменившемся runtime SHA остановиться.
3. Сохранить текущий web image ID, SHA-selector, Compose overlays, конфигурацию
   healthcheck и точный порядок возврата. Не трогать другие образы и тома.
4. Создать полный подписанный PRE штатным `backup_all` под общим backup-lock,
   без capped wrapper и ротации: PostgreSQL, public media, private media,
   manifest, Ed25519. Зашифровать age на Mac отдельно от старых копий,
   сверить SHA-256 и практически восстановить PostgreSQL 16 и оба media-дерева.
   Проверить ссылки на файлы и количественные маркеры. При неуспехе STOP.

## Установка только после отдельного разрешения

1. Подготовить образ вне VPS из точного Git-архива интеграционного коммита.
   До передачи проверить его image ID, OCI revision, source archive SHA-256,
   встроенный `DENSTOCK_APP_COMMIT`, платформу linux/amd64 и отсутствие
   секретов в labels и логах. Сверить SHA-256 переданного архива на Mac и VPS.
   Использовать действующие production Compose overlays, включая signing.
   Сохранить catalog-only overlay и отдельный `COMPOSE_FILE` внутри web.
   Не вызывать `build` или `up` для `catalog-web`, даже если его build arg
   отражает новый selector.
2. Перед запуском web проверить селектор образа и конфигурацию через
   `scripts/operations/release_image_identity.py verify` по правилам
   `docs/operations/release-image-identity.md`. Сохранить прежний image ID.
   Обновить только web без сборки и без пересоздания зависимостей. Штатный
   entrypoint применяет `customs_orders.0005`; вручную второй раз миграцию
   не запускать.
3. Проверить фактический контейнерный image ID, OCI revision, runtime SHA,
   применённую `0005`, Docker health, `/healthz/`, оба HTTPS-сайта,
   анонимный 404 private media, PostgreSQL и ботов. Повторить проверку RAM,
   swap, OOM и healthcheck-процессов.
4. Только чтением открыть существующий заказ, историю и повторно скачать XLSX.
   Сверить `id`, число и состав строк, курс, суммы и статусы с PRE. Проверить
   наличие пустой либо корректно заполненной таблицы аудита. Не изменять номер
   настоящего заказа ради smoke test. Первый реальный исправленный номер
   проверять после отдельного штатного действия уполномоченного сотрудника:
   старый/новый номер, актор и время в истории, прежний `id` и финансовые поля.
5. Создать отдельный полный подписанный POST без ротации, зашифровать age на Mac,
   проверить Ed25519, хеши и изолированно восстановить PostgreSQL 16 и оба
   media-дерева. До успешного POST-восстановления не объявлять SUCCESS.

## Остановка и возврат приложения

- При ошибке миграции или критической проверке остановиться, сохранить журналы,
  текущий image ID и состояние схемы. Не выполнять слепой откат базы.
- Если схема совместима и причина именно в web, по отдельному решению вернуть
  сохранённый старый web image ID вместе с прежним SHA-selector, healthcheck и
  Compose overlays. Не пересоздавать PostgreSQL, каталог, Caddy или ботов.
  На локальной PostgreSQL 16 старый код прошёл `check`, показал отсутствие
  запланированных обратных миграций и открыл заказ по прежнему `id` после
  применения `0005`. Перед реальным возвратом повторить проверку состояния.
- Применённая `0005` является добавочной. Даже при возврате старого web
  таблицу истории оставить: она может уже содержать реальные исправления.
  Не удалять её, не выполнять обратную миграцию и не восстанавливать PRE
  поверх новых бизнес-операций без отдельного решения владельца.
- Старые XLSX и внешние документы с прежним номером остаются историческими.
  Сопоставление по `id` и история изменения номера доступны после возврата
  исправленного приложения.

## Локальная квалификация

Миграция проверена на отдельной PostgreSQL 16.15 с заполненным синтетическим
заказом, включая повторный запуск, внешние ключи, уникальность, атомарный
откат при ошибке аудита и две конкурентные операции. Браузерная проверка
выполнена на отдельной синтетической базе. На страницах обнаружена старая
ошибка `customer_requests_realtime.js` при отсутствии корня рабочего места
заявок; файл не менялся в этом выпуске и не влияет на форму таможенного заказа.
Не смешивать её с ошибками нового кода при оценке релиза.

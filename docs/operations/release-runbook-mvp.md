# Выпуск DenisStock: репетированная процедура

Документ написан после полной репетиции на QA: предшественник production,
обновление, резервная копия, восстановление, откат. Все числа ниже получены
фактически, а не предположены.

Процедура репетирована на QA от одного production-снимка к одному кандидату.
Конкретные хеши здесь намеренно не зафиксированы: подставляйте те, что идут в
этот выпуск, иначе документ со временем начнёт указывать на устаревшую версию.

Перед началом запишите две величины и держите их под рукой до конца выпуска:

- `PROD_SHA` — что развёрнуто сейчас, из `ops_check` или `release_baseline`;
- `NEW_SHA` — что разворачиваете, из `git rev-parse HEAD` кандидата.

Дельта миграций проверяется командой, а не памятью:

```
git diff --name-status <PROD_SHA> <NEW_SHA> -- "*/migrations/*.py"
```

Для кандидата FINAL MVP RC v3 она составляет одну миграцию: `operations.0004`.
Если команда показывает больше, останавливайтесь и разбирайтесь: раздел 6
рассчитан ровно на одну обратимую миграцию.

---

## 1. Что именно меняет этот выпуск

| | |
|---|---|
| Новых миграций | **одна**: `operations.0004_deploymentstate_emergency_primary_authorization` |
| Её характер | два добавленных поля: `authorized_emergency_primary_id` (UUID, NULL) и `primary_authorization_epoch` (целое, по умолчанию 0) |
| Данные | не трогает |
| Обратимость | полная |
| `brp.0003` | **уже в production**, повторно не применяется |

После обновления аварийный режим остаётся **не назначенным** (`authorized = NULL`,
`epoch = 0`), то есть аварийная активация закрыта, пока администратор явно не
назначит Primary. Это проверено.

---

## 2. Перед выпуском: базовый снимок

Обязательный шаг. Снимок читает только данные, ничего не пишет и безопасен на production.

```bash
python manage.py shell < scripts/operations/release_baseline.py > before.txt
```

Снимок обязан показать:

- `deployment_state=present`, `write_state=normal`;
- `offline_sessions_unfinished=0` — **если не ноль, выпуск отменяется**: склад где-то работает автономно;
- `recount_locks_open=0` — если не ноль, идёт инвентаризация, дождитесь окончания;
- `lots_negative=0`, `lots_without_location=0`, `lots_without_batch_line=0`;
- `runtime_sha` — если `EMPTY`, переменная версии не задана, см. раздел 4.

Сохраните `before.txt`. После выпуска он сравнивается построчно.

Сразу после снимка сделайте резервную копию и **проверьте её** (раздел 6).

---

## 3. Порядок развёртывания

Проверено на репетиции; шаги идут строго в этом порядке.

1. Снять `before.txt` (раздел 2).
2. Сделать и проверить резервную копию (раздел 6).
3. Собрать образ ровно из выпускаемого SHA.
4. **Передать `DENSTOCK_APP_COMMIT` = этот же SHA** в окружение приложения.
5. Применить миграции: `python manage.py migrate --no-input`.
6. Пересоздать только контейнеры приложения и прокси. **PostgreSQL не перезапускать.**
7. Проверить `/healthz` и `python manage.py ops_check`.
8. Снять `after.txt` и сравнить с `before.txt`.

### Что обязано отличаться в сравнении, и ничего больше

```
deployed_sha, runtime_sha, migrations_total, primary_authorization_epoch
```

На репетиции сравнение дало ровно эти четыре строки: `migrations_total` 92 → 93,
`primary_authorization_epoch` отсутствовал → 0, версии сменились. **Все складские
и денежные показатели совпали побитово.** Любое другое расхождение означает, что
выпуск изменил данные, и это повод остановиться и разбираться.

---

## 4. Переменная версии приложения

`DENSTOCK_APP_COMMIT` необязательна и по умолчанию пуста, а запасной вариант
читает git, которого в контейнере нет. Пустая версия уже приводила к резервным
копиям без метаданных.

Проверка: в `before.txt` строка `runtime_sha` не должна быть `EMPTY`. На репетиции
после передачи переменной manifest резервной копии получил точный SHA сборки.

## 5. Дерево решений при откате

Всё проверено на репетиции, а не выведено из документации.

### Откат только кода: **БЕЗОПАСЕН**

Старый код против новой схемы работает. Проверено: `manage.py check` без замечаний,
базовый снимок совпадает по всем данным, лишние колонки просто игнорируются.

```
вернуть предыдущий образ  →  перезапустить приложение  →  проверить /healthz
```

Восстанавливать базу **не нужно**. Миграцию отменять **не нужно**.

Это основной и рекомендуемый путь отката.

### Откат только схемы: **ЗАПРЕЩЁН**

Новый код против старой схемы падает:
`column operations_deploymentstate.authorized_emergency_primary_id does not exist`.

Никогда не отменяйте `operations.0004`, оставив новый код развёрнутым.

### Полный откат (код и схема)

Возможен, но не нужен. Если всё же требуется, **порядок обязателен**:

1. пока развёрнут НОВЫЙ код: `python manage.py migrate operations 0003`;
2. затем вернуть старый образ.

Обратный порядок физически не работает: в старом коде файла миграции `0004` нет,
и Django не может отменить то, чего не видит. На репетиции команда просто ничего
не сделала.

### Когда нужно восстановление из копии

Только если данные повреждены. Само по себе неудачное обновление кода
восстановления не требует: миграция данные не трогает.

---

## 6. Резервная копия и восстановление

### Создание

```bash
python manage.py backup_all --keep-last 3
```

Проверено на репетиции. Manifest содержит: точный `app_commit`, `verification_status=verified`,
**время с часовым поясом** (`+03:00`), контрольные суммы базы и media, и **подпись**
с закреплённым идентификатором ключа.

### Проверка (обязательна)

```bash
python manage.py verify_backup <имя_каталога_копии>
```

Аргумент это **имя каталога**, а не путь. Исправная копия проходит семь проверок.
Прерванная копия корректно отклоняется с сообщением про manifest.

### Удержание копий

Проверено специально: две прерванные копии между исправными **не вытеснили**
ни одной проверенной. Прерванные считаются отдельной квотой.

### Восстановление

Восстанавливать нужно в **отдельную** базу, а не поверх рабочей.

```bash
pg_restore -l <копия>/db.dump        # архив читается, видно таблицы
python manage.py restore_db <копия>/db.dump --yes
python manage.py shell < scripts/operations/release_baseline.py
```

На репетиции восстановленная база совпала с исходной по всем данным.

## 7. Сборка с нуля и аварийное восстановление сервера

Важное отличие кандидата от текущего production.

**Текущий production собрать с нуля нельзя.** `migrate` на пустой базе падает на
посевной миграции каталога: защита записи обращается к таблице управляющего
состояния раньше, чем та создана.

**Кандидат это чинит.** На репетиции он мигрировал с нуля полностью, 93 миграции.

Практический вывод: до выпуска кандидата единственный путь восстановления сервера
это восстановление из резервной копии, а не установка с нуля. После выпуска
доступны оба.

## 8. Проверка первого часа после выпуска

Только чтение, без складских операций. Занимает 5 минут.

| Что | Ожидание |
|---|---|
| `/healthz` | `status=ok`, `db=ok` |
| `python manage.py ops_check` | «Готовность к эксплуатации: ОК» |
| Вход администратором | форма входа открывается, вход проходит |
| Поиск по известному номеру | деталь найдена, видно количество и ячейку |
| Остатки | страница открывается |
| Ячейки | список открывается |
| Приёмка (открыть, не проводить) | страница открывается |
| Быстрые действия | страница открывается |
| Продажи, Резервы | списки открываются |
| Ремонты | список открывается |
| Клиенты | список открывается |
| Отчёты | сводка открывается |
| Импорт каталога BRP | список партий открывается |
| Сравнение `before.txt` / `after.txt` | отличия только в четырёх разрешённых строках |
| Свежая резервная копия | создана и прошла `verify_backup` |

Складские записи в production для проверки не создавайте: рабочий день покажет их сам.

## 9. Первый рабочий день: лист для Дениса

Одна страница. Утром пройти по порядку, в течение дня отмечать только то, что
реально мешало.

**Утро**

1. Войти в систему.
2. Найти деталь по номеру. Видно ли сразу: есть, сколько, где, почём?
3. Принять поступление на одну позицию.
4. Открыть Быстрые действия, отсканировать деталь.
5. Провести продажу.
6. Провести выдачу в ремонт.
7. Открыть историю и найти проданную деталь по номеру.

**Записывать в течение дня только это**

- что оказалось непонятно;
- где пришлось делать лишние клики;
- что работало медленно;
- где пришлось звонить разработчику.

Ничего больше записывать не нужно. Четырёх строк за день достаточно.

---

## 10. Приёмка Быстрых действий

Проверяется после того, как Codex закончит новый поток.

1. Отсканировать деталь A.
2. Отсканировать деталь A ещё раз.
3. Отсканировать деталь B.

Ожидание в корзине: **A x2, B x1** одной строкой на деталь.

4. Выбрать один тип действия.
5. Указать одного клиента или один комментарий.
6. **До отправки**: остаток на складе не изменился.
7. Отправить один раз.
8. **После отправки**: движение ровно одно на позицию.
9. Обновить страницу браузером и повторить отправку: удвоения быть не должно.

## 11. Проверка ролей

| Роль | Обязана видеть в меню | Не должна видеть |
|---|---|---|
| Администратор | всё, включая пользователей и цены | — |
| Руководитель | остатки, приёмка, продажи, ремонты, клиенты, отчёты, импорт каталога, цены | пользователей |
| Кладовщик | остатки, склад, приёмка, перемещение, движения, быстрые действия, ремонты, возвраты | цены, пользователей |
| Продавец/Мастер | **быстрые действия**, продажи, резервы, ремонты, клиенты | партии, лоты, экземпляры |

Отдельно проверить: продавец видит пункт «Быстрые действия». Это его основной
ежедневный экран, и в прежней версии он был доступен только по прямому адресу.

Показанный пункт меню обязан открываться. Кнопка, ведущая в «нет доступа», это
дефект.

## 12. Проверка после реального импорта каталога BRP

Выполняется пользователем после Apply. Импорт занимает до минуты, кнопка на это
время блокируется и меняет надпись.

1. Партия помечена применённой, страница успеха показана.
2. Счётчики: всего, актуальных, неактуальных. Сумма актуальных и неактуальных равна всего.
3. Число снятых с актуальности совпадает с показанным в предварительном просмотре.
4. Статус `UCP` в новом файле обрабатывается как `USE`.
5. Взять позицию со статусом `VIN`: цена клиента посчитана от оптовой **плюс 25 USD**.
6. Взять позицию со статусом `OBS`: карточка на месте, остаток на месте, история на месте.
7. Взять позицию, пропавшую из файла: она неактуальна, но **не удалена**, остаток по ней ищется.
8. Неактуальная позиция **не даёт** текущую цену.
9. Открыть продажу, проведённую до импорта: суммы и имя клиента не изменились.

Если пункт 7 или 9 не выполняется, остановиться и не проводить следующий импорт.

## 13. Понятные состояния для сотрудника

Сотруднику не нужно знать про подписи, эпохи и идентификаторы. Он должен видеть
только состояние и следующее действие:

| Состояние | Что означает | Что делать |
|---|---|---|
| Аварийная копия готова | можно работать автономно | ничего |
| Копия устарела | давно не обновлялась | сообщить администратору |
| Этот компьютер не назначен основным | работать нельзя | сообщить администратору |
| Требуется администратор | нужна настройка | сообщить администратору |

---

## 14. Формулировка при сбое

При ошибке сервера **нельзя** обещать, что данные точно не изменились: транзакция
могла зафиксироваться, а сбой произойти при отрисовке страницы.

Правильная инструкция оператору:

> Действие могло не завершиться. **Сначала проверьте историю или список
> документов**, и только потом повторяйте.

Это правило действует независимо от текста на странице ошибки.

## 15. Порядок физического внедрения

| Этап | Что | Условие перехода к следующему |
|---|---|---|
| 1 | Выпуск кандидата на production | проверка первого часа пройдена |
| 2 | Денис работает в системе | 1-2 дня реальной работы |
| 3 | Исправления по обратной связи | список из листа первого дня закрыт |
| 4 | Подготовка аварийного компьютера | см. раздел 16 |
| 5 | Подключение остальных компьютеров как браузерных клиентов | — |
| 6 | Учебная тревога: отключить production, отработать автономный день | — |

Этап 1 и 2 **не блокируются** отсутствием аварийного компьютера, если резервные
копии создаются и проверяются.

## 16. Требования к аварийному компьютеру

Собрать до закупки или выделения машины:

- Windows 10/11 64-bit с поддержкой WSL2;
- виртуализация включена в BIOS;
- не менее 8 ГБ оперативной памяти, желательно 16;
- не менее 50 ГБ свободного места на диске;
- фиксированный адрес в локальной сети склада;
- права администратора на машине для установки;
- машина не выключается на ночь, если запланировано обновление резервной копии по расписанию;
- браузер на остальных компьютерах склада для работы клиентами.

Docker Desktop **не требуется**: используется движок Docker внутри WSL2.

## 17. Первичная настройка аварийного компьютера

Порядок действий администратора. Выполняется **после** стабильной работы production.

1. На production создать ключ подписи и **сохранить приватную часть только там**.
2. Публичную часть передать на рабочую станцию при установке (закрепляется установщиком).
3. Установить рабочую станцию, получить её идентификатор.
4. На production назначить эту станцию основной аварийной.
5. Создать свежую подписанную резервную копию.
6. Обновить standby на станции, дождаться состояния «готово».
7. Учебно отключить production и проверить: станция переходит в работу.
8. Завершить автономную сессию, выполнить финальный экспорт.

Приватный ключ подписи не должен попадать в репозиторий, в резервные копии, в
облако и на рабочую станцию.

---

## 18. Замена аварийного компьютера

Обязательный порядок. Он закрывает известное ограничение: старая станция со своей
старой подписанной копией способна включиться автономно, потому что сверить
назначение ей не с чем.

1. Назначить новую станцию B.
2. Обновить standby на B.
3. Убедиться, что B в состоянии «готово».
4. **Вывести станцию A из эксплуатации физически.**
5. **Удалить или обезвредить standby на A.**
6. Только после этого считать замену завершённой.

Пропуск шагов 4 и 5 оставляет возможность появления второго пишущего компьютера.

## 19. HTTPS и cookies: решение на потом

Рекомендация, менять сейчас не нужно.

Production работает через обратный прокси и должен получить HTTPS, а вместе с ним
защищённые cookies и HSTS. Аварийная локальная сеть может работать по HTTP:
сертификата для локального адреса обычно нет.

Разделить это можно по режиму работы (`DENSTOCK_MODE`): включать защищённые cookies
только в production, оставляя аварийный режим как есть. Аварийный контур это не
ломает, потому что доверие там строится на подписи копии, а не на транспорте.

Срок: после запуска, сентябрь.

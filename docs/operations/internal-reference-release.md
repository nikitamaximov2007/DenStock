# Внутренние справочные номера: план выпуска

Этот документ готовит выпуск ветки `codex/refnum-prod-integration-20261026`.
Сам по себе он не разрешает менять production. Исходный SHA работающего `web`
при подготовке: `741b65c686624dc5a2f5ec5629019af924e13407`.
Перед выпуском нужно заново подтвердить его и точный SHA кандидата.

## До обновления

1. Получить отдельное разрешение владельца на production-выпуск. В режиме
   только чтения сверить `git rev-parse HEAD`, `DENSTOCK_APP_COMMIT`, running
   image identity, состояние `docker compose ps`, `/healthz/`, журнал ошибок,
   незавершённые складские операции и отсутствие параллельного деплоя.
   При изменении production SHA пересобрать интеграционную ветку от нового SHA.
2. Проверить `free -h`, `df -h /opt/denstock`, swap и OOM-события. Не начинать
   сборку на VPS при нехватке памяти или места. Не запускать одновременно
   тяжёлые backup, restore и сборку образа.
3. Создать полный подписанный PRE backup штатным механизмом без ротации.
   Проверить `verify_backup` для конкретного run: `db.dump`, `media.tar.gz`,
   `private_media.tar.gz`, подпись Ed25519, SHA-256 и source commit. Подтвердить
   offsite-копию. Восстановить PRE в изолированной PostgreSQL 16 и проверить
   оба дерева файлов. Сохранить PRE и прежний образ для отката.
4. Сверить `python manage.py makemigrations --check --dry-run` и diff миграций:
   этот выпуск не содержит миграций. Убедиться, что в выпуск не включены
   соседние задачи по клиентскому поиску и таможенному номеру.

## Обновление после отдельного разрешения

1. Собрать образ `web` из точного одобренного SHA средствами
   `scripts/operations/release_image_identity.py build --sha <SHA> --services web`.
   Сверить OCI revision и source archive hash. Сохранить прежний image ID.
2. Обновить только `web` через существующую процедуру с `--no-build --no-deps`.
   Не пересоздавать PostgreSQL, Caddy, каталог, ботов и таймеры. Новых миграций
   нет. Перед переключением подтвердить достаточный запас памяти и диска.
3. Проверить running SHA, `docker compose ps`, `/healthz/`, вход оператора и
   журналы. Затем выполнить только чтение: поиск `AT-04164`, `127388`,
   `010-090`, `01-0090` и неоднозначного номера без дефиса. Ожидаются одна
   карточка BRONCO для первых двух запросов, разные карточки для двух
   структурных артикулов и отсутствие автоматического выбора при коллизии.
   Проверить страницы инвентаризации и приёмки без проведения документов.
   Реальные складские данные для smoke test не менять.
4. Наблюдать за ошибками `web`, памятью, swap и OOM. Подтвердить, что остатки,
   движения и документы не изменились от одних поисковых запросов. Создать
   и проверить POST backup по тому же стандарту только в согласованном окне.

## Откат

При сбое остановить выпуск и сохранить журналы. Вернуть прежний `web` image ID
и прежний source SHA штатной процедурой app-only rollback, затем повторить
healthcheck и чтение складских данных. База и медиа при этом остаются на месте:
миграций в выпуске нет. Восстановление PRE поверх действующей базы может
потерять новые документы; это отдельное аварийное решение владельца, не часть
обычного отката.

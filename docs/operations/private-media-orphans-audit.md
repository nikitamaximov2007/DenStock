## Где пишутся и читаются ссылки на приватные файлы

Полный список мест, которые сканер ссылок обязан учитывать. Только два из них
являются `FileField`; остальные это текст, JSON или хэш.

| Источник | Тип ссылки | Пишет | Читает |
|---|---|---|---|
| `TelegramMessage.attachment`, `MaxMessage.attachment` | `FileField`, `upload_to="customer_requests/"`, хранилище `PrivateAttachmentStorage` | `operator_replies._queue_max_reply` / `_queue_telegram_reply` (вложение оператора из веба, Telegram или MAX) | боты при отправке (`read_attachment`), очистка после доставки |
| `SupportAttachment.relative_path` | `CharField` (`ai-support/ГГГГ/ММ/<uuid>.<ext>`) | `ai_support.services._attach_image` | `ai_support.views` (выдача по праву), `purge_ai_support_data` |
| `CatalogImportBatch.stored_path` | `CharField`, имя внутри `catalog-imports/` | `catalog_import.services.save_upload`; correction-партия BRP **копирует** `stored_path` исходной партии | `run_check`, `apply_batch` (сверка SHA-256), просмотр структуры, скачивание исходного прайса, `brp.correction` |
| `CatalogImportBatch.source_sha256` | SHA-256 содержимого | `save_upload` | `apply_batch`, `brp.correction` |
| `CatalogImportBatch.summary` (JSON) у correction-партии | `previous_filename` (только базовое имя) и `previous_sha256` | `brp.correction.apply_zero_wholesale_correction` (`--previous-file` из CLI) | никто в коде; это доказательство, по какому прайсу исправлены цены |
| `BrpCatalogPart.source_file`, `PolarisCatalogPart.source_file` | только базовое имя файла, без каталога | импортёры (`path.name` и из веба, и из CLI с произвольным путём) | никто в коде, это провенанс |

Проверено, что путей к приватным файлам нет в `WorkspaceEvent.payload`
(только id и номер заявки), в outbox-строках Telegram/MAX (ссылка на сообщение
через FK), в `MaxMessage.buttons` и в `max_attachment_token` (это токен файла
на стороне MAX, а не локальный путь).

### Внешние копии и зависимости

- Вложения оператора после доставки лежат также у Telegram и MAX (их серверы).
  Входящие вложения оператора скачиваются с `getFile` Telegram и по URL MAX.
- Скриншоты ИИ-поддержки помечаются `shared_with_provider_at`: они переданы
  внешнему ИИ-провайдеру.
- Исходные прайсы приходят от поставщиков, но в системе это единственная копия,
  по которой можно доказать примененные цены (`source_sha256`).

## Откуда берутся «сироты» (по коду)

Файл без ссылки появляется, когда файл записан, а строка БД не появилась или
исчезла без удаления файла:

1. **Вложение оператора, транзакция откатилась.** В `_queue_*_reply` файл
   сохраняется внутри транзакции до создания outbox-события. Откат после
   `attachment.save()` оставляет файл без строки.
2. **Удаление после доставки не выполнилось.** `cleanup_attachment` очищает
   поле и удаляет файл в `on_commit`. Ошибка удаления или остановка процесса
   между commit и удалением оставляет файл. Это сделано намеренно: «сирота»
   восстановима, потерянная ссылка нет.
3. **Прежняя версия `reconcile_message_attachments_private --apply`.** Ошибка
   описана ниже: каждый запуск создавал в приватном томе копию под чужим
   именем `<имя>_XXXXXXX.<расширение>`, на которую не ссылается ни одна строка.
   Два legacy-вложения и два запуска дают ровно 4 таких файла. Это гипотеза,
   ее проверка описана ниже.
4. **Партия импорта удалена из админки.** `CatalogImportBatchAdmin` не
   запрещает удаление, а удаление строки не трогает файл.
5. **Загрузка прайса прервана** после записи файла, но до создания партии
   (ошибка чтения, разрыв, ошибка БД).
6. **Correction-партия BRP.** Если `--previous-file` указывал на файл внутри
   `catalog-imports/`, ссылка на него есть только в JSON `summary`
   (`previous_filename`, `previous_sha256`). Сканер по `stored_path` его не видит.
7. **ИИ-поддержка.** Удаление пользователя каскадом удаляет беседы и строки
   `SupportAttachment`, но не файлы. `purge_ai_support_data` удаляет файлы до
   строк: сбой транзакции после удаления оставит строки без файлов (обратная
   проблема).

## Как доказать происхождение 5 «сирот» (только чтение, на копии)

Делать на расшифрованной stage-копии или на сервере только чтением, вывод
без имен файлов (по хэшам):

1. Для каждой «сироты» `customer_requests/` вычислить SHA-256 и сравнить с
   двумя публичными legacy-файлами. Совпадение плюс имя по шаблону
   `<имя legacy>_` + 7 букв/цифр + то же расширение доказывает пункт 3.
2. Для «сироты» `catalog-imports/` сравнить SHA-256 со всеми
   `CatalogImportBatch.source_sha256` и со всеми `summary->>'previous_sha256'`.
   Совпадение означает, что это доказательство цен, а не мусор.
3. Сравнить базовое имя с `source_file` BRP/Polaris и `summary->>'previous_filename'`.
4. Время изменения файла сравнить с `created_at` сообщений и партий: файл
   старше всех строк указывает на пункты 4 или 5.

## Когда удаление вообще допустимо

По умолчанию ничего не удалять. Удаление «сироты» допустимо только при всех
условиях одновременно:

1. Файл не совпадает по SHA-256 ни с одним `source_sha256`, `previous_sha256`,
   `SupportAttachment.sha256` и ни с одним файлом, на который ссылается строка.
2. Его имя не встречается ни в одном источнике из таблицы выше, включая JSON
   и базовые имена.
3. Файл есть минимум в двух независимых проверенных копиях (offsite и
   зашифрованная копия на Mac), чтобы удаление было обратимым.
4. Владелец письменно решил, что это не коммерческий документ, который нужно
   хранить (прайсы поставщика), и не персональные данные с отдельным сроком.
5. Сразу после удаления делается новая подписанная копия и `verify_backup`.

Для дублей из пункта 3 (байт в байт равны legacy-вложению) удаление
безопасно после переноса legacy-вложения в приватный том. Прайсы и скриншоты
ИИ без доказательства из пунктов 1 и 2 не удалять. Автоматическую очистку не
делать: ссылки живут в тексте и JSON, и сканер по `FileField` даст ложные
«сироты».

## Почему 2 legacy-вложения до сих пор в публичном media

До `dacb043` (2026-09-20) вложения писались стандартным хранилищем в
`MEDIA_ROOT/customer_requests/`. `PrivateAttachmentStorage` пишет новые файлы в
приватный том и при чтении откатывается на публичную копию. Перенос старых
файлов делает `reconcile_message_attachments_private`.

**Ошибка в прежней версии команды (исправлена на этой ветке):** копия
сохранялась через `storage.save(name, ...)`. Хранилище считает файл
существующим, если он есть в legacy-дереве, поэтому Django выбирал другое имя
`<имя>_XXXXXXX.<расширение>`. Строка БД продолжала указывать на старое имя, и
чтение уходило в публичную копию. Проверка `is_file()` смотрела на новое имя и
считала перенос успешным. С `--remove-legacy` публичная копия удалялась, и
вложение строки становилось нечитаемым (единственная копия оставалась под
чужим именем). Воспроизведено синтетическим тестом на старом коде: вывод
«скопировано: 1; удалено legacy-копий: 1», а открыть вложение строки нельзя.

Также строки со статусом доставки «неизвестно» (UNCERTAIN) намеренно не
очищаются, поэтому старые вложения таких сообщений не удаляются сами.

**Исправленная команда:**

```bash
docker compose exec -T web python manage.py reconcile_message_attachments_private
docker compose exec -T web python manage.py reconcile_message_attachments_private --apply
docker compose exec -T web python manage.py reconcile_message_attachments_private --apply --remove-legacy
```

- без флагов: только отчет (публичные, приватные, совпадающие, конфликты,
  отсутствующие, вероятные дубли прошлых запусков); имена файлов не выводятся;
- `--apply`: копия под ТЕМ ЖЕ именем во временный файл, `fsync`, публикация
  через `link` без перезаписи, сверка SHA-256; БД не меняется;
- `--remove-legacy` (только вместе с `--apply`): удаляет публичную копию
  только при побайтовом совпадении с приватной;
- приватный файл с другим содержимым считается конфликтом: ничего не
  перезаписывается и не удаляется, команда завершается ошибкой;
- дубли прошлых запусков только считаются, не удаляются.

## Публичная доступность (код и конфигурация)

### Как отдается `/media/`

- Django отдает `MEDIA_URL` только при `DEBUG=True` (`config/urls.py`). В
  production `/media/` до Django не доходит.
- `proxy` (Caddy) монтирует том `media` как `/srv/media:ro`. Том
  `private_media` в `proxy` не монтируется.
- Сайт внутренней системы (`{$CADDY_SITE_ADDRESS}`, в production
  `185-250-44-206.sslip.io`) содержит `handle_path /media/*` с `root /srv/media`
  и `file_server` **без авторизации**. `browse` не включен: списка каталогов нет.
- `pro-brp.ru` и preview-хост отправляют все в `catalog-web`; у
  `catalog-web` `MEDIA_URL` пуст, а `/media/` не маршрутизируется в том.

### Что получает анонимный запрос

Шаблон пути: `https://<внутренний хост>/media/customer_requests/<очищенное
исходное имя файла>`. Имя не случайное: это исходное имя загруженного файла
после очистки символов (например, стандартное имя снимка экрана с датой и
временем), поэтому его можно угадать. При совпадении имен Django добавляет
`_` и 7 случайных символов.

- `docker/caddy/Caddyfile` и `deploy/caddy/Caddyfile.production` в репозитории
  уже содержат правило `@private_customer_media path /media/customer_requests/*`
  с `respond 404` (добавлено в `dacb043`).
- Production **не использует файл из репозитория**: `proxy` монтирует
  `/etc/denstock/caddy/Caddyfile`. Его байтовая копия на 2026-09-17
  (`deploy/caddy/Caddyfile.production.pre-max`) правила не содержит. Правило
  появилось в репозитории на три дня позже MAX edge-install, а `edge-install`
  ставит только маршрут MAX. Вывод по конфигурации: анонимный доступ к
  `/media/customer_requests/*` **вероятен**. Живую проверку делает ведущий
  инженер. Об этом же говорит падающий тест
  `test_max_edge_route::test_only_the_public_catalog_block_changes`: репозиторий
  отличается от живой копии строками правила.
- Аварийная станция (`docker/caddy/Caddyfile.emergency`) раздавала `/media/*`
  из восстановленного публичного media без такого правила; на этой ветке
  правило добавлено. Хост станции по умолчанию привязан к `127.0.0.1`, у
  primary может быть адрес в локальной сети.
- Ссылок на эти файлы нет: `PrivateAttachmentStorage.url()` бросает ошибку,
  шаблоны не строят URL вложений, `robots.txt` и sitemap есть только у
  публичного каталога и содержат карточки товаров.

### Минимальное исправление и что требует решения владельца

На ветке (без production):

1. `docker/caddy/Caddyfile.emergency`: то же правило `respond 404`.
2. Исправленная команда переноса с тестами
   (`tests/test_reconcile_private_attachments.py`).
3. Тесты конфигурации (`tests/test_public_media_exposure.py`): каждый сайт,
   который раздает `/media/*`, закрывает `customer_requests/`, без `browse`;
   `proxy` не видит `private_media`; Django не отдает `/media/` вне DEBUG.

Требует решения владельца (порядок):

1. **Edge.** Добавить в блок внутреннего сайта
   `/etc/denstock/caddy/Caddyfile` перед `handle_path /media/*`:

   ```
   @private_customer_media path /media/customer_requests/*
   handle @private_customer_media {
       respond 404
   }
   ```

   Запись на месте (тот же inode, single-file bind mount), `caddy validate`
   в контейнере `proxy`, затем `caddy reload`. Копия старого файла в `/root/`.
   После этого проверить анонимно: обычный путь, `//` вместо `/`,
   `/./`, `%5F` вместо `_` и другой регистр должны давать 404, а фото
   товаров по-прежнему 200.
2. **Перенос.** Отчет команды без флагов; затем `--apply`; затем свежий
   подписанный backup и `verify_backup`; только после этого
   `--apply --remove-legacy`. Правило в Caddy закрывает доступ сразу, перенос
   убирает сами файлы из публичного тома и из `media.tar.gz` будущих копий.
3. **Старые копии.** Уже сделанные `media.tar.gz` (локальные, Yandex, Mac)
   содержат эти 2 файла. Они не публичны, но при восстановлении на аварийную
   станцию или новый сервер правило Caddy должно быть на месте до запуска
   `proxy`.
4. **Дубли.** После проверки по хэшам (раздел выше) удалить только дубли,
   совпадающие с перенесенными вложениями, с новой копией после удаления.

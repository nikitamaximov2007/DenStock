# Restore runbook: восстановление DenisStock из бэкапа

Восстановление ПЕРЕЗАПИСЫВАЕТ текущую базу и media. Это аварийная операция:
используйте её только при реальной аварии или переезде на новый сервер.
В production и на аварийной станции online web-restore отключён независимо
от feature flag: БД, публичные и приватные файлы не имеют общего атомарного
переключателя. Последовательные CLI-команды ниже также не являются
автоматически откатываемой операцией. Их разрешено применять только в
контролируемом offline-окне с остановленными `web`, `catalog-web`,
`telegram-bot`, `max-bot` и proxy, с проверенной точкой возврата и отдельным
операторским журналом. При сбое writers не запускать до сверки всех трёх
компонентов либо полного ручного возврата к pre-restore snapshot.

### Незакрытый архитектурный gate для автоматического DR

Контейнер web сейчас подключён к одному имени PostgreSQL-базы и двум отдельным
томам media. У этих трёх хранилищ нет общего атомарного переключателя. Поэтому
`pre_restore` и последовательные команды ниже не доказывают согласованность
после SIGKILL, отказа диска или ошибки `pg_restore`.

Для безопасного автоматического восстановления нужен отдельный операторский
инструмент и независимый от восстанавливаемой БД durable journal:

1. Заблокировать все writers и трафик, доказать остановку процессов, затем
   проверить подпись и содержимое всех трёх компонентов и свободное место.
2. Создать и проверить точку возврата; восстанавливать БД в **новую** базу,
   media и private_media в **новые** каталоги на соответствующих томах.
3. Проверить миграции, содержимое, связи БД с файлами и health в изолированном
   режиме. Записать в journal имена staging и old слотов, контрольные суммы и
   стадию; синхронизировать journal на диск до первого переключения.
4. При cutover держать writers закрытыми. Обновлять маршрутизацию/конфигурацию
   только в контролируемом порядке; после SIGTERM/SIGKILL при старте читать
   journal и оставаться закрытым до проверки или полного возврата к old слотам.
5. Только после итоговой проверки всех трёх хранилищ и приложения разрешать
   запись. Сохранять old слоты и journal до подтверждённого POST-бэкапа.

Шаги 2 и 3 реализованы командой `dr_stage_restore` (ниже). Шаги 1, 4 и 5
реализованы офлайн-командами `dr_cutover_*` (раздел «Офлайн-переключение на
восстановленное поколение») и проверены на изолированном PostgreSQL 16 с
настоящими SIGKILL/SIGTERM. Они **ещё не проверены на production-сервере и
не прошли независимый аудит**: до этого не объявлять DR готовым и не
выполнять переключение на production без отдельного решения владельца.

### Staging-восстановление в новые слоты (`dr_stage_restore`)

Команда восстанавливает подписанный бэкап в НОВУЮ базу PostgreSQL и НОВЫЕ
каталоги media и private_media. Рабочие база и тома не затрагиваются,
приложение не переключается.

```bash
python manage.py dr_stage_restore <каталог бэкапа> \
  --target-db dr_stage_20261011 \
  --media-dir /srv/dr/stage-media --private-media-dir /srv/dr/stage-private \
  --journal /srv/dr/stage-20261011.journal
```

- До создания чего-либо команда отказывает, если: база не PostgreSQL; имя
  staging-базы совпадает с рабочей или системной; каталоги или журнал уже
  существуют; каталоги пересекаются с MEDIA_ROOT, PRIVATE_MEDIA_ROOT,
  BACKUP_ROOT, каталогом бэкапа или друг с другом; manifest не проходит
  строгую проверку; подпись Ed25519 не проверяется (обязательна в любом
  режиме); контрольная сумма любого файла не совпадает.
- Бэкап без private_media (production-копии до исправления) не считается
  полным DR-набором. Отдельно снятый архив private_media передаётся явно:
  `--private-media-archive <tar.gz> --private-media-files N
  --private-media-bytes B --private-media-tree <sha256>`; содержимое
  архива обязано совпасть с этим инвентарём.
- Журнал: по одной JSON-строке на шаг, каждая запись сбрасывается на диск
  (fsync файла и каталога) до следующего действия. Намерение пишется до
  действия, факт после него, поэтому после SIGKILL видно, что было создано.
- Проверка staging: применённые миграции и отпечаток бизнес-данных
  staging-базы обязаны совпасть с подписанным manifest; дерево media обязано
  совпасть с `media_tree_sha256`; каждая ссылка FileField из staging-базы
  ищется в staging-каталогах. Итог `staged` или `staged_needs_review`
  (есть ссылки на отсутствующие файлы, первые 20 записаны в журнал).
- Код должен быть той же версии миграций, что и бэкап: иначе отпечаток
  данных не вычисляется и staging завершается ошибкой.
- В дампе production есть права для роли `denstock_public` (каталог
  публичной витрины). На чистом сервере PostgreSQL роль нужно создать до
  восстановления (`CREATE ROLE denstock_public NOLOGIN`), иначе pg_restore
  завершится ошибкой. Пароль и LOGIN роли выдаются отдельно при запуске
  витрины, не для проверки.
- Архив private_media, снятый с тома Docker целиком (`tar -C <volume> _data`),
  содержит префикс `_data/`. Команда принимает только архив с корнем `.`:
  перепакуйте его без изменения содержимого и убедитесь, что инвентарь
  (файлы, байты, хеш дерева) совпал, до запуска staging.

Проверка 2026-10-11: реальный бэкап `2026-10-11_03-00-12` вместе с
отдельно снятыми private_media (16 файлов, снимок на ~17,5 часа позже
базы) восстановлен на изолированном PostgreSQL 16 с итогом `staged`.
Эта пара не является атомарным снимком: файлы, созданные или удалённые
между снимками, проверяются отдельно (в той проверке таких не было).

Удаление staging-слотов (только того, что журнал отмечает как созданное
этой командой; базу, которую команда не создала, она не удаляет):

```bash
python manage.py dr_stage_discard /srv/dr/stage-20261011.journal --yes
```

### Офлайн-переключение на восстановленное поколение (`dr_cutover_*`)

Переключает приложение с рабочего поколения (база + media + private_media)
на проверенный staging. Только из командной строки: ни одна страница и ни
один HTTP-запрос не могут запустить эти команды.

Состояния (журнал `<журнал staging>.cutover`, рядом с журналом staging):

```
SOURCE_VERIFIED -> STAGED                        dr_stage_restore
-> VALIDATED -> WRITERS_QUIESCED -> CUTOVER_PREPARED    dr_cutover_prepare
-> CUTOVER -> POST_CUTOVER_VERIFIED                     dr_cutover_execute
-> COMMITTED                                            dr_cutover_commit
ROLLED_BACK, RECOVERY_REQUIRED                          dr_cutover_recover
```

Что атомарно и что нет:

- Переключение базы атомарно: одна транзакция PostgreSQL из двух
  `ALTER DATABASE ... RENAME` (рабочая база получает имя `<имя>_dro_<id>`,
  staging-база получает рабочее имя). Проверено на PostgreSQL 16: либо обе
  смены имени применились, либо ни одна.
- Каждое файловое хранилище переключается двумя `rename` на одной файловой
  системе: рабочий каталог становится `<каталог>.dr-old-<id>`, staging
  становится рабочим. Между ними рабочего пути нет, и это видно всем.
- **Общей атомарности базы и двух файловых хранилищ нет.** Гарантия другая:
  после любого прерывания приложение не может молча запуститься с базой и
  файлами разных поколений.

Как это обеспечено:

1. Метка поколения. Перед первым переключением обе базы получают метку в
   комментарии PostgreSQL (`COMMENT ON DATABASE`): номер переключения, роль
   (новое или старое поколение), состояние и inode каталогов media и
   private_media нового поколения. Комментарий переезжает вместе с
   переименованием базы, меняется в той же транзакции и не попадает в
   `pg_dump` (проверено), поэтому не утекает в бэкапы.
2. Защита при каждом подключении. Каждый процесс (web, catalog-web,
   telegram-bot, max-bot, `migrate`, shell) при каждом новом подключении к
   PostgreSQL читает метку своей базы. Если переключение не завершено, если
   это старое или откатанное поколение, или если inode MEDIA_ROOT и
   PRIVATE_MEDIA_ROOT не совпадает с записанным для поколения, соединение
   закрывается и возникает ошибка `GenerationRefused`. WSGI-процесс в этом
   случае не стартует; `manage.py check --database default` выдаёт
   `operations.E010`. Каталог публичной витрины файлов не имеет и проверяет
   только метку базы. Обслуживание разрешено только в состояниях
   `verified` и `committed` нового поколения. База без метки работает как
   обычно, поэтому разработка и тесты не затронуты; SQLite не проверяется.
3. Журнал. Каждая запись пишется одной строкой и сбрасывается на диск
   (на macOS через `F_FULLFSYNC`) до действия, которое она объявляет.
   Оборванная последняя строка (отключение питания) игнорируется и
   запечатывается записью `torn_tail_sealed`; любой другой мусор в журнале
   останавливает автоматическое восстановление.
4. Восстановление по факту. `dr_cutover_recover` перечитывает журнал и
   проверяет реальность: какая база (по oid) под каким именем и какой
   каталог (по inode) по какому пути. Каждое хранилище должно быть ровно в
   состоянии «старое», «половина» (только каталоги: после первого `rename`)
   или «новое». Иначе журнал получает RECOVERY_REQUIRED, и ничего не
   трогается.
5. Одна операция за раз: `flock` на файл блокировки (по умолчанию
   `<BACKUP_ROOT>/.dr-operation.lock`, настройка `DENSTOCK_DR_LOCK_PATH`;
   внутри pid и хост держателя) и advisory-блокировка в PostgreSQL на весь
   кластер. Обе снимаются ядром или сервером при гибели процесса, поэтому
   SIGKILL не оставляет «вечной» блокировки (поэтому выбран `flock`, а не
   файл через `O_EXCL`, который после SIGKILL пришлось бы удалять вручную).
   Блокировку держат `dr_stage_restore`, `dr_stage_discard` и все
   `dr_cutover_*`, кроме `dr_cutover_status`.

Процедура оператора:

1. Staging: `dr_stage_restore` с итогом `staged`. Каталоги staging должны
   лежать на тех же файловых системах, что рабочие MEDIA_ROOT и
   PRIVATE_MEDIA_ROOT, рядом с ними.
2. Включить режим только для чтения:
   `production_maintenance --enable --confirm PRODUCTION-ТОЛЬКО-ЧТЕНИЕ`.
3. Остановить web, catalog-web, telegram-bot, max-bot и proxy.
4. Подготовка (ничего не переключает):

   ```bash
   python manage.py dr_cutover_prepare /srv/dr/stage-20261011.journal --writers-stopped
   ```

   Команда повторно проверяет подпись manifest и staging (миграции, все
   миграции кода применены, отпечаток бизнес-данных, деревья media и
   private_media, ссылки FileField), рабочую базу в состоянии
   `maintenance`, отсутствие других сессий в `pg_stat_activity` к рабочей и
   staging-базе, одну файловую систему у рабочего и staging-каталога, что
   рабочий каталог не точка монтирования. Любой отказ ничего не оставляет:
   исправьте причину и повторите. После успеха обе базы помечены, и
   приложение с рабочей базой уже не стартует до execute или recover.
5. Переключение и проверка нового поколения:

   ```bash
   python manage.py dr_cutover_execute /srv/dr/stage-20261011.journal --writers-stopped
   ```

   При любой ошибке переключения или проверки старое поколение
   возвращается автоматически (ROLLED_BACK).
6. `dr_cutover_status <журнал>` должен сказать, что запуск безопасен.
   Запустить web и проверить приложение (запись ещё закрыта).
7. POST-бэкап нового поколения: `backup_all`.
8. Фиксация (старое поколение сохраняется, не удаляется):

   ```bash
   python manage.py dr_cutover_commit /srv/dr/stage-20261011.journal \
     --post-backup backups/<run_id> --confirm ЗАФИКСИРОВАТЬ-DR
   ```

   POST-бэкап обязан быть подписан, не совпадать с исходным и описывать
   ровно проверенное поколение (отпечаток данных, database_identity,
   деревья media и private_media).
9. Только после COMMITTED: `production_maintenance --disable --confirm
   ОПАСНО-РАЗРЕШИТЬ-ЗАПИСЬ` и запуск остальных сервисов.
10. Старое поколение (`<база>_dro_<id>`, `<каталог>.dr-old-<id>`) удалять
    вручную и только после того, как POST-бэкап проверен и выгружен
    offsite. Инструмента удаления старого поколения нет сознательно.

После сбоя (SIGKILL, перезагрузка, ошибка диска):

```bash
python manage.py dr_cutover_status /srv/dr/stage-20261011.journal
python manage.py dr_cutover_recover /srv/dr/stage-20261011.journal --writers-stopped
python manage.py dr_cutover_recover /srv/dr/stage-20261011.journal --writers-stopped --rollback
```

- Без `--rollback` recover доводит переключение вперёд, если подготовка
  завершилась и все staging-слоты на месте; новое поколение проверяется
  заново, ему не доверяют по журналу. Если подготовка прервана или
  пропал staging-слот, выполняется откат.
- Начатый откат всегда доводится как откат, даже без `--rollback`.
- RECOVERY_REQUIRED и повреждённый журнал: автоматически ничего не
  делается, приложение не стартует. Разбор вручную: по `dr_cutover_status`
  (oid баз, inode каталогов) вернуть рабочему имени старую базу и рабочим
  путям старые каталоги, затем снять метку `COMMENT ON DATABASE <имя> IS
  NULL` только со старой базы. Документировать каждое действие.
- Прерванная фиксация (COMMITTING): повторить `dr_cutover_commit`.
- `dr_stage_discard` запрещён, пока переключение не откатено.
- Повторный запуск execute, recover, commit, prepare после завершения
  ничего не меняет (проверено).

Ограничения и что не проверено:

- Production не проверялся. В docker-compose тома `media` и `private_media`
  смонтированы прямо в `/app/mediafiles` и `/app/private_media`: точку
  монтирования переименовать нельзя, команда откажет. Переключение нужно
  запускать в отдельном контейнере, где смонтированы родительские каталоги
  томов (например `/var/lib/docker/volumes/<проект>_media`), а
  `DENSTOCK_MEDIA_ROOT` и `PRIVATE_MEDIA_ROOT` указывают на их `_data`, и
  staging-каталоги лежат там же. Такой запуск не отлажен и требует
  отдельной проверки, как и то, что inode каталога `_data` внутри
  контейнеров совпадает с inode на хосте.
- Метка проверяется при каждом новом подключении к PostgreSQL: это один
  дополнительный лёгкий запрос к `pg_database` на подключение.
- Проверка «writers остановлены» по `pg_stat_activity` видит только
  открытые сессии. Процесс без открытого соединения она не увидит; его
  остановит защита при подключении (метка), а переименование базы с
  чужим подключением PostgreSQL отклоняет.
- fsync: на macOS используется `F_FULLFSYNC`, на Linux `fsync` файла и
  каталога. Отключение питания не моделировалось; проверены только
  SIGKILL/SIGTERM процесса и обрыв последней строки журнала.
- Полный диск: staging в настоящий заполненный том (образ HFS+ на 16 МБ,
  macOS) проверен вручную разовым прогоном 2026-10-12: `failed` на
  `restoring_media`, рабочее поколение не тронуто, `dr_stage_discard`
  убрал базу и каталог. Во время переключения полный диск проверен только
  внедрённой ошибкой `ENOSPC` (автоматический откат). Отказ записи самого
  журнала на полном диске не моделировался. По устройству: если не
  записалось намерение, шаг не выполняется; если не записался итог
  выполненного шага, `dr_cutover_recover` определяет его по факту.
- Удаление старого поколения и повторный prepare после отката по тому же
  staging не реализованы: после отката удалите staging (`dr_stage_discard`)
  и создайте новый.

Точки сбоя для тестов: `DENSTOCK_DR_FAULT=<точка>` и
`DENSTOCK_DR_FAULT_ACTION=SIGKILL|SIGTERM|ENOSPC|PAUSE` действуют только в
режиме разработки с DEBUG и в тестах; в production, витрине и аварийной
станции переменная игнорируется.

## 0. Перед любым восстановлением

1. Создайте бэкап текущего состояния (UI «Экспорт бэкапа» или
   `docker compose exec web python manage.py backup_all`).
2. Проверьте целостность бэкапа, который собираетесь восстановить:

```bash
docker compose exec web python manage.py verify_backup <run_id>
```

Команда read-only: печатает отчёт (manifest, файлы, движок, свежесть) и
падает с ошибкой, если бэкап непригоден.

## 1. Offline CLI (только под управлением DR-оператора)

```bash
docker compose exec web python manage.py restore_db   backups/<run_id>/db.dump --yes
docker compose exec web python manage.py restore_media backups/<run_id>/media.tar.gz --yes
docker compose exec web python manage.py restore_private_media <run_id> --yes
docker compose exec web python manage.py migrate
docker compose exec web python manage.py ops_check
```

`restore_private_media` заменяет содержимое приватного тома целиком и откатывает
замену при ошибке. Старая копия без private_media **не является полным DR-набором**:
простое пропускание шага оставит несовместимую смесь. Использовать её можно
только как отдельно согласованное частичное восстановление с оценкой потери
вложений. Подробности: private-media-backup.md.

Подробности и сценарий «новый VPS с нуля»: production-deploy-runbook.md.

## 2. Исторический веб-restore (Layer 30, production заблокирован)

В production и `emergency-local` код теперь отказывает до любых операций
восстановления. Наличие allowlist и `DENSTOCK_ENABLE_WEB_RESTORE=true` не
снимает этот запрет. Ниже сохранено описание старого интерфейса для истории;
включать его для production больше нельзя. Доступный в тестовом окружении
workflow не является заменой offline DR-процедуре.

### Кому доступен

Только владельцу-администратору из allowlist и только при включённом флаге.
Все четыре условия одновременно:

1. `DENSTOCK_ENABLE_WEB_RESTORE=true` в `.env` (по умолчанию false);
2. пользователь аутентифицирован;
3. пользователь superuser или роль «Администратор»;
4. email пользователя входит в `DENSTOCK_RESTORE_ALLOWED_EMAILS` (по
   умолчанию nikita.maximov2007@gmail.com) ИЛИ username входит в
   `DENSTOCK_RESTORE_ALLOWED_USERNAMES`.

Обычные администраторы и все остальные роли restore-блок НЕ видят, а прямые
запросы на restore-URL получают 403. Загрузки внешних файлов бэкапов нет:
восстановление только из существующих локальных бэкапов DenisStock.

### Production-доступ

Исторический feature flag и allowlist **не разблокируют** этот путь в
production или emergency-local. Не меняйте конфигурацию и не перезапускайте
web ради веб-восстановления.

### Как выполняется

1. «Бэкапы» -> блок «Аварийное восстановление» -> «Проверить бэкап» у нужной
   строки (видны дата, тип, размер, наличие manifest/БД/media, метка «старый»).
2. Экран проверки: manifest, файлы, движок, контрольные суммы (если есть в
   manifest), совместимость версии, свежесть. Ошибки блокируют восстановление.
3. Подтверждение: ввести слово ПОДТВЕРЖДАЮ (заглавными) и отметить checkbox
   «Я понимаю, что текущие данные будут перезаписаны». POST + CSRF; GET
   никогда ничего не запускает.
4. Система создаёт pre-restore бэкап текущей базы и media (тип pre_restore).
   Если он не создался, восстановление НЕ выполняется.
5. Затем: восстановление БД (pg_restore, тот же путь, что CLI), восстановление
   media, `migrate`. Соединения Django закрываются перед restore; обычная
   транзакция Django не используется (restore идёт внешними инструментами).
6. Страница результата: статус, журнал шагов, рекомендации (войти заново,
   проверить Главную/Остатки/Движения/Статистику, создать новый бэкап).

### Журнал

- Таблица «Журнал восстановлений» в разделе «Бэкапы» (кто, какой бэкап,
  какой pre-restore, статус, ошибка, время): модель RestoreJob.
- Файл `backups/restore.log`: дублирующий след, переживает перезапись базы.

### Откат, если восстановили не то

Pre-restore бэкап хранит состояние ДО восстановления. Его run_id виден в
журнале восстановлений и в restore.log. Возврат в production возможен только
через контролируемую офлайн-процедуру, а не через веб-restore.

### Если восстановление упало

- Ошибка ДО шага restore (проверка, pre-restore бэкап): текущая база не
  тронута, ничего делать не надо.
- Ошибка ВО ВРЕМЯ restore: база может быть в неполном состоянии. Немедленно
  восстановите pre-restore бэкап по пути A (CLI). Его run_id показан на
  странице ошибки и в `backups/restore.log`.

## 3. Совместимость версий PostgreSQL (transaction_timeout)

Симптом из drill 2026-07-05: restore падал с
`unrecognized configuration parameter "transaction_timeout"`, хотя данные
восстанавливались. Причина: дамп сделан клиентом pg_dump 17, а сервер
PostgreSQL 16 не знает параметр `transaction_timeout` (появился в 17).

Дополнительный симптом (hotfix 2): после пина клиента 16 старый архив,
созданный pg_dump 17, перестал открываться вовсе:
`pg_restore: error: unsupported version (1.16) in file header`. Причина:
custom-архив pg_dump 17 имеет формат 1.16, а pg_restore 16 читает только
форматы до 1.15. То есть старые архивы 17 может прочитать только pg_restore 17.

Исправлено (hotfix Layer 30 + hotfix 2):

- **Новые дампы чистые:** web-образ ставит `postgresql-client-16` из PGDG
  (та же major-версия, что сервер `postgres:16`); `backup_all`/`backup_db`
  вызывают явный `/usr/lib/postgresql/16/bin/pg_dump`. Такие дампы не
  содержат `SET transaction_timeout` и читаются pg_restore 16.
- **Старые архивы pg_dump 17 восстанавливаются через fallback:** в образе
  стоит и `postgresql-client-17`. `restore_db` сначала запускает
  `/usr/lib/postgresql/16/bin/pg_restore`; если stderr содержит ровно
  «unsupported version (1.16) in file header», повторяет восстановление
  клиентом `/usr/lib/postgresql/17/bin/pg_restore` и пишет предупреждение.
- **transaction_timeout остаётся честным предупреждением:** если
  единственная ошибка restore (в т.ч. после fallback) - пропущенный
  `SET transaction_timeout`, restore завершается успешно с предупреждением.
  ЛЮБАЯ другая ошибка pg_restore фатальна: это не «ignore all errors».
- **verify_backup предупреждает заранее:** определяет формат архива по
  заголовку (PGDMP + версия формата; 1.16 = нужен fallback pg_restore 17)
  и наличие `SET transaction_timeout` в дампе. Read-only.
- **ops_check показывает фактические пути и версии** pg_dump/pg_restore
  (включая fallback-клиент 17), а не просто «доступны».

После обновления пересоберите образ: `docker compose build web`.

## 4. Известные ограничения

- Веб-restore выполняется синхронно в запросе: для маленькой базы DenisStock
  это секунды; страницу не закрывать до результата.
- Загрузка внешнего файла бэкапа через браузер не реализована (сознательно):
  внешний бэкап сначала кладётся в `backups/<run_id>/` на сервере (scp/rclone),
  затем восстанавливается.
- Несовпадение версий PostgreSQL client/server: см. план 37 и инцидент
  2026-07-02 (transaction_timeout).

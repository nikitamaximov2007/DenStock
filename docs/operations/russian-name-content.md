# Русские названия деталей: что нужно от оператора

Поиск по русскому названию реализован и проверен. Находится только то, что
оператор подтвердил руками, поэтому пока подтверждённых названий нет, искать
по-русски нечего: код работает, содержания нет.

## Где живёт название

| Что | Где |
| --- | --- |
| Русское название | «Таможенные данные» детали, поле «Таможенное название (RU)» |
| Подтверждение | там же, галочка «Русское название подтверждено» |
| Поисковая форма | считается сама при сохранении, руками не заполняется |

Второго места для русского названия в системе нет и заводить его не нужно.
Автоперевод, пока он не подтверждён, не ищется и покупателю не показывается.

Поиск по-русски у покупателя не работает именно поэтому.

Отдельно: у 23 публичных карточек русский текст записан в само название
детали (например «Двигатель Rotax 900 ACE»). Это ручные карточки, их название
и так видно покупателю, но канонический русский поиск на них не
распространяется - им тоже нужно подтверждённое таможенное название.

## Очередь на перевод

```
python manage.py public_catalog_coverage_report --russian-backlog /tmp/russian-backlog.csv
```

Только чтение. В файле: `part_id`, артикул, производитель, английское
название, доступный остаток и признак наличия. Сначала идёт то, что лежит на
складе, по убыванию остатка: покупателю нужно найти по-русски именно то, что
можно купить сегодня.

**Приоритет: 825 позиций в наличии.** Из них 748 BRP, 4 Polaris, 73 ручные
карточки. Остальные 125 160 публичных позиций это каталог аналогов без
остатка; их можно переводить постепенно.

## Как проверить, что название заработало

1. Открыть деталь, «Таможенные данные», вписать русское название, поставить
   «Русское название подтверждено», сохранить.
2. В поиске DenisStock ввести название строчными буквами. Деталь обязана
   найтись сразу же, отдельного пересчёта или переиндексации нет.
3. На публичном сайте название встанет в заголовок карточки, английское
   останется вторым.

## Требование к базе для опечаток

Опечатки в русских словах («проклатка» вместо «прокладка») работают только
если CTYPE базы считает кириллицу буквами. У стандартного образа
`postgres:16` это так (`en_US.utf8`). В базе, созданной с локалью `C`,
расширение `pg_trgm` не выделяет из кириллицы ни одной триграммы, и тир
опечаток молча ничего не находит; остальной русский поиск (точное совпадение,
начало, подстрока, все слова) работает в любой локали.

Проверка:

```
python manage.py ops_check
```

Строка `Опечатки в русском поиске`: `OK` - всё в порядке; `WARN` - локаль
базы не даёт триграмм для кириллицы. Починить это можно только пересозданием
кластера с UTF-8-локалью, приложение обойти ограничение не может.

Кандидат Codex `codex/private-media-backup-wrapper-safe` (`3dba178`) правит
`backup_offsite.sh`, который на production не используется, и не удаляет
удалённые копии вовсе: при росте копий до ~92 МБ бакет заполнится примерно
за неделю, и после этого каждая ночная выгрузка будет падать. Поэтому за
основу взята обёртка с доказанной ротацией.

## 3. Гарантии и их пределы

- Новая копия считается успешной, только если удалённые байты совпали с
  локальной копией, которая заново прошла проверку SHA-256 и Ed25519.
- Удаляются только поколения старше «предыдущего доказанного», по точному
  пути, и только пока после загрузки не хватает места на ещё одну копию.
- Повреждённая (прерванная) копия новее предыдущей доказанной удаляется,
  только если её локальный двойник проверяется, а удалённые байты другие.
  Копия без локального двойника не удаляется: ротация останавливается со
  статусом `degraded`.
- Атомарного снимка файлов нет. Гарантия: архив равен дереву, которое не
  менялось за время упаковки, иначе бэкап не создаётся (RPO при постоянной
  записи в media растёт до следующего успешного запуска).
- Бакет версионированный: очистка скрытых версий выполняется только по пути
  удаляемого поколения.

## 4. Проверка S3: что сделано и что нет

Проверено на синтетическом стенде `tests/offsite_harness.py` (поддельный
`rclone` с семантикой версионированного S3): полная загрузка, обрыв, ENOSPC,
SIGTERM посреди загрузки, частичный объект, неполный multipart, задержка
учёта места, список без свежего поколения, список без старого поколения,
сбой `cleanup-hidden`, повторный ID, параллельный запуск, подмена локальной
копии после проверки, случайные серии сбоев (инвариант: самое новое
восстанавливаемое поколение не удаляется до подтверждения более нового).

НЕ проверено (блокер для установки обёртки, не для выпуска приложения):
настоящий протокол S3. На Mac нет `rclone`, MinIO и запущенного Docker;
скачивание ПО и тестовый бакет в Yandex требуют разрешения владельца.
Нужно отдельно подтвердить на настоящем S3: `rclone check --download`,
`rclone check` по ETag для файлов меньше 200 МиБ, `backend cleanup-hidden`
с путём поколения, `size --s3-versions`.

## 5. Квота, хранение, стоимость

Факты на 2026-10-12: бакет 418.5 МБ, 9 поколений по ~46.5 МБ, мягкий лимит
838 860 800 байт (800 МиБ); жёсткая квота бакета ~921.6 МБ известна только
из комментария в обёртке, на production не подтверждена.

После выпуска поколение ~92.4 МБ. Новая обёртка держит запас на одну копию:
после ротации остаётся до 8 поколений (~739 МБ), пик во время загрузки ~831
МБ. В день выпуска (PRE и POST подряд) Yandex ещё учитывает только что
удалённое (до ~20 минут), и вторая загрузка может быть отклонена квотой:
ничего не удаляется, частичная копия снимается следующей ночью. Рекомендация
владельцу: мягкий лимит 734 003 200 (700 МиБ), тогда 7 поколений и пик ~739 МБ.

Трафик: каждую ночь скачиваются новая и предыдущая копии, ~185 МБ, около
5.5 ГБ в месяц, плюс десятки GET/LIST запросов. Цены Yandex Object Storage
на исходящий трафик и запросы нужно сверить с актуальным прайсом.

Локально: `--keep-last 14` при ~92.4 МБ это ~1.3 ГБ; свободно 8.7 ГБ.

## 6. Выпуск (после аудита, только с разрешения владельца)

Шаг 1, приложение (разрешение на деплой):
1. PRE-бэкап штатным `systemctl start denstock-backup.service`, проверка:
   `verify_backup`, Ed25519, `pg_restore -f /dev/null`, `rclone check
   --download` (как в выпуске 2026-10-12).
2. Тег отката: `docker tag denstock-web:latest denstock-web:rollback-f7b8086`.
3. `git fetch`, `git checkout --detach <SHA>`, `DENSTOCK_APP_COMMIT` в `.env`.
4. `docker compose build web telegram-bot max-bot`, затем
   `docker compose up -d --no-deps --wait web telegram-bot max-bot`
   (боты: изменение удаления вложений в `attachments.py`). `catalog-web`,
   `db`, `proxy` не трогаются.
5. POST-бэкап: в каталоге есть `private_media.tar.gz`, manifest подписан,
   `private_media_status=included`, 16 файлов, чтение назад без различий.

Шаг 2, обёртка (отдельное разрешение, меняет инфраструктуру бэкапов):
1. Сохранить копию `/usr/local/sbin/denstock-backup-capped`.
2. Установить `scripts/operations/denstock-backup-capped-safe.sh` как
   `/usr/local/sbin/denstock-backup-capped-safe` (root, 0755).
3. В `denstock-backup.service` заменить `ExecStart` (drop-in), `daemon-reload`.
4. Ручной запуск, статус `ok`, в логе чтение назад обоих поколений.
5. Мягкий лимит в `.env.backup`: решение владельца.

# BRP-каталог: импорт дилерского прайса и учёт наличия

Layer 31. Файл-источник: дилерский прайс BRP (Excel, ~127 тысяч строк,
пример: BRP DEALER PRICE 2.10.2026.xlsx). Файл в Git НЕ коммитится.

## 1. Справочник, а не остатки

BRP-прайс: это МАСТЕР-КАТАЛОГ (справочник всех деталей BRP), а не то, что
лежит у Дениса на складе. Поэтому:

- импорт создаёт только строки справочника BrpCatalogPart;
- импорт НЕ создаёт остатков, движений, поступлений и складских карточек;
- на складе появляются только детали, которые физически есть: пользователь
  находит позицию в BRP-каталоге, добавляет её в склад и учитывает наличие
  документом (см. раздел 6).

Если бы все 127k строк стали остатками, склад показывал бы наличие деталей,
которых нет, и все отчёты/статистика врали бы.

## 2. Как запустить импорт

Проверка без записи (обязательный первый шаг):

```bash
docker compose exec web python manage.py import_brp_catalog "/app/brp.xlsx" --dry-run
```

Боевой импорт (только после бэкапа):

```bash
docker compose exec web python manage.py backup_all
docker compose exec web python manage.py import_brp_catalog "/app/brp.xlsx" --commit
```

Файл кладётся на сервер вручную (scp) и не хранится в репозитории.
Импорт идемпотентен: повторный запуск того же файла ничего не меняет
(created=0, updated=0); новый прайс обновит изменившиеся строки по Material_No.

Итог команды: строк просмотрено/данных, создано, обновлено, пропущено,
дубликаты (и сколько решено по ненулевой цене), нулевых цен исправлено,
уникальные номера, счётчики статусов, строки с ценами и заменами.

### Нулевые wholesale не затирают известную цену

Для каждого Material_No импортёр выбирает цену отдельно от metadata строки.
Порядок источников строго такой:

1. ненулевая wholesale из приоритетной строки текущего Excel;
2. ненулевая wholesale из другой строки того же Excel по детерминированному
   правилу дубликатов;
3. прежняя ненулевая wholesale текущего каталога;
4. если цены нет ни в одном источнике, в каталоге хранится отсутствие цены,
   а не экономически значимые `0 ₽`.

Статус, описание и замены всегда остаются из нового Excel. Например, новый
статус VIN с нулевой supplier wholesale сохраняет предыдущую raw wholesale,
а надбавка VIN 25 USD применяется далее только централизованным pricing
helper. UCP продолжает нормализоваться в USE.

Отрицательная или нечисловая wholesale блокирует применение до разбора с
поставщиком. Разные ненулевые значения в дубликатах видны в сводке; для
совместимости действует существующий deterministic tie-break: строка с лучшим
рангом, затем первая в файле.

Для исправления уже применённого прайса с известной прежней официальной
копией используется отдельная аудируемая correction-партия. Она не
переписывает исходный batch и меняет только raw wholesale:

```bash
# 1. Посмотреть план (ничего не пишет):
docker compose exec web python manage.py correct_brp_zero_wholesale \
  --source-batch 2 --previous-file /path/to/previous-brp.xlsx

# 2. После свежего verified backup записать correction:
docker compose exec web python manage.py backup_all
docker compose exec web python manage.py correct_brp_zero_wholesale \
  --source-batch 2 --previous-file /path/to/previous-brp.xlsx --commit \
  --confirm "CORRECT BRP ZERO WHOLESALE"
```

Коррекция пересчитывает только текущие рекомендованные цены связанных
складских карточек через штатный сервис. Складские количества, лоты,
резервы, движения, продажи, ремонты и исторические снимки цен не меняются.

Незавершённые ЧЕРНОВИКИ пересчёта ячеек подхватят исправленные цены сами
при открытии страницы сессии: пересканировать ячейку не нужно. Проведённые
документы и их снимки цен не переписываются.

### Починка цен документа из пересчёта (hotfix 33.1)

До 33.1 конвертация пересчёта писала во все строки документа один
глобальный ноль вместо цен клиента (кейс POS-000003 от ячейки
S04-L03-D01-C01). Команда переносит цены строк пересчёта в строки уже
созданного документа; итог документа становится равен «Стоимости ячейки»:

```bash
# 1. Посмотреть, что изменится (ничего не пишет):
docker compose exec web python manage.py repair_counting_receipt_prices --session-id 3 --dry-run
# 2. Бэкап и запись:
docker compose exec web python manage.py backup_all
docker compose exec web python manage.py repair_counting_receipt_prices --session-id 3 --commit
```

Можно указать --receipt-id вместо --session-id. Команда чинит ТОЛЬКО
документы, связанные с пересчётом (обычные поступления от поставщика
отклоняет), меняет только цены строк: количества, остатки, лоты и движения
не затрагиваются.

### Пересчёт в разделе «Инвентаризация» (Layer 34)

Проведённый пересчёт ячейки - документ ПЕРВИЧНОГО ВВОДА с IC-номером в
разделе /stocktaking/, а не поступление: технические POS-документы скрыты
из списка /receipts/ (физически целы: на них ссылаются партии/лоты/
движения). Историческая миграция уже проведённых ячеек:

```bash
# 1. Отчёт без записи:
docker compose exec -T web python manage.py migrate_counting_receipts_to_stocktaking --dry-run
# 2. Бэкап и запись (присваиваются только IC-номера, склад не меняется):
docker compose exec -T web python manage.py backup_all
docker compose exec -T web python manage.py migrate_counting_receipts_to_stocktaking --commit
```

Команда идемпотентна: повторный запуск ничего не меняет. Демо-черновики
поступлений (например POS-000001/000002, если они не нужны) удаляются
ТОЛЬКО явной командой по id (черновик не имеет склада, удаление безопасно;
проведённые и связанные с пересчётом документы команда отклоняет):

```bash
docker compose exec -T web python manage.py delete_draft_receipts --receipt-id 1 --dry-run
docker compose exec -T web python manage.py delete_draft_receipts --receipt-id 1 --commit
```

Приоритет поиска по номеру (hotfix 32.3.1): точное совпадение material_no
ВСЕГДА выше совпадения по замене номера; внутри группы предпочитается
ненулевая оптовая цена, затем меньший id. Кейс: у 417224458 (опт 0, USE)
замена 417224916; скан 417224916 выбирает позицию 417224916 (28.15 $ ->
4138 ₽), а не старый номер. Строки черновиков, привязанные к старому
номеру до починки, перепривязываются автоматически при открытии сессии
(количество и сканы не меняются).

Источник цены отдельно от личности (hotfix 32.3.2): строка пересчёта
остаётся привязанной к точному номеру, но если у него оптовая цена 0, цена
клиента берётся из связанной по цепочке замен позиции с оптовой ценой > 0
(кандидаты: позиции, у которых номер или замена равны отсканированному
номеру, плюс позиции, на которые ссылаются замены самой выбранной; порядок:
оптовая цена > 0, меньший id). Если цены нет ни у кого из цепочки, остаётся 0.
Правило действует
для сканов и черновиков; проведённые документы не переписываются.

## 3. Формат файла и поля

- первый лист; строка 1: заголовки; строка 2: примечания; данные со строки 3;
- колонки A..H: Material_No, Part_Desc, Last_Yr_Util, Status, РОЗНИЦА (USD),
  ОПТОВАЯ (USD), ЗАМЕНА НОМЕРА, ЗАМЕНА НОМЕРА; правее: легенда, игнорируется;
- Material_No хранится СТРОКОЙ (ведущие нули не теряются), пробелы обрезаются;
- обе колонки «ЗАМЕНА НОМЕРА» сохраняются отдельно и индексируются для поиска;
- дубликаты Material_No (hotfix 32.3): из повторяющихся строк выбирается
  лучшая по детерминированному правилу: 1) оптовая цена > 0; 2) при равенстве
  розница > 0; 3) дальше первая по порядку в файле. Если у всех строк нет
  пригодной wholesale, для существующей позиции сохраняется прежняя ненулевая
  wholesale, иначе цена остаётся неуказанной. Только Decimal, без float. Все дубликаты считаются в отчёте
  (плюс отдельный счётчик «решено по ненулевой цене»).

Статусы BRP (по легенде файла):

- OBS: снято с производства;
- USE: замена номера;
- VIN: винтажный склад, будет доставка 25$;
- LIQ: последние остатки у завода;
- UCP: alias статуса USE (замена номера).

## 4. Цены: формула, итог в целых рублях

Цены прайса в долларах. Цена клиента считается из оптовой цены BRP:

    сырая_цена_руб = оптовая_USD x курс x (1 + наценка_% / 100)
    цена_клиента_руб = сырая_цена_руб, округлённая до целого рубля
                       (ROUND_HALF_UP, без копеек; hotfix 32.1)

Текущие настройки по умолчанию: общий курс 105 ₽/$, наценка BRP 40%.
Примеры оптовой цены: 100 $ -> 14700 ₽; 7.39 $ -> 1086.33 -> 1086 ₽;
9.03 $ -> 1327.41 -> 1327 ₽; 99.99 $ -> 14698.53 -> 14699 ₽.

- округляется ТОЛЬКО итоговая цена клиента в рублях: исходные цены USD,
  курс и наценка не округляются;
- нет округления до 10/50/100: только до целого рубля;
- только Decimal, не float;
- исторические проведённые документы и старые снимки цен задним числом
  не переписываются: правило действует для новых расчётов (в интерфейсе
  копейки старых снимков просто не показываются);
- 40%: это НАЦЕНКА (в интерфейсе «Наценка»), не «маржа»;
- общий курс, наценка BRP и наценка Polaris настраиваются на странице
  «Справочники» -> «Настройки цен» (админ/руководитель);
- при добавлении детали в склад использованные курс/наценка, исходные цены
  USD, рассчитанная и итоговая цена фиксируются в связи (BrpPartLink) и при
  смене глобальных настроек задним числом НЕ меняются;
- цену можно указать вручную: исходная USD-цена и рассчитанное значение при
  этом сохраняются (price_source = manual).

После импорта с `--commit` DenisStock пересчитывает только текущую
`recommended_price` связанных карточек, использующих расчётную цену. Для уже
загруженного каталога есть отдельный безопасный просмотр:

```bash
# Только показать, какие текущие рекомендованные цены изменятся:
python manage.py recalculate_linked_part_prices

# Явно применить только текущие recommended_price:
python manage.py recalculate_linked_part_prices --apply
```

Команда не меняет снимки BrpPartLink, проведённые продажи, остатки, партии,
резервы или StockMovement. Если оптовая цена отсутствует, текущая
рекомендованная цена не затирается.

## 5. Поиск по каталогу

Раздел «BRP-каталог» в меню (группа «Каталог»). Поиск по номеру BRP, обеим
заменам номера, штрихкоду склада и описанию; фильтр по статусу. Порядок:
сначала фактический склад (с остатками и адресами), затем справочник BRP.
Основной «Поиск детали» тоже подсказывает совпадения из BRP-каталога с
пометкой «справочник, не остаток». Сканер = клавиатура: ввод номера + Enter.

Скорость на реальном объёме (126 399 строк): поиск по номеру ~3 мс, по
замене ~2 мс, по описанию ~16 мс.

## 6. Учёт наличия (первичный ввод остатков)

1. Найти позицию в «BRP-каталог».
2. «Создать карточку» (ранее подписана «Добавить в склад»): создаёт ТОЛЬКО
   карточку (название из описания BRP, номер BRP и замены как номера для
   поиска, рекомендованная цена = рассчитанная цена клиента). Остатков не
   появляется.
3. «Учесть наличие»: открывает черновик документа «Инвентаризация начальных
   остатков» (это документ поступления Layer 28 от поставщика «Стартовый
   ввод») с уже подставленной деталью: ввести количество, ячейку (адрес),
   себестоимость, комментарий.
4. «Провести поступление»: только теперь появляется остаток в выбранной
   ячейке и движение прихода. Черновик склад не меняет; проведённый документ
   read-only.

Одна деталь может лежать в нескольких адресах: остаток привязан к месту.

Права: смотреть каталог могут все роли; «Создать карточку»: администратор и
руководитель (can_manage_parts); «Учесть наличие»: роли склада
(can_manage_inventory; кладовщику нужна уже созданная карточка).

Быстрая альтернатива для целой ячейки: «Инвентаризация ячейки»
(/inventory/counting/, Layer 32). Кладовщик выбирает адрес и пикает всё
содержимое подряд; система группирует одинаковые номера, распознаёт склад,
затем BRP, а при проведении сама создаёт карточки из BRP и пишет остаток по
адресу. Скан и черновик склад не меняют. Это режим первичного ввода:
проведение ДОБАВЛЯЕТ остаток, повторно провести ту же сессию нельзя. Подробно
см. docs/user-guide/denstock-user-manual.md, раздел «Инвентаризация ячейки».

## 7. Адресное хранение

Структура Storage Address V2: Стеллаж -> Ящик -> Ячейка. Склад - одна комната
и около шести стеллажей, навигация по номеру
стеллажа. Полный адрес записывается в код места хранения:

- S01-D03-C08: стеллаж 1, третий ящик снизу, ячейка 8.

Буквы: S = стеллаж (shelving unit), D = выдвижной ящик (drawer),
C = ячейка (cell/compartment). D01 - самый нижний ящик; ячейки считаются
слева направо, ряд за рядом.

Обратная совместимость: старые адреса с зоной (A-S01-L02-D01-C01) и легаси-
буквами B/K/X остаются валидными, читаются и ищутся. Новые адреса L, зону и
буквы B/K/X не используют.
Хелпер: apps/warehouse/addresses.py (compose_address, get_or_create_location).

Рекомендации: мелочь (сальники, подшипники, крепёж, датчики): в ящики/ячейки;
среднее (ремни, комплекты прокладок, шланги, пластик): в контейнеры; крупное
(вариаторы, стартеры, генераторы, помпы): на полки. Физическое размещение -
по удобству склада, а не по виду техники: совместимость хранится в карточке
(вид/марка/модель техники), потому что одна деталь подходит нескольким.

## 8. Правила безопасности

- перед боевым импортом: свежий локальный бэкап + offsite + verify_backup;
- сначала dry-run, только потом --commit;
- импорт не трогает вручную отредактированные складские карточки и их цены
  (обновляется только справочник BrpCatalogPart);
- фактические остатки меняются только проведением документа;
- зафиксированные в истории курс/наценка не меняются при смене настроек.

# Резервная копия private_media

С этой версии каждая production-копия (`backup_all`, в том числе ежедневная
`denstock-backup-capped`) содержит приватные файлы: вложения заявок клиентов,
скриншоты ИИ-поддержки, файлы импорта каталогов. Раньше они в копию не
попадали и были невосстановимы.

## Где лежат приватные файлы

Именованный Docker volume `denstock_private_media`, смонтирован в `web`,
`telegram-bot` и `max-bot` как `/app/private_media` (`PRIVATE_MEDIA_ROOT`).
`catalog-web` и `proxy` его не видят. Боты сами добавляют и удаляют вложения,
поэтому архив снимается с проверкой согласованности (см. ниже).

## Состав копии

| Файл | Что внутри |
|---|---|
| `db.dump` | PostgreSQL 16, как раньше |
| `media.tar.gz` | публичные фото, как раньше |
| `private_media.tar.gz` | весь `PRIVATE_MEDIA_ROOT`, всегда, даже пустой |
| `manifest.json` | подписанный Ed25519 перечень и контрольные суммы |

Новые поля manifest (входят в подпись):

- `private_media_status`: `included` (архив есть, файлов может быть 0) или
  `absent` (каталога не было; в production это запрещено).
- `private_media_filename`, `private_media_sha256` (также в `sha256`).
- `private_media_tree_sha256`: хэш путей и содержимого всех файлов.
- `private_media_file_count`, `private_media_bytes`.

У старых копий этих полей нет: подписанные исторические копии остаются
действительными, но приватных файлов не содержат. Неподписанные копии нельзя
автоматически восстановить в production: удаление подписи не должно превращать
новую копию в «старую». Их происхождение нужно разбирать отдельно вне web-restore.

## Когда бэкап завершается ошибкой (и не помечается verified)

- каталога нет (том не смонтирован);
- в production отсутствует каталог публичных media;
- нет прав на каталог или на любой файл;
- внутри есть символическая ссылка или специальный файл;
- остались каталоги `.denstock-restore-*` от прерванного восстановления;
- содержимое менялось во время копирования три раза подряд (боты писали файлы).

Архив сначала пишется как `.partial` и переименовывается, только если
содержимое архива совпадает с каталогом до и после упаковки.
Публичный media archive теперь также сверяется с отпечатком дерева до и после
упаковки; копия с изменившимся во время операции фото не помечается verified.
PostgreSQL dump декодируется целиком без подключения к БД: проверка одного
оглавления не обнаруживала повреждённые сжатые блоки таблиц.
Удаление вложения Telegram/MAX сначала убирает ссылку в БД и только после
commit удаляет файл. Поэтому backup lock не может застать БД, которая ещё
ссылается на уже удалённое вложение.
При локальной ротации production повторно проверяет подпись и хэши перед тем,
как считать поколение завершённым: один поддельный флаг `verified` не может
вытеснить последнюю проверенную копию. Удалённую ротацию Yandex выполняет
отдельная production-обёртка; её политика проверяется отдельно.

## Проверка

```bash
docker compose exec web python manage.py verify_backup <run_id>
```

Проверяет подпись Ed25519 manifest, контрольные суммы, безопасность каждого
элемента архива (только обычные файлы и каталоги, без `..`, абсолютных путей,
ссылок и дубликатов), целостность gzip и совпадение содержимого с manifest.
Для старой копии печатает предупреждение «старая копия без private_media».

## Восстановление

```bash
docker compose exec web python manage.py restore_private_media <run_id> --yes
```

Содержимое `PRIVATE_MEDIA_ROOT` **заменяется** целиком (лишние файлы удаляются).
Архив распаковывается во временный каталог внутри тома, сверяется с manifest,
затем содержимое меняется местами. Любая ошибка возвращает прежние файлы.

Веб-восстановление делает то же самое первым шагом, до базы: если архив
испорчен или не хватает места, восстановление останавливается и база не
трогается. Pre-restore копия теперь тоже содержит private_media.

Если процесс был убит посреди замены, в томе останутся каталоги
`.denstock-restore-<id>-old` (прежние файлы) и `-new`. Новые бэкапы и
восстановления откажутся работать, пока оператор не разберёт их вручную:
верните содержимое `-old` на место или удалите его после проверки.

## Ограничения

- Аварийная станция разворачивает private_media из нового подписанного бэкапа
  в тот же изолированный standby slot, что БД и публичные media. При запуске
  выбранного slot контейнер использует именно его приватный каталог. Старые
  копии без private_media остаются неполными: эти вложения восстановить нельзя.
- Production failback finalizer пока проверяет БД и публичные media, но не
  сверяет фактическое приватное дерево перед открытием записи. До устранения
  этого блокера оператор должен сверить private_media с подписанным manifest
  вручную и не считать автоматический finalizer доказательством полноты.
- Web-restore не откатывает БД, публичные и приватные файлы как единое целое
  при сбое после начала восстановления. Сохраняйте pre-restore backup и
  выполняйте аварийный откат по runbook; выпуск полной DR-процедуры требует
  отдельного решения.
- Права и владелец файлов при восстановлении: владелец берётся от процесса
  `web` (UID 2001), права файлов сохраняются без setuid/записи для группы.
- Для подписанной копии нужен закреплённый ключ `DENSTOCK_MANIFEST_PUBLIC_KEY_PATH`;
  без него проверка подлинности и автоматическое восстановление завершаются ошибкой.
  Восстановление подписанной копии на машине без ключа будет отклонено.

## Размер и offsite (оценка от 2026-10-09)

Production: 16 файлов, 51,3 MB без сжатия, 45,9 MB в архиве (из них 45,6 MB
это 7 файлов `catalog-imports`). Копия растёт с 46,5 MB до ~92,4 MB.

Моделирование правил `denstock-backup-capped` (ежедневно + PRE/POST на релизах):

| Мягкий лимит | Копий в облаке | Риск отказа загрузки при задержке учёта Yandex |
|---|---|---|
| 800 MiB (сейчас) | 6–9 | есть: утро после релиза, до ~924 MB при лимите бакета 921,6 MB |
| 700 MiB | 4–6 | нет, в том числе при росте копии до 185 MB |

Yandex пишет, что учёт размера бакета обновляется до 20 минут и место после
удаления освобождается не сразу. Поэтому перед выпуском рекомендуется
`BACKUP_REMOTE_SOFT_LIMIT_BYTES=734003200` в `.env.backup` (решение владельца).
Лимит бакета 921,6 MB взят из комментария в обёртке и с сервера не проверялся.
Жёсткой гарантии объёма это не даёт: это бюджет приложения, а не провайдера.
Две полные проверенные копии помещаются с большим запасом (2 × 92,4 MB).

Локальный диск: 14 полных копий × 92,4 MB ≈ 1,3 GB при 9,4 GB свободных.

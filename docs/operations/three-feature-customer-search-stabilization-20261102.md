# Стабилизация поиска клиента после объединённого выпуска

Объединённый выпуск быстрых действий, внутренних справочных номеров и правки
номера таможенного заказа уже находится в Git-коммите
`01a0b7eb4fb79b25bc6cbc7ae87ce4da8eb1bad6`. Его история и первоначальный
план сохранены в `three-feature-release-20261029.md`. Эта процедура касается
только обнаруженного PostgreSQL-дефекта поиска клиента по имени с разным
регистром. Дополнительных миграций и изменений складской логики нет.

02.11.2026 read-only Docker image identity работающего `web` показала OCI
revision `01a0b7eb4fb79b25bc6cbc7ae87ce4da8eb1bad6` и image ID
`sha256:78f2ddb2fa66887c4d34f409a479469d97e0289f57f066564a1a70fbaa17f467`.
Позднее в этой же проверке SSH перестал завершать handshake, а оба HTTPS-сайта
не завершили TLS handshake. Причина не установлена. Пока доступность и
состояние сервисов не подтверждены повторно, любые действия выпуска блокированы.
При последующей проверке оба `/healthz/` снова ответили HTTP 200, SSH стал
доступен, image identity не изменился, а `customs_orders.0005` оказалась
применённой. Кратковременный таймаут требует отдельного наблюдения; эти
значения могут измениться и не заменяют preflight перед выпуском.
Отдельно `telegram-bot` оказался `unhealthy`: его heartbeat не обновлялся
около 3,8 суток при продолжающем работать Python-процессе. Доставка сообщений
этим не подтверждена. До выяснения и устранения причины выпуск заблокирован;
бота в рамках этого runbook не перезапускать.

## Объём

- Обновить только `web` после отдельного разрешения владельца. `catalog-web`,
  PostgreSQL, Caddy, ботов и preview не пересоздавать.
- Новых миграций нет. Ожидаемый лист `customs_orders` после уже принятого
  объединённого выпуска: `0005_customsordernumberchange`; 02.11.2026
  применение подтверждено read-only запросом, перед выпуском проверить снова.
- Отчёт о квалификации должен указать точный целевой Git SHA, image ID,
  OCI revision, source archive hash, linux/amd64 и результаты SQLite,
  PostgreSQL 16 и браузера. Один Docker-тег без identity gate недостаточен.

## До разрешения на выпуск

1. В режиме только чтения подтвердить фактический running SHA по image ID,
   OCI revision, source archive hash и файлам внутри `web`, а не по checkout
   либо `.env`. Сверить migration leaves. Если SHA уже не `01a0b7e...`,
   остановиться и пересобрать кандидата от новой базы.
2. Подтвердить устойчивое HTTPS 200 склада и публичного каталога, анонимный
   404 private media, здоровье PostgreSQL, `web`, `catalog-web`, Caddy,
   Telegram и MAX. При SSH/TLS timeout, новом OOM, росте orphan healthcheck,
   деградации памяти или нехватке диска: STOP и отдельная диагностика.
3. Проверить backup-lock, отсутствие backup/restore, миграций, сборок и
   складских операций. Согласовать тихое окно. Зафиксировать контрольные
   показатели остатков, лотов, движений, продаж, ремонтов, заявок и
   таможенных заказов, а также состояние доставки MAX/Telegram.
4. Сохранить прежний image ID, отдельные SHA-селекторы `web`/`catalog-web`,
   Compose overlays, healthcheck и защищённую копию изменяемой конфигурации.
   Сравнить `docker compose config` до и после подстановки целевого SHA:
   допустимо изменение только `web` и необходимых build args; не вызывать
   сборку либо `up` для каталога. Учитывать production-only signing и
   catalog-only overlays.
5. Создать один свежий полный подписанный PRE штатным `backup_all` под общим
   backup-lock, без capped wrapper и ротации. Проверить PostgreSQL dump,
   public media, private media, manifest, Ed25519 и SHA-256 каждого компонента.
   Зашифровать age и сохранить на Mac отдельно от прежних recovery points.
   Изолированно восстановить PostgreSQL 16 и оба media-дерева, проверить
   ссылки на файлы и количественные маркеры. При неуспехе STOP.

## Установка только после отдельного разрешения

1. Собрать `web` вне VPS из точного Git-архива целевого SHA для linux/amd64
   через `scripts/operations/release_image_identity.py build`. Проверить
   OCI revision, source archive hash, встроенный SHA и отсутствие секретов в
   labels/logs. На VPS образ не собирать: память ограничена 2 ГиБ.
2. Передать архив образа, сверить SHA-256 на Mac и VPS, выполнить `docker load`.
   Не удалять старый image ID. Проверить image identity gate и эффективную
   Compose-конфигурацию. Обновить исключительно `web` с `--no-build --no-deps`.
   Новых миграций нет; не запускать их повторно вручную.
3. Подтвердить runtime image ID, OCI revision, `/healthz/`, оба HTTPS-сайта,
   анонимный 404 private media, здоровье PostgreSQL и ботов, отсутствие новых
   OOM/orphan/zombie и приемлемые RAM/swap. Если пункт не пройден: STOP.
4. Проверить без реальных складских записей: поиск клиента по `Мих`, `мИх`,
   `Михаил П` и фрагменту телефона; выбор клиента; навигацию по четырём полям
   корзины; строгую идентификацию внутренних номеров; отдельность
   `010-090`/`01-0090`; неоднозначный ввод без автовыбора; чтение
   таможенного заказа и его истории. Сверить контрольные показатели данных.
5. Создать отдельный полный подписанный POST по той же процедуре, без ротации.
   Зашифровать age на Mac отдельно от PRE и изолированно восстановить
   PostgreSQL 16, public и private media. До успешного POST-восстановления
   статус не может быть SUCCESS.

## Остановка и возврат приложения

При критическом сбое сохранить журналы и состояние схемы. Если схема
совместима и причина в новом `web`, по отдельному решению владельца вернуть
сохранённый image ID `web` и прежний SHA-селектор, затем повторить health,
безопасность private media и контроль данных. `catalog-web` не откатывать.
Не удалять таблицу истории `customs_orders.0005` и не восстанавливать старый
PRE поверх текущей БД: после снимка могли появиться действительные операции.
Разрушительные действия требуют отдельного решения владельца.

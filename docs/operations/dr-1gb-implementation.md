# DR 1 GB: инженерный статус, лимиты и порядок ввода

**Статус: Round 2, не готов к production. Облачная публикация по умолчанию
заблокирована.** Ветка не
заменяет работающий `denstock-backup.timer` и `/usr/local/sbin/denstock-backup-capped`,
не подключает реальные Google Drive и Yandex, не ставит launchd и не удаляет
ни одной действующей копии. Миграций БД нет.

## Что именно делает конвейер

```
VPS: backup_all (как раньше, подписанный manifest, db + media + private_media)
  -> dr_encrypt (в контейнере web): age-шифрование, подписанный receipt
  -> dr_upload.py (на хосте): независимо в Yandex и в Google Drive
MacBook: dr_mac_pull.py (launchd): берёт шифротекст из обоих облаков, проверяет подпись
```

- Содержимое: дамп PostgreSQL 16, `media`, `private_media`, подписанный
  Ed25519 manifest и SHA-256 каждого файла. `private_media` обязателен для новых
  копий; production без смонтированного тома даёт ошибку, а не неполную копию.
- Шифрование: стандартный `age`, потоково, без временного открытого tar.
  На production хранится только **публичный** recipient. Приватный ключ age
  хранится офлайн, отдельно от VPS, Yandex, Google и MacBook.
- Receipt: `{version, run, backup_created_at, bytes, sha256}` шифротекста, подписан тем же ключом
  `production-1`. Mac и облачные адаптеры проверяют подпись закреплённым
  публичным ключом, а не ключом из самого облака.
- Раскладка в облаке: `<префикс>/<run>/bundle.tar.age` и `receipt.json`.
  Receipt загружается **последним**: его наличие означает завершённую загрузку.

## Лимит 1 000 000 000 байт: блокирующее ограничение

Жёсткий физический лимит на каждом облачном направлении **не доказан**.
`dr_upload.py` по умолчанию не публикует данные. Флаг
`--allow-best-effort-budget` разрешает лишь явно выбранный владельцем режим
без такой гарантии. Он не делает текущую ветку годной для выпуска по исходному
требованию. Измерение через API может запаздывать, а внешние процессы могут
писать параллельно. Блокировка процесса действует только на данном VPS.

| Назначение | Что считается | Что НЕ удаётся доказать |
|---|---|---|
| Yandex Object Storage | видимые версии (`--s3-versions`), наличие незавершённых multipart, живые объекты в префиксе | точный мгновенный физический объём при задержках провайдера, другие префиксы и внешние авторы |
| Google Drive | папка + корзина папки + весь объём аккаунта (`used + other` из `rclone about`, то есть Drive + Gmail + Photos), берётся максимум | квота Drive общая на аккаунт, лимита на папку нет; ревизии учтены только через общий объём аккаунта |
| MacBook | реальные байты файлов в каталоге (включая `.incoming-*`) | служебные блоки файловой системы APFS |

Следствия, которые нельзя скрывать:

1. У Drive нет лимита на отдельную папку. У Yandex есть `max_size` бакета,
   но документация предупреждает: обновление информации может занимать до
   20 минут, и заданный максимум иногда может быть превышен при быстрых
   последовательных загрузках. Поэтому даже `max_size=1000000000` нельзя
   объявлять доказанной абсолютной физической границей. Источники:
   [Yandex bucket](https://yandex.cloud/en/docs/storage/concepts/bucket),
   [Google Drive quota](https://developers.google.com/workspace/drive/api/reference/rest/v3/about).
2. **Два поколения должны помещаться одновременно.** Единственная проверенная
   копия не удаляется до тех пор, пока новая не загружена и не прочитана
   обратно. Поэтому устойчивое состояние: два поколения плюс служебные байты.
   Размер одного шифротекста не должен превышать примерно **490 MB**. Если
   копия больше, конвейер **остановится с ошибкой и алертом**, но не удалит
   последнюю хорошую копию. Это выбранный компромисс «безопасность важнее
   свежести». Если production-копия выше, нужно либо поднять лимит, либо
   хранить одно поколение (теряется защита от порчи при замене).
3. Ротация только **после** проверки новой копии. До и во время загрузки ничего
   не удаляется: если старая и новая копии не помещаются вместе, загрузка
   отменяется с алертом. После загрузки новая копия заново читается целиком
   (SHA-256), и только тогда удаляются проверенные поколения, у которых
   **подписанное** время создания (`backup_created_at`) строго раньше. Не
   удаляются: непроверенные, неполные (нет receipt в списке), неоднозначные
   (дубли имён или ID на Drive), поколения без подписанного времени и более
   новые копии. Обрыв посреди удаления оставляет непроверяемый остаток; он
   учитывается в объёме, автоматически не удаляется и после заполнения лимита
   остановит публикацию с алертом. Так же работает MacBook.
4. S3 multipart `backend cleanup` отключён. Исходный код rclone
   (`backend/s3/s3.go`, `listMultipartUploads`) фильтрует по строковому префиксу
   без границы каталога: префикс `dr` совпал бы и с `dr2/...` чужого
   приложения, а без префикса затрагивается весь бакет. Точную область доказать
   нельзя, поэтому очистка не вызывается. Незавершённые загрузки в своём префиксе
   (с границей `/`) блокируют измерение. Безопасная альтернатива (решение
   владельца): правило lifecycle бакета `AbortIncompleteMultipartUpload` с
   фильтром ровно на префикс DenisStock.
5. Назначения логически изолированы по префиксам, но изоляция не равна
   гарантиям квоты, Object Lock или защите от внешнего автора. Публикация и
   ротация одного назначения сериализуются блокировкой (поток + `flock`) только
   на одном хосте. Второй хост, ручные действия в консоли или другой инструмент
   с теми же учётными данными этой блокировкой не охвачены.
6. Старые копии существующего production-механизма лежат отдельно и занимают
   собственные байты. Если для нового конвейера использовать тот же бакет, общий
   объём превысит 1 GB: нужен отдельный бакет/аккаунт.

## Что проверяется перед признанием поколения исправным

Облачный адаптер считает поколение проверенным, только если: ровно два файла,
подпись receipt верна закреплённым ключом, размер совпадает, и **полное
потоковое чтение** шифротекста даёт тот же SHA-256. Иначе оно не считается
хорошим и не может быть «последней исправной копией». Битое новейшее поколение
поэтому не заменяет старую копию. Совпадающие имена файлов/каталогов Drive
или повторяющиеся ID считаются неоднозначными: такое поколение не проходит
проверку и не удаляется. Чтение идёт по имени через rclone; чтение по
устойчивым ID объектов не реализовано. Повторная публикация под тем же именем
с другим шифротекстом отклоняется (сравнение с подписанным receipt).

## Ключи и секреты

- Подпись `production-1` (Ed25519, на VPS) и приватный age-ключ (офлайн) это
  **разные** ключи. Потеря age-ключа = потеря возможности восстановить любую
  копию: хранить минимум две независимые копии ключа вне VPS и облаков.
- Приватный ключ age никогда не читается конвейером. Ошибки облачных вызовов не
  содержат аргументов rclone и stderr. Статус-файл не содержит секретов.
- MacBook хранит только шифротекст: сам по себе он не расшифровывается, и для
  восстановления нужен офлайн-ключ.

## Мониторинг и алерты

Реализовано: ненулевой код выхода, `dr-status.json` (последняя попытка, время
исходного бэкапа из подписанного receipt, время загрузки/проверки, объём),

если VPS полностью недоступен, сообщение об этом даст только устаревание копии
на Mac (код 4) и ручная проверка.

## Восстановление

`manage.py dr_restore` расшифровывает копию и восстанавливает в **новую** базу и
**новые** каталоги. Существующее ничего не перезаписывает. До создания базы
проверяются: age, подпись manifest, SHA-256 всех файлов, хэши деревьев `media` и
`private_media`. После pg_restore сверяются миграции. Любая ошибка удаляет новую
базу, подготовленные каталоги и все расшифрованные временные файлы.
Переключение приложения на восстановленные данные выполняет оператор вручную.
`restore_private_media` и веб-восстановление теперь возвращают `private_media`.

Синтетический RTO из тестов (доли секунды) относится к пустой базе из нескольких
строк и **не** является production RTO.

### Совместимость старых поколений

| Формат | PostgreSQL | `media` | `private_media` | Ed25519 | age | Автоматический новый restore |
|---|---|---|---|---|---|---|
| Старый Yandex manifest + файлы | да | да, если присутствует | нет | да, для подписанных поколений | нет | нет, сохраняется прежний emergency-порядок |
| Новый DR bundle + receipt | да | да, если присутствует | да, обязательно | да | да | да, только после проверки ключей и хэшей |

Старые копии не переименовываются и не получают выдуманный `private_media`.
Каталог нового бэкапа создаётся атомарно (`mkdir` без `exist_ok`). Имя остаётся
прежним `ГГГГ-ММ-ДД_ЧЧ-ММ-СС`, потому что аварийная станция
(`Get-BackupRunAgeHours`) и интерфейс разбирают именно его. Только при
реальном совпадении в одну секунду добавляется суффикс; для такой копии
станция покажет возраст как неизвестный, а не выдумает его.
Новый `backup_created_at` обязателен для подтверждения свежести нового
поколения. Старый receipt без этого поля можно проверить криптографически,
но мониторинг не считает его свежим без временной привязки к подписанному
исходному manifest.

## Незакрытые условия до включения

1. Проверка адаптеров на реальных тестовых аккаунтах (команды `rclone` проверены
   только по подставной реализации).
2. Доказанный способ удовлетворить физическому лимиту, включая параллельные
   загрузки, скрытые версии и multipart. Сейчас отсутствует. `max_size` Yandex
   полезен как предохранитель, но не абсолютная гарантия.
3. Решение владельца по правам delete и отдельным аккаунтам; юридическое решение
   по размещению персональных данных в Google Drive. Google Drive не поддерживает
   Object Lock: владелец аккаунта может удалить шифротекст.
4. Канал алертов и внешний наблюдатель.
5. Совместимость с аварийной станцией: она читает прежний формат в Yandex. Новый
   формат работает **параллельно**, старый не отключается.
6. Production (read-only, 2026-10-08): 31 локальный каталог, 8 с владельцем
   root:root и режимом 755; web работает под UID 2001; ежедневный systemd unit
   запускается от root и завершался успешно семь последних дней. Web UID не
   имеет права очищать файлы внутри восьми каталогов, поэтому ручной/UI
   `keep_last` может остановиться на них. Нужна отдельная инвентаризация
   проверенности и утверждённый план прав, без массового chown или удаления.
7. Реальный запуск launchd на MacBook и отдельный Google аккаунт не проверены.

## Production: проверено только чтением, 2026-10-09

- HEAD `6916276`, все контейнеры healthy, `denstock-backup.timer` ежедневно в
  03:00 MSK, последние семь запусков завершились успешно (2026-10-09 за 5 мин).
- 31 локальный каталог, 8 из них root:root (все от 2026-09-21), web работает
  под UID 2001. Локальные копии около 1.1 GB, одна копия около 46.5 MB.
- **Текущие production-копии не содержат `private_media`.** Том
  `/app/private_media` (16 файлов, около 50 MB) сейчас не попадает ни в одну
  копию: это реальный пробел до выпуска этой ветки.
- В `media` и `private_media` нет символических ссылок и специальных файлов:
  новая проверка не остановит ежедневный бэкап.
- Обёртка `/usr/local/sbin/denstock-backup-capped` запускается с
  `set -euo pipefail` и вызывает `backup_all --keep-last 14` от UID 2001.
  Поэтому ошибка ротации **не должна** валить `backup_all`: иначе выгрузка в
  Yandex прекратилась бы каждый день. В этой ветке ошибка ротации
  выводится предупреждением, остальные старые копии удаляются, новая копия
  считается созданной.
- Бакет Yandex версионирован, обёртка выполняет `backend cleanup-hidden` по
  всему бакету и разбирает имена копий строгим шаблоном времени. Новый DR
  конвейер поэтому должен жить в **отдельном невесионированном бакете**: в общем
  бакете чужая очистка затронула бы его версии, а удаление на версионированном
  бакете не освобождает объём (ротация тогда честно остановится с алертом).
- Оценка: шифротекст около 46.5 MB + около 50 MB `private_media` (до сжатия),
  то есть около 100 MB на поколение. Два поколения помещаются в 1 GB с большим
  запасом.

## Отдельный план для восьми root-owned локальных копий

Это только план, в Round 2 production не меняется.

1. Снять read-only список точных каталогов, владельцев, manifest, подписей и
   результатов проверки восстановления; сопоставить с offsite-копиями.
2. Сделать новую проверенную копию и подтвердить минимум одно независимое
   восстановимое поколение до любых изменений прав или retention.
3. Выбрать одного ответственного за локальную ротацию: host-level root unit
   либо web UID 2001. Не запускать два разных очистителя одновременно.
4. Если выбран web, отдельно утвердить изменение прав только на восемь
   подтверждённых каталогов и их содержимое. Без утверждения оставить как есть
   и сигнализировать об ошибке ротации. Нельзя делать рекурсивный chown всего
   дерева бэкапов или удалять каталоги по одному лишь возрасту.
5. После изменения, если оно будет разрешено, проверить подписи, локальную
   ротацию, доступность offsite и тест восстановления.
6. Репетиция восстановления на копии production по письменному разрешению, в
   изолированной PG16 без сети Telegram и MAX.

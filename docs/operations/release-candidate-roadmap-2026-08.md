# Release candidate: roadmap 2026-08

Локальный кандидат на релиз. НЕ развёрнут, НЕ влит в main, НЕ отправлен в
удалённый репозиторий. Документ описывает состав, проверки и то, что
сознательно оставлено за рамками релиза.

## Состав

Ветка: `integration/roadmap-release-candidate`
База: `ff6048b` (main на момент сборки)

Собрано из двух независимо проверенных веток:

- `integration/roadmap-client360-emergency` на `4910fd4`;
- `feature/catalog-excel-import` на `b45382d`.

Возможности:

1. Аварийный локальный режим (резервная копия, standby, заморозка, failback).
2. Мультипозиционный сканер продажи.
3. Мультипозиционный сканер выдачи в ремонт.
4. Справочник клиентов с постоянной карточкой.
5. Телефон клиента и безопасный поиск по нему.
6. Исторические снимки клиента в документах.
7. Отчёт «Ремонты по клиентам».
8. Отчёт «Продажи и ремонты по клиентам» и лента документов клиента.
9. Импорт каталога из Excel (первый поддержанный формат BRP).
10. Надбавка BRP за винтажный склад в централизованном расчёте цены.

## Миграции

Новые относительно `ff6048b`:

- `operations/0002_deploymentstate_offlinesession_emergencyauditevent_and_more`;
- `operations/0003_add_completed_offline_session_status`;
- `customers/0001_initial`;
- `sales/0005_reservation_customer_sale_customer`;
- `repairs/0003_repairorder_customer`;
- `catalog_import/0001_initial`.

Свойства, проверенные вручную:

- по одному листу на приложение, конфликтующих веток миграций нет;
- зависимости корректны: `sales/0005` и `repairs/0003` зависят от
  `customers/0001_initial`;
- ни одной `RunPython` среди новых миграций, то есть данные не переписываются;
- ни одного `unique=True`: телефон клиента только индексирован;
- связь документа с клиентом `null=True` и `PROTECT`;
- автоматической привязки исторических документов к карточкам НЕТ.

## Что релиз НЕ делает

- не связывает существующие документы с карточками клиентов: после
  развёртывания они остаются с `customer_id = NULL` и работают на снимках;
- не импортирует прайс BRP: развёртывание возможности и загрузка файла это
  два разных действия;
- не переводит склад в автономный режим: код аварийного режима появляется, но
  переключение выполняет оператор отдельной процедурой.

## Матрица проверок

Смотри финальный отчёт сессии. Кратко: полный набор на SQLite, целевые наборы
по каждой возможности, миграции, линтеры, проверка секретов, синтаксис JS и
PowerShell.

## Дефекты, найденные при сборке

1. Справочник клиентов и партии импорта каталога не входили в список
   бизнес-приложений аварийного режима: их записи проходили мимо SQL-уровня
   защиты записи, а отпечаток бизнес-состояния их не учитывал, из-за чего
   решение о failback было слепым к изменениям клиентов на production.
   Исправлено, добавлен тест на полноту списка.
2. Надбавка за винтажный склад применялась не во всех путях расчёта цены:
   очередь приёмки, пересчёт при инвентаризации, продвижение позиции через
   замену и финансовый отчёт склада обходили её. Одна деталь показывала бы
   разную цену на разных экранах. Исправлено, добавлен тест согласованности.

## Известные ограничения

- Приёмка реального файла BRP от 13.08.2026 не выполнялась: файла нет ни в
  репозитории, ни в сессии. Формат доказан документацией импортёра и
  зафиксирован тестами, но подтверждение на реальном файле остаётся.
- Тест приватного вложения помощи падает только на PostgreSQL по причине
  изоляции теста, а не дефекта продукта. Подробности в
  `docs/operations/emergency-local-mode.md`.

## Перед релизом

Обязательно снять свежие показатели production прямо перед выпуском: счётчики
предыдущих сессий устарели, работа на складе продолжалась. Порядок шагов в
отчёте сессии.

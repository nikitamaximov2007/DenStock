# Web healthcheck после OOM 23 октября 2026 года

База кандидата: `5afd34902bf170b58a6f54ed226f53d558d78a7c`.
Целевой SHA берётся из отдельного отчёта о квалификации. Этот документ не даёт
разрешения менять production.

## Причина и область исправления

В `web` и `catalog-web` Docker запускал `CMD-SHELL`, который создавал дочерний
Python. У `urllib.request.urlopen` не было собственного таймаута. Когда Docker
прерывал shell по истечении пяти секунд, Python оставался работать с PPID 1.
В журнале предыдущей загрузки число таких процессов в `web` выросло с 14 до
84; затем происходили global OOM с завершением PostgreSQL, Gunicorn и ботов.

Новый HTTP probe запускается напрямую через `CMD`, проверяет только локальный
`127.0.0.1:8000/healthz/`, имеет таймаут подключения/чтения две секунды и
общий срок три секунды. Docker timeout остаётся пять секунд. Изменены
`web`, `catalog-web` и `emergency-web`; healthcheck ботов и PostgreSQL не
использует зависший HTTP-запрос и остаётся прежним. Миграций нет.

## Отдельный web-only выпуск после разрешения владельца

1. Сверить фактический running image ID, OCI revision и source archive hash
   через `scripts/operations/release_image_identity.py verify --runtime`.
   Сверить точный Git SHA, чистоту checkout, Compose overlays, схему,
   здоровье всех сервисов, backup lock, свободное место, swap и число
   зависших healthcheck-процессов. При ином running SHA подготовить новую
   интеграцию вместо установки этого кандидата поверх неизвестной версии.
2. В согласованном тихом окне создать полный подписанный PRE через общий lock
   и `backup_all` **без** `--keep-last` и без capped wrapper. Проверить
   `db.dump`, `media.tar.gz`, `private_media.tar.gz`, Ed25519 и SHA-256;
   зашифровать age и сохранить на Mac в новом каталоге. Восстановить
   PostgreSQL 16 и оба дерева файлов в изоляции, проверить ссылки. Сохранить
   предыдущие recovery points. Точный порядок и идентификацию SHA задаёт
   `docs/operations/release-image-identity.md`. Если согласованная процедура
   передачи/восстановления недоступна, остановиться до установки.
3. Сохранить прежний `web` image ID и конфигурацию для app-only rollback.
   На точном одобренном SHA собрать только `web` командой
   `python3 scripts/operations/release_image_identity.py build --sha "$TARGET_SHA" --services web`.
   Перед запуском проверить image ID, OCI revision, source archive SHA-256 и
   Compose-конфигурацию. Убедиться, что image содержит
   `/app/docker/http_healthcheck.py`, а у `web` задан `CMD`, не `CMD-SHELL`.
4. После отдельного разрешения обновить только `web`:
   `docker compose up -d --no-build --no-deps --wait web`. Не пересоздавать
   `db`, `catalog-web`, Caddy, Telegram, MAX или preview. Не запускать
   `migrate` вручную: штатный entrypoint выполнит свою проверку; новых
   миграций в кандидате нет.
5. Проверить runtime identity, `/healthz/`, HTTPS склада и `pro-brp.ru`,
   анонимный 404 приватного вложения, здоровье ботов и каталога, миграции,
   остатки и документы без бизнес-записей. Повторно моделировать зависший
   HTTP только в синтетическом контейнере, не на production. На production
   в течение наблюдения проверять, что число probe-процессов не растёт,
   swap и `oom_kill` не увеличиваются.
6. Создать полный подписанный POST без ротации, зашифровать age отдельно от
   PRE, восстановить PostgreSQL 16, public media и private_media в изоляции.
   Только успешное восстановление POST закрывает выпуск. При ошибке
   остановиться и сохранить журналы, образ и копии; не восстанавливать старую
   БД и не выполнять разрушительный откат без отдельного решения.

Существующий `catalog-web` продолжит работать с прежним healthcheck до его
отдельного разрешённого обновления. Он потреблял меньше зависших проверок,
но тот же механизм присутствует. Проверка в emergency Compose вступит в силу
при будущем отдельном запуске аварийного контура.

## Preview: только после подтверждения, что контур не используется

`catalog-web-preview` и `catalog-preview-db` принадлежат отдельному Compose
проекту `denstock-catalog-preview`; БД хранится в отдельном volume. У них нет
опубликованных портов. Production Caddy маршрутизирует публичный каталог на
`catalog-web`, а не на preview. Preview web также входит в `denstock_default`,
поэтому перед остановкой нужно подтвердить у владельца отсутствие ручного
внутреннего использования и проверить активные соединения preview-БД.
У `catalog-web-preview` тот же старый HTTP healthcheck; этот Git-кандидат не
перезаписывает конфигурацию отдельного preview-проекта.

После отдельного разрешения, зафиксированных container/image ID и здорового
основного склада остановить **существующие контейнеры**, без `compose down`,
`rm`, `prune` и удаления volume:

```bash
docker stop --time 30 catalog-web-preview
docker stop --time 30 catalog-preview-db
```

Проверить основной склад, каталог, Caddy, ботов, свободную память и swap.
По измерению до swap ожидается освобождение порядка 180 MiB, но немедленное
изменение `free` может отличаться. Политика `unless-stopped` сохраняет ручную
остановку после рестарта Docker. Для возврата без пересоздания:

```bash
docker start catalog-preview-db
# дождаться healthy, сверить container ID и доступность preview-БД
docker start catalog-web-preview
# дождаться healthy, сверить container ID и доступность preview web
```

Если обнаружены пользовательские обращения или зависимость production от
preview, остановку не проводить.

## Остальные источники нагрузки

MySQL 8.0 появился **после** аварии: журнал APT показывает установку
`mysqltuner` 23 октября в 14:26 МСК с `mysql-server-8.0` как зависимостью.
Сервис включён в автозапуск, слушает только loopback, пользовательских схем
и активных подключений при проверке не было. Он занимает примерно 380–400 MiB.
Не останавливать и не менять автозапуск без отдельного согласия владельца.

`/opt/scan.sh` создан в июне 2024 года и вызывается root cron `@reboot`.
Он проверяет свободные сегменты `/dev/vda` и при определённом условии запускает
`/opt/disk.sh`, который вызывает `fdisk`, `partprobe` и `resize2fs`.
Назначение похоже на расширение системного раздела при увеличении диска;
происхождение у провайдера не подтверждено. Не запускать и не изменять без
отдельного разбора. В скриптах не обнаружено сетевых обращений.

На VPS с 2 GiB RAM даже после удаления утечки остаётся маленький запас при
совместной работе Gunicorn, PostgreSQL, preview и MySQL. Увеличение до 4 GiB
рекомендуется как отдельное решение после стабилизации healthcheck; оно не
заменяет исправление. Для раннего предупреждения отслеживать `MemAvailable`,
swap, `oom_kill`, число процессов `/app/docker/http_healthcheck.py` и
процессы с PPID 1 внутри web, а также пиковую нагрузку backup jobs. Мониторинг
не должен запускать ещё один тяжёлый процесс на этом VPS.
На момент проверки отдельного GitHub backup timer/cron не найдено; штатный
`denstock-backup.timer` запускается в 03:00 МСК и не имеет `MemoryMax`.
Добавление нового backup job требует отдельного измерения пика памяти и
разнесения расписаний, чтобы два полных архива не создавались одновременно.

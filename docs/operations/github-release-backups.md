# Ежедневные зашифрованные копии в GitHub Releases

Независимый канал резервных копий: отдельный ПРИВАТНЫЙ репозиторий GitHub,
каждая копия хранится как выпуск (Release) с зашифрованным файлом. Бюджет
владельца: не больше 1 ГиБ файлов выпусков.

Состояние на 2026-10-22: `nikitamaximov2007/datamax` создан и приватен, но
в нём нет ни одного Release. Кандидат прошёл локальную синтетическую
квалификацию; настоящая приёмка GitHub ещё не проводилась.
Production и настройки `datamax` на этом этапе не меняются. Пока не выполнены
настоящая выгрузка, чтение назад и восстановление (раздел 11), этот канал
production не защищает.

## 1. Ограничения GitHub (проверено по документации 2026-10-13)

- Каждый файл выпуска меньше 2 ГиБ. Общего лимита на размер выпусков и трафик
  GitHub не объявляет; до 1000 файлов в одном выпуске.
- Правила допустимого использования, раздел 9 "Excessive Bandwidth Use":
  GitHub может ограничить аккаунт при трафике, значительно большем, чем у
  похожих пользователей. Наш объем: около 100 МиБ выгрузки в сутки, 1 ГиБ
  хранения, чтение назад того же объема. Это скромно, но гарантии нет: канал
  не единственный (Yandex и комплект на Mac остаются).
- Права fine-grained токена: выпуски и их файлы относятся к разрешению
  "Contents" (чтение: list и download; запись: create, publish, delete).
- Черновики выпусков видны только пользователям с правом записи.
- Неизменяемые выпуски (immutable releases) запрещают менять и удалять файлы
  опубликованного выпуска, но сам выпуск удалить можно. От удаления злоумышленником
  они не защищают.
- Скачивание файла: API отвечает 302 на подписанный адрес хранилища. Скрипт
  переходит туда сам и БЕЗ токена: токен никогда не уходит на чужой адрес.

## 2. Что лежит в одной копии

Выпуск `denstock-backup-<RUN>-<12 знаков SHA-256 manifest>`, два файла:

| Файл | Содержимое |
| --- | --- |
| `<RUN>.signed-backup.tar.age` | весь подписанный запуск копии: `db.dump`, `media.tar.gz`, `private_media.tar.gz`, `manifest.json` с подписью Ed25519 и хешами. Зашифрован age на сервере, до выгрузки |
| `<RUN>.backup.json` | описание: размер и SHA-256 шифртекста, SHA-256 manifest, коммит, время, публичный получатель age. Без секретов и данных клиентов |

Открытого текста клиентов, приватных файлов, секретов и ключей в GitHub нет:
это проверяет тест (маркер открытого текста не встречается ни в одном файле).

## 3. Как проходит ежедневный запуск

`scripts/operations/github_release_backup.py push`:

1. Блокировка: второй одновременный запуск выходит с кодом 75, ничего не меняя.
2. Репозиторий должен быть приватным и не совпадать с репозиторием исходного
   кода (`GHB_FORBIDDEN_REPOS`).
3. Берется самая новая локальная копия со статусом `verified`. Отказ, если в
   ней нет `private_media` (или public media, когда она указана в manifest),
   если хеш любого файла не совпадает с manifest или подпись Ed25519 manifest
   не проходит проверку закрепленным публичным ключом
   (`GHB_MANIFEST_PUBKEY`, по умолчанию
   `/etc/denstock/manifest-signing/production-ed25519.pub`). На VPS перед
   установкой требуется проверить наличие `python3-cryptography`.
   `app_commit` обязан быть полным SHA из 40 шестнадцатеричных символов.
4. Если на GitHub уже есть целая копия с тем же идентификатором: ничего не
   делается. Если есть неподтвержденная с тем же идентификатором: отказ, без
   перезаписи. Если на GitHub уже есть более новая целая копия: старая не
   выгружается.
5. Собственные незавершенные черновики (обрывы прошлых запусков) удаляются.
6. `tar | age -r <получатель>` в файл шифртекста (открытый текст на диск не
   пишется), считаются размер и SHA-256.
7. Ротация до выгрузки (раздел 4). Если копия не помещается в бюджет даже
   после ротации: отказ, НИЧЕГО не удаляется.
8. Создается ЧЕРНОВИК выпуска, файл выгружается, затем скачивается назад и
   сравнивается по размеру и SHA-256. Так же с описанием.
9. Только после совпадения выпуск публикуется. Обрыв на любом шаге оставляет
   черновик, который никогда не считается точкой восстановления.
10. Ротация после выгрузки: под рабочий порог ВМЕСТЕ с запасом на завтрашнюю
    копию (размер сегодняшней плюс 10%, `GHB_RESERVE_FACTOR`). Поэтому в
    обычном режиме старые копии удаляются только после того, как новая
    доказана чтением назад, а не перед выгрузкой.
11. Статус в `/opt/denstock/backups/github_backup_status.json`: `ok`,
    `warning` (занято выше порога, но в бюджете) или `failed` с причиной.

Ошибки называются прямо: токен недействителен или просрочен (401), нет прав
или лимит (403), GitHub недоступен (5xx, сеть), файл выгружен не полностью.
Токен не попадает ни в журнал, ни в статус, ни в аргументы команд.

## 4. Политика хранения и ротации

| Параметр | По умолчанию |
| --- | --- |
| `GHB_BUDGET_BYTES` (жесткий бюджет) | 1 073 741 824 (1 ГиБ) |
| `GHB_WATERMARK_BYTES` (рабочий порог) | 891 289 600 (850 МиБ) |
| `GHB_MIN_KEEP` (минимум целых копий) | 2 (меньше нельзя) |

Конфигурация может только уменьшить бюджет и порог; увеличить их выше 1 ГиБ
и 850 МиБ скрипт не разрешает.

- Считаются байты ВСЕХ файлов ВСЕХ выпусков репозитория, включая чужие
  выпуски и черновики. Размер git-репозитория не важен: копии в git не
  попадают, выпуски создают только легкие теги.
- Удаляются только собственные копии, старые раньше новых: сначала
  поврежденные или неполные, затем самые старые целые.
- Целые копии удаляются, только пока их остается больше двух. Перед удалением
  целой копии оставшиеся последние копии скачиваются полностью и сверяются по
  SHA-256. Тихо поврежденная копия перестает считаться целой и не может
  остаться "последней".
- Никогда не удаляются: чужие выпуски и теги, выпуски с `[keep]` в названии
  (владелец закрепляет вручную), выпуски с тем же идентификатором без
  подтверждения.
- Сбой старой операции не трогает более новые копии.
- Инвариант предполагает, что кроме этой процедуры никто не добавляет assets
  одновременно с выгрузкой. Сторонняя запись в репозиторий может изменить
  объем после измерения; монитор повторно проверяет общий размер.
- Контроль с токеном только для чтения не видит черновики GitHub. Полный учёт
  черновиков и их assets делает `push` с токеном записи; независимые наблюдатели
  проверяют опубликованные выпуски. Одновременных сторонних авторов в
  `datamax` быть не должно.

Расчет для production: копия около 98 МиБ (база 34,5 МБ, media 12 МБ,
private_media 51 МБ, шифрование почти не меняет размер). Под порогом 850 МиБ
с запасом на завтрашнюю копию держится 7 копий (на время выгрузки 8), то
есть 7 дней истории. Рост данных автоматически уменьшает
число дней. Во время выгрузки рядом с новой копией должны остаться две целые
старые, то есть три копии сразу: до 283 МиБ на копию все идет под порогом; от
283 до 341 МиБ занятость ненадолго выше порога и сразу после выгрузки
возвращается под него; больше 341 МиБ три копии не помещаются в 1 ГиБ и
выгрузка останавливается с ошибкой бюджета, ничего не удаляя. Запас роста
относительно сегодняшних 98 МиБ: примерно в 3,5 раза.

## 5. Расписание

- `deploy/github-backup/systemd/denstock-github-backup.timer`: ежедневно в
  05:00 МСК (ночная копия в 03:00), случайная задержка до 15 минут,
  `Persistent=true` догоняет пропуск после простоя.
- Шифртекст готовится в `/var/lib/denstock-github-backup` (systemd
  `StateDirectory`, 0700), а не в `/opt/denstock/backups`: ночная обёртка и
  ротация `backup_all` его не видят.
- `denstock-github-backup.service`: после `denstock-backup.service`, таймаут
  2 часа, защита systemd (`ProtectSystem=strict`, `NoNewPrivileges`), код 75
  (занято) не считается ошибкой.
- При ошибке: `OnFailure` пишет запись в журнал, а сама задача вызывает
  `GHB_NOTIFY_SCRIPT` (текст ошибки на stdin), если он задан.

## 6. Независимый контроль: FRESH / STALE / CORRUPT

`github_release_backup.py check` с токеном ТОЛЬКО ДЛЯ ЧТЕНИЯ, не на VPS:

| Вывод | Код | Значение |
| --- | --- | --- |
| `FRESH` | 0 | новейшая целая копия моложе порога, целых копий не меньше двух |
| `DEGRADED` | 2 | свежая, но целая копия только одна |
| `STALE` | 2 | новейшая целая копия старше порога (26 часов) или копий нет |
| `CORRUPT` | 1 | `--deep`: SHA-256 скачанной копии не совпал |
| `OVER_BUDGET` | 1 | занято больше бюджета |
| `UNREACHABLE` | 1 | GitHub недоступен или токен не работает |

Два независимых наблюдателя:

1. GitHub Actions в самом репозитории копий
   (`deploy/github-backup/backup-repo/.github/workflows/backup-freshness.yml`):
   ежедневно в 07:30 МСК, по понедельникам полная проверка всех копий.
   Встроенный токен только читает. Упавший запуск GitHub присылает владельцу
   письмом. Правило об отключении расписания после 60 дней без активности
   относится к публичным репозиториям, а этот приватный.
2. Mac владельца (`deploy/github-backup/mac/`): ежедневная проверка с
   уведомлением macOS и раз в неделю ХОЛОДНАЯ КОПИЯ новейшего шифртекста в
   `~/DenisStock-Recovery-Updates/github/<дата>/`.

## 6a. Как видны ошибки GitHub (квота, API, токен)

| Что случилось | Где видно |
| --- | --- |
| Токен истек или отозван (401) | статус `failed`: «токен недействителен или просрочен»; Actions и Mac: `UNREACHABLE`, затем `STALE` |
| Нет прав или лимит запросов (403, 429) | статус `failed`: «нет прав или превышен лимит» / «лимит запросов GitHub исчерпан» |
| GitHub недоступен, обрыв сети | статус `failed`: «GitHub недоступен»; копия не публикуется, старые не трогаются |
| Копия не помещается в 1 ГиБ даже после ротации | статус `failed`: «не помещается в бюджет ... ничего не удалено» |
| Объем выше 850 МиБ, но в бюджете | статус `warning` |
| Ночь не выполнилась вовсе (VPS умер) | Actions и Mac: `STALE` через 26 часов, письмо GitHub |
| Копия на GitHub испорчена | Actions по понедельникам и Mac: `CORRUPT` |

Статус-файл: `/opt/denstock/backups/github_backup_status.json`; при `failed`
задача вызывает `GHB_NOTIFY_SCRIPT` (текст на stdin), если он задан, и
systemd пишет запись `denstock-github-backup` в журнал.

## 7. Безопасность и остаточные риски

- Токен VPS: fine-grained, доступ только к одному репозиторию копий,
  разрешение "Contents: Read and write" (и обязательное "Metadata: Read").
  Без "Workflows", поэтому изменить наблюдатель Actions он не может. Срок
  действия ограничен (не больше года): просроченный токен дает понятную
  ошибку 401 и письмо от наблюдателя.
- Закрытого ключа age нет ни на VPS, ни в GitHub: на сервере только публичный
  получатель. Задача отказывается работать, если в файле получателя лежит
  закрытый ключ.
- РИСК: тот, кто захватит VPS, получит токен и сможет удалить выпуски (право
  записи в "Contents" включает удаление; неизменяемые выпуски это не
  запрещают). Смягчение: (а) наблюдатель Actions и Mac увидят STALE на
  следующий день; (б) холодная копия на Mac не зависит от GitHub; (в) Yandex и
  комплект на Mac остаются отдельными каналами; (г) расшифровать украденное
  злоумышленник не может.
- Включите в репозитории неизменяемые выпуски: файлы опубликованной копии
  нельзя будет подменить, даже имея токен (удалить выпуск по-прежнему можно).
  Скрипт совместим: файлы прикладываются к черновику до публикации, а ротация
  удаляет выпуск целиком.

## 8. Настройка и установка (только после отдельного одобрения владельца)

### 8.1 GitHub (владелец, в браузере)

1. Использовать приватный `nikitamaximov2007/datamax`, а не репозиторий кода.
2. После разрешения Settings: включить Immutable releases. В настройках уведомлений GitHub:
   письма о падении Actions.
3. После разрешения опубликовать три файла из
   `deploy/github-backup/backup-repo/`: README, workflow и
   `monitor/github_release_backup.py` (его совпадение с проверенным скриптом
   контролирует тест).
4. Токен для VPS (fine-grained): только этот репозиторий; Contents: Read and
   write; Metadata: Read; срок 1 год; напоминание за 2 недели.
5. Токен для монитора на Mac: только этот репозиторий; Contents: Read-only.
6. Токены сохранять сразу в файлы с правами 0600, не в чат, не в аргументы
   команд и не в историю shell. На Mac: скопировать токен в буфер и
   `umask 077; pbpaste > ~/.config/denisstock/github-read.token` (и так же
   файл токена записи для приемки). На VPS (шаг 8.3):
   `install -m 600 /dev/null /etc/denstock/github-backup.token`, затем
   `cat > /etc/denstock/github-backup.token`, вставить токен, Enter, Ctrl+D.

### 8.2 Приемка на настоящем GitHub (Mac, пока репозиторий пуст)

```bash
cd ~/Developer/DenStock-github-backups-67b
GHB_CONFIG=/nonexistent GHB_REPO=nikitamaximov2007/datamax GHB_TOKEN_FILE=<файл ограниченного токена записи> ~/Developer/DenStock/.venv/bin/python scripts/operations/github_backup_acceptance.py --source-repo nikitamaximov2007/DenStock
```

(Python из venv проекта: системному `python3` macOS не хватает
`cryptography` для одноразовой подписи. Нужны `age` и `age-keygen`, они
установлены.)

Синтетические данные, одноразовый ключ age и одноразовый ключ подписи.
Проверяет: приватность, что токен не видит репозиторий кода, черновик,
выгрузку, чтение назад по SHA-256 (перенаправление без токена), публикацию,
постраничную выдачу выпусков и файлов, учет байтов, расшифровку. Перед
удалением своего тестового выпуска спрашивает `DELETE`. Итог `ACCEPTED`.
Этот шаг требует отдельного разрешения на создание тестового выпуска. Его
удаление выполняется только после ещё одного подтверждения владельца.

### 8.3 Production (после отдельного разрешения и успешной 8.2)

1. `apt install age` на VPS.
2. `/etc/denstock/github-backup.token` (0600, root): токен записи.
3. `/etc/denstock/github-backup-recipient.txt`: содержимое
   `~/DenisStock-Recovery/keys/recipient.txt` (публичный, не секрет).
4. `/etc/denstock/github-backup.env` (0600): пример без секретов находится в
   `deploy/github-backup/config/github-backup.conf.example`.

   Публичный ключ подписи берется по умолчанию из
   `/etc/denstock/manifest-signing/production-ed25519.pub`.
5. Скрипт вне рабочего дерева git (как обёртка в `/usr/local/sbin`), чтобы
   будущий `git checkout` в `/opt/denstock` его не задевал:
   `install -D -m 755 github_release_backup.py /usr/local/lib/denstock/github_release_backup.py`
   (файл из квалифицированной ветки `codex/github-release-backups-prod-67b`), файлы
   `deploy/github-backup/systemd/*` в `/etc/systemd/system/`,
   `systemctl daemon-reload`.
6. Первый запуск вручную: `systemctl start denstock-github-backup.service`,
   затем `cat /opt/denstock/backups/github_backup_status.json` (ожидается `ok`).
7. С Mac (файл `~/.config/denisstock/github-backup-monitor.env`, 0600:
   `GHB_REPO=nikitamaximov2007/datamax` и
   `GHB_TOKEN_FILE=<путь к файлу токена чтения>`):

   ```bash
   cd ~/Developer/DenStock-github-backups-67b
   export GHB_CONFIG=~/.config/denisstock/github-backup-monitor.env
   python3 scripts/operations/github_release_backup.py check --deep
   python3 scripts/operations/github_release_backup.py fetch --out ~/DenisStock-Recovery-Updates/github/first
   scripts/dr/morning_real_drill.sh --kit ~/DenisStock-Recovery-Updates/github/first \
     --fresh-secrets --pubkey <закреплённый публичный ключ> \
     --source-git https://github.com/nikitamaximov2007/DenStock.git
   ```

   Ожидается `DEGRADED` (копия пока одна, это нормально), затем
   `passed=True` изолированного восстановления; фразу вводит владелец.
8. Только после этого: `systemctl enable --now denstock-github-backup.timer`.
9. Монитор на Mac (`deploy/github-backup/mac/`) и проверка Actions.

## 9. Восстановление только с GitHub (VPS и Yandex недоступны)

Нужно: доступ к аккаунту GitHub; ключ `recovery-identity.age` и его парольная
фраза; заранее закреплённый публичный ключ подписи production
(`production-manifest-ed25519-public.pem`, храните независимо от VPS и GitHub);
исходный код из репозитория DenStock на GitHub.

```bash
GHB_REPO=nikitamaximov2007/datamax GHB_TOKEN_FILE=<файл токена чтения> GHB_CONFIG=/nonexistent \
  python3 scripts/operations/github_release_backup.py fetch --out ~/dr-kit
scripts/dr/prepare_kit_restore.sh --kit ~/dr-kit --identity <recovery-identity.age> --work <НОВАЯ папка> \
  --fresh-secrets --pubkey <production-manifest-ed25519-public.pem> \
  --source-git https://github.com/nikitamaximov2007/DenStock.git
```

Затем команду `offline_restore.sh`, которую напечатает скрипт (изолированный
запуск и полная проверка), и дальше по
`disaster-recovery-vps-and-yandex-lost.md` с раздела 13.

Обычный полный clone репозитория DenStock получает ветку с текущим production
SHA `67b468a467cce81c1f2154b167791681d3171e76`; shallow/single-branch
clone `main` этот SHA не содержит. `prepare_kit_restore.sh` проверяет наличие
точного SHA и отказывается продолжать без него. Ветку с развёрнутым SHA
нельзя удалять до переноса принятой истории в `main`.

- `fetch` выбирает новейшую целую копию, сверяет SHA-256 с описанием, не
  перезаписывает существующие файлы.
- `--fresh-secrets` создает новые пароли базы и `DJANGO_SECRET_KEY`.
  Данных, зашифрованных этим ключом, в DenisStock нет; пользователям нужно
  войти заново. Токены Telegram и MAX, домен и новый ключ подписи владелец
  получает и вписывает до открытия сервиса (у @BotFather и в кабинете MAX).
- Если доступен комплект на Mac, лучше `--secrets` из него: сохранятся
  прежние настройки.

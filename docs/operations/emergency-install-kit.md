# Установка аварийного DenisStock на компьютер склада

Документ для того, кто физически придёт к компьютеру и поставит аварийный
DenisStock. Здесь только порядок действий и точные команды. Устройство самого
аварийного режима описано в [emergency-local-mode.md](emergency-local-mode.md),
процедуры замены станции и ротации ключа - в
[release-runbook-mvp.md](release-runbook-mvp.md), разделы 17 и 18.

Инструкция для сотрудника, который будет этим пользоваться, отдельная и
короткая: [emergency-denis-one-page.md](emergency-denis-one-page.md).

---

## 1. Что должно быть до выезда

| | |
|---|---|
| Публичный ключ подписи | файл `production-manifest-ed25519-public.pem` с production |
| Отпечаток этого ключа | `5615837ef355d2d1881508434980efac31f1c467acb3d31c57101ced3ee5d5b1` |
| Идентификатор ключа | `production-1` |
| Полный SHA развёрнутого релиза | значение `DENSTOCK_APP_COMMIT` с production |
| Источник копий | путь или remote, откуда станция забирает подписанные копии |
| Probe token | отдельный read-only токен, вводится в установщике вручную |
| Доступ к копиям | отдельная служебная учётная запись только на чтение и её ключ, настроенные в rclone как источник `yandex-s3` |
| Адрес production | `https://185-250-44-206.sslip.io` |

Приватный ключ подписи на станцию не привозится и не устанавливается никогда.
Станция проверяет подписи закреплённым публичным ключом, подписывать ей нечего.

---

## 2. Требования к компьютеру

| | Минимум | Рекомендуется |
|---|---|---|
| Windows | 10, сборка 19041 | 11 |
| Разрядность | 64 | 64 |
| Оперативная память | 8 ГБ | 16 ГБ |
| Свободное место | 30 ГБ | 60 ГБ |
| Сеть | проводная или Wi-Fi в сети склада | проводная, постоянный адрес |

Место расходуют образы Docker, база PostgreSQL, media, две копии standby и
файловая система WSL. Минимум взят из проверки в установщике, рекомендуемое
значение оставляет запас на рост каталога и истории.

Виртуализация в BIOS/UEFI должна быть включена: без неё WSL2 не работает.

Docker Desktop не нужен. Станция работает на Docker Engine внутри WSL2.

## 2а. Доступ к хранилищу копий

Станция забирает копии из объектного хранилища и **ничего в него не пишет**.
Поэтому у неё своя учётная запись, только на чтение, и свой ключ. Учётные
данные, которыми production выгружает копии, на станцию не переносятся никогда.

Порядок делается один раз и вне DenisStock:

1. В облаке завести отдельную служебную учётную запись для станции.
2. Выдать ей право чтения **только** на хранилище копий, ничего больше.
3. Создать для неё статический ключ доступа.
4. На станции выполнить `rclone config` под тем пользователем Windows, от
   которого будет работать станция, и создать источник с именем `yandex-s3`:
   тип `s3`, провайдер `Other`, регион `ru-central1`, адрес
   `https://storage.yandexcloud.net`.
5. Проверить источник командой из шага 1 ниже.

Правила, которые нарушать нельзя:

- ключ выгрузки копий с production на станцию не переносится;
- ключ не попадает в снимки экрана, заявки, переписку, Git и наборы диагностики;
- ключ не передаётся сценариям параметром: параметр остаётся в журнале команд;
- права на запись у станции нет, и проверка её не запрашивает.

Проверка источника ничего в хранилище не создаёт и не удаляет: она только
перечисляет каталоги копий. Пробного объекта не появляется.

## 3. Порядок установки

### Шаг 1. Проверка компьютера

Открыть PowerShell **от имени администратора** и выполнить:

```
powershell -NoProfile -ExecutionPolicy Bypass -File C:\DenisStock\scripts\operations\Test-DenisStockEmergencyPreflight.ps1 -BackupSource "yandex-s3:denstock-backups-nikita"
```

Проверка ничего не меняет. Итог трёх видов: `ГОТОВО`, `ВНИМАНИЕ`, `ОСТАНОВКА`.
Пока есть хотя бы одна `ОСТАНОВКА`, дальше идти нельзя: в конце выводится
список того, что именно исправить.

Источник копий проверяется здесь намеренно, **до** установки. Без него станция
встанет готовой, но забирать копии ей будет неоткуда, и выяснится это только на
первой синхронизации.

### Шаг 2. Подготовка подсистемы Linux

Если проверка сказала, что WSL нет или нет нужного дистрибутива, выполнить
установщик с ключом подготовки среды. Он поставит WSL, дистрибутив и Docker
Engine, после чего **сам остановится и попросит перезагрузку**:

```
powershell -NoProfile -ExecutionPolicy Bypass -File C:\DenisStock\scripts\operations\Install-DenisStock-EmergencyWorkstation.ps1 `
  -RepoRoot C:\DenisStock -InstallWslRuntime `
  -BackupSource "<источник копий>" -ProductionUrl "https://185-250-44-206.sslip.io" `
  -PrimaryLanAddress "<адрес компьютера в сети склада>" -AppCommit "<полный SHA релиза>" `
  -ReleaseSource "<источник релиза>" `
  -ManifestPublicKeyPath "C:\DenisStock-install\production-manifest-ed25519-public.pem" `
  -ManifestSigningKeyId "production-1" -ConfirmPrimary
```

Установщик останавливается на этом этапе несколько раз: после создания
дистрибутива, после включения systemd, после установки Docker. Каждый раз он
пишет, что сделать дальше. Это нормально, а не ошибка.

### Шаг 3. Установка станции

Та же команда **без** `-InstallWslRuntime` и с созданием заданий:

```
powershell -NoProfile -ExecutionPolicy Bypass -File C:\DenisStock\scripts\operations\Install-DenisStock-EmergencyWorkstation.ps1 `
  -RepoRoot C:\DenisStock -CreateTasks `
  -BackupSource "<источник копий>" -ProductionUrl "https://185-250-44-206.sslip.io" `
  -PrimaryLanAddress "<адрес компьютера в сети склада>" -AppCommit "<полный SHA релиза>" `
  -ReleaseSource "<источник релиза>" `
  -ManifestPublicKeyPath "C:\DenisStock-install\production-manifest-ed25519-public.pem" `
  -ManifestSigningKeyId "production-1" -ConfirmPrimary
```

Установщик спросит probe token: он вводится вслепую и не показывается.

Что происходит: проверяется отпечаток публичного ключа, создаётся или
находится идентификатор станции, создаётся конфигурация с собственными
секретами станции, открывается один порт брандмауэра только для локальной
сети, создаются ярлыки и задание обновления копии.

**Отпечаток ключа сверяется всегда.** Если он не совпал с ожидаемым, установка
останавливается. Это значит, что привезли не тот файл или ключ подменили.
Продолжать нельзя.

Повторный запуск установщика безопасен: идентификатор станции и её секреты
сохраняются, ключ не подменяется, задания и ярлыки создаются заново.

### Шаг 4. Записать идентификатор станции

```
type C:\DenisStock\.emergency\workstation-id.txt
```

Этот идентификатор нужен администратору production. Без него станция копию не
получит.

### Шаг 5. Назначение станции на production

Выполняет администратор **на production**, не на станции:

```
docker compose exec -T web python manage.py authorize_emergency_primary \
  --workstation-id "<идентификатор со шага 4>" \
  --actor "<кто назначает>" \
  --confirm "НАЗНАЧИТЬ-EMERGENCY-PRIMARY"
```

Команда назовёт назначенную станцию и новое значение epoch. Установщик сам
production не меняет никогда.

### Шаг 6. Первое получение копии

На станции:

```
powershell -NoProfile -ExecutionPolicy Bypass -File C:\DenisStock\scripts\operations\DenisStock-Emergency.ps1 -Action Sync
```

Копия скачивается, проверяется подпись закреплённым ключом, сверяется версия
приложения, и только потом standby заменяется. Если проверка не прошла,
прежняя рабочая копия остаётся нетронутой.

### Шаг 7. Проверка готовности

```
powershell -NoProfile -ExecutionPolicy Bypass -File C:\DenisStock\scripts\operations\Test-DenisStockEmergency.ps1
```

Это главная команда: её можно запускать на любом шаге установки, в том числе до
неё. Проверка идёт по слоям снизу вверх, показывает источник копий и свежесть
последней копии, а в конце пишет раздел **«Что делать дальше»** с ровно
следующим шагом. Нужно состояние `ГОТОВО: станция готова к работе.`

Пока станция не установлена, отсутствие её частей помечается как незавершённая
установка, а не как поломка. После каждой перезагрузки достаточно запустить эту
команду, чтобы понять, на чём вы остановились.

### Шаг 8. Проверка со второго компьютера

С другого компьютера в той же сети открыть в браузере:

```
http://<адрес станции>:8080/
```

Должна открыться страница входа. Если не открывается, смотреть слой «Сеть» в
проверке шага 7.

### Шаг 9. Проверка перезагрузки

Перезагрузить компьютер, войти в Windows и повторить шаг 7. Станция обязана
вернуться в состояние готовности **сама** и остаться в режиме ожидания.
Автоматически в автономный режим она не переходит никогда.

### Шаг 10. Учебное отключение

Проводится по [сценарию учения](emergency-local-mode.md) отдельно и не в день
установки.

## 4. Что делать, если пошло не так

| Что случилось | Что делать |
|---|---|
| Проверка: виртуализация выключена | Перезагрузка, BIOS/UEFI, включить Intel VT-x или AMD-V. Без этого установка невозможна |
| Проверка: нет прав администратора | Закрыть окно, открыть PowerShell правой кнопкой «Запуск от имени администратора» |
| Проверка: мало памяти или места | Освободить место либо ставить на другой компьютер. Ниже минимума не ставить |
| Проверка: порт занят | Освободить порт или указать другой параметром `-Port` во всех командах |
| Установщик просит перезагрузку | Перезагрузить и повторить ту же команду. Шаг не потеряется |
| WSL отвечает ошибкой | Выполнить `wsl --update`, затем `wsl --shutdown`, повторить |
| Docker не поднимается | `wsl -d Ubuntu -u root -- systemctl start docker`, затем повторить проверку |
| **Отпечаток ключа не совпал** | **Остановиться.** Взять файл ключа у администратора заново и сверить отпечаток |
| rclone не установлен | Поставить rclone, затем `rclone config` и повторить шаг 1 |
| Источник `yandex-s3` не настроен | Выполнить `rclone config` под тем же пользователем Windows, от которого работает станция |
| Ключ доступа не принят | Проверить ключ учётной записи станции. Ключ production не подходит и применяться не должен |
| Доступ запрещён | У учётной записи станции должно быть право чтения именно этого хранилища |
| Хранилище не найдено | Проверить имя хранилища в источнике копий |
| Хранилище недоступно по сети | Проверить сеть и доступ к storage.yandexcloud.net |
| Часы расходятся с хранилищем | Включить синхронизацию времени Windows |
| Источник доступен, копий нет | Проверить, что production создаёт копии и выгружает их |
| Станция не назначена | Выполнить шаг 5 на production и повторить шаг 6 |
| Подпись копии неверна | Прежняя копия остаётся рабочей. Не трогать её, разбираться с источником копий |
| Копия слишком старая | Выполнить шаг 6. Если источник недоступен, разбираться с ним, а не с копией |
| Версия станции устарела | Обновить станцию до версии production, затем повторить шаг 6 |
| Кончилось место на диске | Освободить, затем `-Action Prune` удалит лишние старые копии |
| Нужно отправить сведения разработчику | `Collect-DenisStockEmergencyDiagnostics.ps1` соберёт архив без секретов |

## 5. Сколько времени занимает

Замеров на настоящем компьютере склада ещё не было, поэтому здесь только
ориентиры, а не обещания:

- проверка компьютера: минуты;
- установка WSL и Docker с нуля: заметно дольше, зависит от скорости сети, и
  требует минимум одной перезагрузки;
- установка станции: быстро, основное время уходит на сборку образа;
- первое получение копии: зависит от размера копии и канала.

Планировать визит стоит с запасом и не на конец рабочего дня: шаг 9 требует
перезагрузки, а шаг 8 - второго компьютера.

## 7. Что остаётся за администратором production

- назначение станции (шаг 5) и отзыв назначения при её замене;
- выдача публичного ключа и его отпечатка;
- выдача probe token;
- решение о переходе в автономный режим и о возврате.

Станция ничего из этого не делает сама.

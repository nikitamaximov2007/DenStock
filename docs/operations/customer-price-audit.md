# Аудит клиентских цен

Как убедиться, что клиенту показывается цена, посчитанная из оптовой цены
каталога, и что делать с расхождениями. Ничего в базе команда не меняет.

## Правило

```
цена клиента ₽ = оптовая цена USD × курс ₽/$ × (1 + наценка % / 100)
```

Итог квантуется до ЦЕЛОГО рубля, ROUND_HALF_UP. Исходные значения не
округляются. При курсе 105 и наценке 40%: 100 $ -> 14 700 ₽.

Реализация одна: `apps/brp/pricing.py` (`customer_price_rub`). Аудит считает
ожидаемую цену тем же кодом, второй формулы в проекте нет.

Что ещё входит в канон:

* **Источник оптовой цены** у BRP и Polaris может быть не сама позиция, а
  связанная по цепочке замен АКТУАЛЬНАЯ позиция с положительной оптовой ценой
  (`find_brp_price_source`, `find_polaris_price_source`). Позиция, выпавшая из
  текущего снимка прайса, источником цены не бывает.
* **Надбавка винтажного склада**: позиции BRP со статусом VIN получают +25 $ к
  оптовой цене до пересчёта. Это правило поставщика, в оптовую цену каталога
  оно не записывается.
* **Каталог аналогов** считается по той же формуле от `dealer_cost_usd` с
  наценкой BRP: своей арифметики у аналогов нет.
* **Курс и наценки** живут в «Настройки» -> «Цены» (`ValuationSettings`,
  `BrpPricingSettings`, `PolarisPricingSettings`).
* **Публичная цена PRO-STOR** это ровно `PartType.recommended_price`
  (`resolve_current_customer_price`). Своей и устаревшей формулы у сайта нет:
  поиск, карточка, корзина, форма заявки и снимок `price_seen` берут одно и то
  же число. Цена, присланная браузером, не авторитетна нигде.

## Проверка

```
python manage.py audit_customer_prices --csv /tmp/prices.csv
```

Команда только читает. Она печатает счётчики по категориям, отдельно по
публичным деталям и отдельно по тем, что есть в наличии, и подробности по
расхождениям; `--csv` выгружает строки целиком. `--rate` и `--markup`
позволяют посчитать сверку по другому курсу или наценке, ничего не сохраняя.

Категории:

| Категория | Значение |
| --- | --- |
| `EXACT_MATCH` | цена ровно та, что даёт формула |
| `ROUNDING_ONLY_MATCH` | расходится не больше рубля, то есть округлением |
| `PRICE_MISMATCH` | расходится больше рубля: это другая цена |
| `MANUAL_OVERRIDE` | цена помечена ручной в снимке связи |
| `WHOLESALE_SOURCE_MISSING` | источника нет: позиция снята с прайса или оптовой цены нет во всей цепочке |
| `SOURCE_INVALID` | источник есть, но оптовая цена не положительная |
| `CUSTOMER_PRICE_MISSING` | оптовая цена есть, а цены у карточки нет |
| `FORMULA_NOT_APPLICABLE` | карточка не связана с каталогом: оптовой цены у неё нет в принципе |

Последние четыре категории это НЕ «неправильная цена». Конвейер в этих случаях
сохраняет прежнюю цену, поэтому такая цена историческая: проверить её нечем, и
решение по ней принимает владелец. Публичный каталог при отсутствии
положительной цены пишет «цена уточняется», а не ноль.

Ручная цена НЕ является постоянным замком: следующий удачный прайс поставщика
её заменяет. Это осознанное правило (`apps/catalog/services.py`), иначе
карточка с однажды вписанной ценой навсегда выпадала бы из переоценки.

## Что делать с расхождениями

1. Посмотреть строку в CSV: источник, оптовую цену, фактическую и ожидаемую
   цену, разницу в рублях и процентах.
2. Если цена расходится, а источник в порядке - выровнять её штатным
   пересчётом. Он по умолчанию dry-run и печатает, сколько цен изменится:

```
python manage.py recalculate_linked_part_prices
```

3. Применять только после того, как владелец согласился с суммами:

```
python manage.py recalculate_linked_part_prices --apply
```

Пересчёт меняет ТОЛЬКО `PartType.recommended_price` и ярлык источника цены у
перекрытых ручных связей. Исторические снимки проведённых документов, склад,
продажи и прайсы он не трогает (проверено сравнением снимка базы до и после).

4. Если расхождение возникло из-за того, что цену вписали руками в карточке
   детали, сумму нужно подтвердить у владельца ДО пересчёта: пересчёт заменит
   её расчётной, и публичная цена изменится.

## Порядок перед запуском PRO-STOR

- [ ] `audit_customer_prices` прогнан на свежем снимке продакшена.
- [ ] `PRICE_MISMATCH` среди публичных деталей В НАЛИЧИИ разобран поштучно.
- [ ] `MANUAL_OVERRIDE` среди публичных деталей в наличии подтверждён
      владельцем: либо цена остаётся (и тогда пересчёт запускать нельзя), либо
      пересчёт применяется и цена становится расчётной.
- [ ] Карточки без каталога (`FORMULA_NOT_APPLICABLE`) с ценой и остатком
      просмотрены: у них цена всегда ручная, формулы для них нет.
- [ ] `recalculate_linked_part_prices` (dry-run) показывает ожидаемое число
      изменений, и оно совпадает с числом из аудита.

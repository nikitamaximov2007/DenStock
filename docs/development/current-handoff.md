# Handoff: финальная приёмка Telegram/MAX и production release

Ветка `codex/prostor-bots-integration`; кодовая база кандидата `8c767d47c3b53f3b0198515634716189fd6de2e0`, последний handoff checkpoint `5c916d0`.
Production не изменялась. Это незавершённая приёмка: deployment не запускать, пока
не закрыты критические живые проверки и не выполнен production pre-backup.

## Завершено

- Обновлены устаревшие ожидания Caddy и Compose в тестах и release qualification.
- Профильный набор Compose/Caddy: 18 passed; Caddy route checker прошёл.
- `ruff check .`, `djlint templates --check`, `manage.py check` и
  `makemigrations --check` прошли.
- Полный pytest: 5 известных baseline failures, 298 skipped; новых регрессий в
  изменённых областях не выявлено. Не называть полный набор зелёным.
- Образы `web`, `telegram-bot`, `max-bot` собраны для SHA `8c767d47...`; текущий
  DEV web и MAX worker работают из образов `c0922c94...`. Изменения `8c767d47`
  относятся к тестам и документации, runtime-код остался от `c0922c94`.
- Владелец подключил свой разрешённый MAX-клиент к искусственной DEV-заявке №1.
  DEV webhook сохранил одно сообщение `DEV MAX сообщение после привязки 18.11`
  с внешним ID в правильной связанной переписке. Автор совпадает с активной
  привязкой MAX.
- Владелец подтвердил, что веб-ответ `DEV MAX ответ из веб-интерфейса 18.11`
  показан в разрешённом MAX-диалоге ровно один раз. В DEV он сохранён со статусом
  `sent` и внешним ID. После перезапуска MAX worker обе записи остались по одной,
  worker восстановил healthy heartbeat; свежих ошибок в логах нет.
- Из ранее согласованного фото DEV-заявки №2 отправлен один ответ `Тестовое фото
  DEV RC` в ту же связанную заявку №1. DEV запись имеет вложение в
  `PrivateAttachmentStorage`, статус `sent` и внешний ID. После второго
  перезапуска MAX worker сообщение осталось единственным, ошибок нет. Ждём
  визуального подтверждения владельца и реальное входящее фото.
- DEV использует БД `denstock_rc`; MAX webhook включён; operator console и
  introductions выключены; активных тестовых привязок сотрудников нет.
- Временный sidecar для проверки introductions остановлен и удалён; его тома
  не затрагивались. Основные DEV-контейнеры продолжают работать.
- Production и Telegram production не изменялись.

## Не завершено / блокеры

- Требуется визуальное подтверждение доставки исходящей фотографии в MAX и
  реальное входящее фото от владельца для проверки его сохранения в заявке.
- В текущем DEV operator flags выключены. Поскольку тестовых привязок Дениса,
  Рима и независимого второго MAX-клиента нет, не проверены персональные
  подписи, однократное представление оператора и изоляция двух клиентских
  диалогов на этом кандидате. Не создавать привязки к чужим аккаунтам и не
  выдавать фиктивные identities за Дениса или Рима.
- Фото в обе стороны, старые/новые кнопки и полный перезапуск с подтверждённым
  реальным повторным webhook delivery на текущем candidate DEV ещё не пройдены.
- Полный production release заблокирован обязательными незавершёнными live
  сценариями. Не делать PRE-backup и deployment до закрытия gate.
- `release_image_identity.py verify` из worktree не проходит из-за отсутствующего
  локального runtime `.env`; не создавать его из production secrets. Ранее
  `build` успешно выдал image identity attestations для SHA `8c767d47...`.

## Следующие шаги

1. Получить ответ владельца: отображается ли `DEV MAX ответ из веб-интерфейса
   18.11` ровно один раз в разрешённом личном MAX-диалоге.
2. Владелец уже попросил самостоятельно выполнить доступные проверки и получил
   запрос прислать одну фотографию в тот же DEV-диалог; после ответа проверить
   attachment в заявке №1, приватное
   хранение, внешний ID и отсутствие дублей.
3. Для исходящего фото использовать только ранее согласованное тестовое
   изображение в этой же заявке/диалоге; дождаться фактического подтверждения
   владельца.
4. Запросить независимый второй тестовый MAX-аккаунт для проверки разделения
   диалогов. Для персональных подписей попросить Дениса и Рима лично выполнить
   привязку своих подтверждённых MAX identities в DEV.
5. Включать `CUSTOMER_OPERATOR_CONSOLE_ENABLED` и
   `CUSTOMER_STAFF_INTRODUCTIONS_ENABLED` только по существующей инструкции
   `docs/development/operator-console-activation.md`, после готовности реальных
   привязок. Не подменять identities.
6. Завершить старые/новые кнопки, историю, текст/фото и duplicate checks; затем
   повторить целевые тесты, полный набор, static checks и image verification для
   конечного SHA.
7. Только после закрытия всех критических гейтов провести свежий проверенный
   PRE-backup и последовательный production rollout по
   `docs/operations/production-deploy-runbook.md`, сохранив rollback.

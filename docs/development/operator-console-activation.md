# Панель администратора PRO-STORE: controlled activation

Код и миграции могут быть заранее размещены в production только с выключенной
переменной `CUSTOMER_OPERATOR_CONSOLE_ENABLED=false`. Эта инструкция включает
консоль отдельно. До включения нужен независимый review и подтверждение
владельца на controlled live acceptance.

## Перед включением

1. Убедитесь, что production использует согласованный commit и нет другого
   production writer.
2. Создайте и полностью проверьте signed PRE-ACTIVATION backup, включая
   offsite upload и `rclone check` без различий.
3. Откройте в DenisStock `/customer-requests/staff-bindings/` под администратором.
   Эта страница не добавляется в обычное меню.
4. Для новых привязок владельца выберите существующего внутреннего
   пользователя, укажите видимую клиенту подпись и создайте одноразовый код.
   Не перевыпускайте и не перепривязывайте уже действующие Telegram/MAX
   identity Дениса и Рима. Не сохраняйте код в чате или документации: передайте
   его владельцу в утверждённом приватном канале.
5. Владелец отправляет полученный код соответствующему боту. В админской
   странице убедитесь, что привязка появилась и активна. При необходимости
   повторите для второго канала. Не используйте username, отображаемое имя или
   номер телефона вместо завершённой provider-identity привязки.
6. Выполните `python manage.py check_operator_console_readiness`. Команда
   ничего не изменяет, не показывает секреты и не выводит полный provider ID.
   Исправьте только указанные критичные блокеры; истёкшие неиспользованные
   коды можно штатно отозвать.

## Включение и controlled acceptance

1. Установите только `CUSTOMER_OPERATOR_CONSOLE_ENABLED=true`. Остальные
   customer-account и customer-cabinet флаги меняются лишь по отдельному
   утверждённому плану.
2. Перезапустите только `web`, `telegram-bot` и `max-bot` штатной production
   compose-процедурой. Убедитесь, что все healthchecks зелёные. Перезапуск сам
   по себе не отправляет панель и не создаёт операторский контекст.
3. Для явно подтверждённой административной Telegram identity NIKITA сначала
   выполните отдельную fail-closed команду:

   ```
   docker compose exec web python manage.py activate_telegram_admin_identity \
     --provider-user-id <AUTHORIZED_ID> --username admin --confirm
   ```

   Команда не использует pairing code, не создаёт нового пользователя и не
   принимает username Telegram как авторизацию. После этого в отдельном шаге
   активации поставьте панели в durable-очередь:

   ```
   docker compose exec web python manage.py send_owner_console_panel
   ```

   По умолчанию команда затрагивает только активные привязки Дениса и Рима.
   Для одной административной панели используйте `--operator-key NIKITA`.
   Команда не отправляет клиентам и не создаёт заявки. Telegram и MAX доставляют очередь каждый своим
   bot-worker, поэтому секреты не появляются в `web`. Для Telegram доставка
   панели сначала удаляет устаревшую customer reply-клавиатуру, затем показывает
   внутреннюю inline-панель. Повторный запуск без
   `--refresh` не дублирует уже поставленную панель; если панель была удалена,
   используйте `--refresh`.
4. Создайте одну явно помеченную синтетическую заявку, принадлежащую тестовым
   messenger-аккаунтам, а не реальному клиенту. Проверьте рабочее меню,
   уведомление о новой заявке, открытие заявки и автора ответа.
5. Минимальная живая матрица: Telegram-владелец → Telegram-тестовый клиент;
   Telegram-владелец → MAX-тестовый клиент; MAX-владелец → Telegram-тестовый
   клиент; MAX-владелец → MAX-тестовый клиент. Для каждого доступного
   направления проверьте текст, изображение и PDF, terminal delivery status,
   realtime history и отсутствие дублей. Если независимых тестовых аккаунтов
   недостаточно, два направления должны быть проверены живьём, а оставшиеся
   только после документированной автоматизированной проверки и решения
   владельца.
6. Проверьте, что владелец не может открыть чужой контекст, customer callback
   не принимается как operator callback, а web workspace продолжает работать.
7. После успешного controlled acceptance создайте и полностью проверьте signed
   POST-ACTIVATION backup.

## Немедленный rollback

Установите `CUSTOMER_OPERATOR_CONSOLE_ENABLED=false` и штатно перезапустите
только `web`, `telegram-bot` и `max-bot`. Это сразу убирает operator behavior,
не удаляя исторические сообщения, заявки или существующие привязки. Затем
зафиксируйте время и причину rollback в операционном журнале.

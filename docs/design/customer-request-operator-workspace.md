# Рабочее место оператора по заявкам клиентов (Release A)

Задача релиза: «Заявки клиентов» отвечают на вопрос «чем заняться прямо
сейчас», а сотрудник отвечает клиенту из DenisStock и из бота сотрудников —
одинаково для MAX и Telegram.

## 1. «Ждёт ответа» — вычисляемое состояние

Ничего не хранится: состояние читается из истории сообщений
(`apps/customer_requests/workspace.py`). Заявка ждёт ответа, когда выполнено
всё сразу:

1. заявка открыта (`new` или `in_progress`). Закрытая заявка не ждёт никого:
   клиент в неё уже не пишет (Stage 0), это история;
2. клиент написал хотя бы одно сообщение (`customer_to_operator`) — в любом из
   мессенджеров;
3. после последнего сообщения клиента нет **доставленного** ответа сотрудника:
   сообщения `operator_to_customer` со статусом `sent`, созданного позже.

Дополнительно к состоянию показывается его причина:

| Что произошло после последнего сообщения клиента | Метка | Ждёт ответа |
|---|---|---|
| ничего | «Ждёт ответа» | да |
| ответ в очереди или отправляется (`pending`, `sending`) | «Ответ отправляется» | да |
| мессенджер отказал (`failed`) или судьба неизвестна (`uncertain`) | «Ответ не доставлен» | да |
| ответ доставлен (`sent`) | нет метки | нет |

Почему так:

* **только доставленный ответ закрывает ожидание.** Недоставленный или
  неопределённый ответ клиент мог не увидеть никогда — считать заявку
  отвеченной значит потерять клиента молча;
* **сообщения бота не считаются ответом.** Сводка заказа, подтверждение приёма
  сообщения и выбор заявки — это `system`, а не работа сотрудника;
* **сравниваются времена создания.** Клиент, написавший снова, пока ответ ещё
  в пути, снова ждёт — как только тот ответ уйдёт, ожидание снимет уже
  следующий ответ;
* ручного состояния «ответил по телефону» в этом релизе нет — решение
  владельца.

## 2. Порядок по умолчанию

`workspace.order_by_priority`: 1) ждут ответа, дольше всех ждущий первым;
2) новые; 3) в работе; 4) завершённые и отменённые. Внутри пунктов 2–4 —
по последней активности, сверху свежие. Статусы берутся только те, что есть у
`CustomerRequest`.

## 3. Фильтры и поиск

Вкладки: активные (по умолчанию), ждут ответа, новые, завершённые, отменённые,
все — со счётчиками. Отдельно переключатель мессенджера (все / MAX / Telegram).
Выбранные фильтры едут в карточку и обратно, в том числе после ответа и смены
статуса.

Поиск (`workspace.search_filter`) — по номеру заявки, имени, телефону
(нормализованная колонка) и по артикулу/названию позиции (от трёх символов).
Регистр кириллицы не сворачивает ни SQLite, ни PostgreSQL в локали C (см.
`apps/core/part_lookup`), поэтому сравниваются несколько написаний строки
вместо `icontains`; отдельная сложенная колонка ради этого не вводится.

## 4. Один ответ для обоих мессенджеров

`apps/customer_requests/operator_replies.py` — единственное место, где
рождается ответ сотрудника, откуда бы он ни пришёл (карточка DenisStock или
бот сотрудников):

* мессенджер выбирается по самой заявке (`reply_target`), а не страницей;
* ответ уходит только в заявку, в которую клиенту ещё можно писать: открытый
  статус, согласие не отозвано, мессенджер подключён. Решает состояние сервера,
  а не возраст кнопки;
* автор — реальный пользователь DenisStock (`operator_user`), клиенту он
  никогда не виден: клиент получает сообщение от бота PRO-STOR;
* идемпотентность: строка заявки блокируется, повторная отправка находит уже
  сохранённый ответ. Ключ формы — свежие 32 hex-символа на каждый рендер,
  ответ из бота опознаётся по своему `update_id`.

## 5. Бот сотрудников

`apps/customer_requests/operator_bot.py` рисует одинаковые уведомления для
обоих мессенджеров: номер заявки, мессенджер, клиент, текст сообщения и кнопки
[Ответить] [Открыть заявку] [Активные заявки]. [Ответить] не показывается,
когда отвечать нельзя (закрыта, нет согласия, клиент не подключён) — кнопка,
ведущая в тупик, хуже её отсутствия.

Режим ответа — единственное состояние бота: `TelegramOperator.reply_request`.
Его меняет только собственное нажатие [Ответить] этим сотрудником. Уведомления,
списки и карточки его не трогают, поэтому сообщение по заявке B, пришедшее пока
сотрудник отвечает по A, ничего не переключает. После отправки режим
заканчивается: следующее сообщение требует нового явного [Ответить].

Кнопки, отправленные до этого релиза, называют переписку Telegram, а не заявку;
`operator_bot.request_by_hex` открывает по ним ту же заявку.

## 6. Миграция

`0010_operator_workspace` — только добавления:

* `TelegramOperator.reply_request` — заявка, на которую отвечает сотрудник
  (прежнее `reply_conversation` остаётся нетронутым, чтобы предыдущий релиз
  запускался на этой же схеме; режим ответа переносится данными);
* `TelegramMessage.dedupe_key` с условным уникальным индексом — одна отправка
  формы DenisStock даёт ровно один ответ в Telegram, как это уже сделано в
  `MaxMessage`.

Публичной роли БД ни одна из этих таблиц не выдана, новых прав релиз не
добавляет.

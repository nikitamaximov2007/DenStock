# MAX для заявок клиентов

MAX — второй мессенджер PRO-STOR рядом с Telegram. Источник истины остаётся в
DenisStock: `CustomerRequest` и её позиции, а мессенджер только переносит
сообщения. MAX не становится второй базой заказов.

## Проверенный контракт официального API

Проверено по официальным источникам MAX (`https://dev.max.ru/`, раздел
`/docs-api`, `/help/deeplinks`, `/docs/chatbots/bots-coding/prepare`) и по
клиентским библиотекам самой MAX (`github.com/max-messenger/max-bot-api-client-go`,
`github.com/max-messenger/max-botapi-python`). Там, где официальные документы
расходятся с прежним текстом этого файла, побеждают официальные документы.

| Контракт | Значение |
| --- | --- |
| Хост API | `https://platform-api2.max.ru` |
| Аутентификация | заголовок `Authorization: <token>` (не query-параметр) |
| Личность бота | `GET /me` → `user_id`, `first_name`, `username`, `is_bot`, `commands`; неверный токен → `401` |
| Отправка текста | `POST /messages?user_id=…` или `?chat_id=…`, тело `{"text": …, "format": …, "notify": …}` |
| Предел текста | 4000 символов (совпадает с нынешним `MAX_MESSAGE_CHARS`) |
| Ограничения | 30 rps на хост; не более 2 сообщений в секунду в один диалог |
| Продакшн-транспорт | только webhook: «Для production-окружения — только Webhook»; long polling — для разработки |
| Подписка | `POST /subscriptions` `{url, update_types, secret}`; удаление `DELETE /subscriptions`; список `GET /subscriptions` |
| Требования к URL | только HTTPS, порт 443, доверенный сертификат (или Минцифры); самоподписанные отклоняются |
| Проверка webhook | секрет 5–256 символов `[a-zA-Z0-9_-]`, приходит в заголовке `X-Max-Bot-Api-Secret` |
| Ответ webhook | HTTP 200 в течение 30 секунд |
| Взаимоисключение | при активной подписке long polling не работает |
| Deep-link | `https://max.ru/<botName>?start=<payload>`, payload до 128 символов |
| Никнейм бота | генерируется платформой (`idИНН_bot` / `se(orgid)_bot`), выбрать нельзя |
| События | `bot_started`, `bot_stopped`, `message_created`, `message_callback`, `message_edited`, `message_removed`, `bot_added`, `bot_removed`, `user_added`, `user_removed`, `dialog_*`, `chat_title_changed`, `comment_*` |
| Базовое обновление | `update_type`, `timestamp` — **отдельного идентификатора обновления нет** |
| `bot_started` | `chat_id`, `user`, `user_locale`, `payload` — payload deep-link |
| `message_created` | `message` (`sender.user_id`, `recipient.chat_id`, `recipient.chat_type`, `body.mid`, `body.seq`, `body.text`), `user_locale` |
| Идентичность сообщения | `body.mid` — строковый уникальный идентификатор; `body.seq` — порядковый номер в чате |

### Что из этого следует для нас

* **Токен не попадает в URL.** В отличие от Telegram, MAX принимает токен
  заголовком, поэтому он не окажется ни в логах прокси, ни в строке запроса.
* **Дедупликация входящих строится на `body.mid`.** У MAX нет аналога
  `update_id`, поэтому общий слой хранит внешний идентификатор сообщения
  строкой, а не целым числом, как это делает Telegram сегодня.
* **Payload помещается без ослабления модели.** Нынешний
  `secrets.token_urlsafe(32)` даёт 43 символа при лимите 128, поэтому
  доказанная Telegram-схема одноразовых ссылок переносится без изменений.
* **Транспорты разные по природе.** Telegram остаётся на long polling с
  единственным потребителем и advisory-lock, MAX обязан работать через
  webhook. Общим остаётся бизнес-слой, а не способ доставки обновлений.

## Возвращающийся клиент

`BotStarted` описан самой MAX как «обновление, сигнализирующее о **первом**
старте бота». Повторный переход по deep-link в уже существующий диалог
приходит как `message_created` с командой, а не как `bot_started` с payload,
ровно тот же край, который мы уже видели в Telegram в продакшне.

Поэтому привязка второй и последующих заявок не опирается на `bot_started`:

1. первый старт привязывает заявку по `payload` из `bot_started`;
2. ссылка следующей заявки, открытая в уже существующем диалоге, приходит
   сообщением `/start <payload>` и привязывает заявку тем же одноразовым
   токеном к тому же пользователю MAX, без второго аккаунта;
3. дальше клиент выбирает заявку кнопками (`message_callback`), `/requests`
   показывает их снова;
4. при единственной заявке сообщение уходит в неё без вопросов, при
   нескольких без активного выбора бот просит выбрать и ничего не сохраняет.

Что именно MAX присылает при повторном переходе по ссылке в существующий
диалог, проверяется на настоящем MAX в Stage C (см. ниже).

### Наблюдение на production (2026-09-17, выпуск `aa63ab8`)

Формулировка документации MAX выше осталась прежней. Выше записана и наша
тогдашняя трактовка; её не переписываем. Ниже то, что показал настоящий MAX с
одним аккаунтом клиента и двумя тестовыми заявками A и B:

* **Ссылка новой заявки доставила payload в уже существующий диалог.** Токен
  заявки B использован через 8 секунд после создания, B стала текущей, и
  клиенту автоматически ушла её собственная сводка из неизменяемых строк
  заявки. Второй аккаунт MAX не понадобился.
* **Каким типом события это пришло** (`bot_started` или `message_created` с
  `/start <payload>`), по сохранённым данным не различить: обработаны оба пути,
  а тип обновления не записывается. Утверждать одно из двух без журнала нельзя.
* **Один пользователь MAX, несколько заявок.** Переписки A и B связаны с одним
  и тем же пользователем и одним диалогом MAX при одной строке текущего выбора.
* **Маршрутизация без перекрёстных ошибок.** Сообщение после выбора B ушло
  только в B, после выбора A только в A.
* **Подтверждение по заявке.** B получила своё первое подтверждение; следующее
  сообщение в A подтверждения не получило, потому что A уже подтверждена.

Итого: «повторный клиент без второго аккаунта» на MAX выполняется и привязкой
по новой ссылке, и выбором заявки кнопками. Оба пути остаются в коде.

## Безопасность ссылки

Модель одноразовой ссылки общая с Telegram и не ослабляется: высокоэнтропийный
непрозрачный payload, привязка к конкретной заявке, ограниченный срок, одно
использование, хранение только SHA-256, блокировка строки при разборе, отзыв
оставшихся неиспользованных ссылок после успешной привязки, ограниченное число
повторов и отсутствие сырого токена в HTML, cookie и сессии.

## Что остаётся за пределами кода

Реальный токен бота устанавливается только на проде отдельной защищённой
процедурой (root, режим 600, не в Git, не в общий `.env`). Ни один тест и ни
один локальный прогон не использует настоящий токен: для них есть фальшивый
MAX-транспорт.

### Хранение

Таблицы Telegram не переименовываются и не мигрируются. У MAX свои строки:

* `MaxConversation`: одна на заявку; числовой пользователь MAX (идентичность
  безопасности) и диалог (куда отправлять); в состоянии «подключён» оба
  обязательны (ограничение в базе).
* `MaxCustomerChat`: один на пользователя MAX; активная заявка для обычных
  сообщений.
* `MaxMessage`: сообщения клиента, сотрудника и бота; статус доставки
  `received / pending / sending / sent / failed / uncertain`.
* `MaxOutboxEvent` и `MaxOperatorDelivery`: уведомления сотрудникам; получатель
  это пользователь DenisStock, а не чей-то аккаунт в мессенджере.
* `operations.MaxBotRuntime`: аренда и heartbeat воркера, вне бизнес-приложений.

Миграции `customer_requests.0008`, `0009` и `operations.0006` только добавляют
и полностью откатываются (проверено на SQLite и PostgreSQL 16).

### Идентичность событий и защита от повторов

У MAX нет идентификатора обновления. Каждое действие поэтому несёт свою
идентичность, и повторная доставка webhook находит уже сделанное:

| Событие | Правило |
| --- | --- |
| Сообщение клиента | уникально по `body.mid` целиком (до 512 символов; длиннее отвергается, никогда не обрезается); проверка под блокировкой строки пользователя |
| `bot_started` с payload | токен одноразовый; повтор старта того же токена тем же пользователем распознаётся по состоянию (токен использован, заявка связана с этим пользователем) и остаётся без ответа |
| Сводка | `summary:<id токена>:<n>` |
| Подтверждение | `ack:<переписка>`: не больше одного на заявку |
| Ответ на сообщение | `reply:<mid>` |
| Нажатие кнопки | `callback:<хеш callback_id, пользователя, payload и времени нажатия>`. MAX называет `callback_id` идентификатором клавиатуры, два нажатия на одной клавиатуре могут его разделять. На production (2026-09-17) два нажатия одной и той же кнопки дали **разные** `callback_id` длиной 116 символов; хеш нажатия остаётся ключом, потому что официальный контракт уникальности не обещает |
| Прочий `bot_started` | `start:<хеш типа, пользователя, диалога, времени и хеша payload>`; сырой payload не хранится |
| Ответ сотрудника | `operator_reply:<ключ формы>`: двойной клик не отправляет дважды |

### Webhook

`POST /customer-requests/max/webhook/` во внутреннем `web`. Секрет из
`X-Max-Bot-Api-Secret` сравнивается за постоянное время; неверный, пустой,
неправильного формата секрет или выключенный webhook дают 404. Тело больше
64 КБ или не JSON-объект с `update_type` дают 400. Любое принятое обновление
отвечает одинаково `{"ok": true}`, поэтому webhook ничего не сообщает о
заявках. Ошибка базы даёт 503 и MAX доставит снова (всё идемпотентно); одно
«ядовитое» обновление записывается в журнал только типом ошибки и
отбрасывается. Тело, текст клиента, секрет и токен в журнал не попадают.

### Отправка

`manage.py run_max_bot` работает в одном экземпляре (advisory lock
PostgreSQL и аренда). Строка помечается `sending` до вызова API.

| Ответ MAX | Что происходит |
| --- | --- |
| 200 с `message.body.mid` | `sent`, `mid` сохраняется |
| 400 и прочие 4xx | `failed` сразу |
| 401 | воркер останавливается, строка возвращается в очередь без попытки |
| 429 | повтор после `Retry-After` (1..3600 с) или 1 с; все вызовы ждут, не только отказанный |
| 500, 503 | повтор с растущей паузой до 900 с, не больше 8 попыток |
| отказ соединения | повтор, ничего не ушло |
| тайм-аут после отправки, 502/504, оборванное соединение, 200 без `mid` | `uncertain`, **никогда не отправляется повторно** |

Более позднее сообщение в том же диалоге не обгоняет сообщение, ждущее
повтора, и ждёт вместе с ним. Лимиты MAX соблюдаются с запасом: не чаще
одного сообщения в 0,55 с в диалог и 25 вызовов в секунду всего.

### Сотрудники

Ответ клиенту пишется в DenisStock, в карточке заявки («Ответ клиенту в
MAX»). Сообщение хранит пользователя DenisStock и уходит от имени бота
PRO-STOR; личный аккаунт сотрудника в MAX не нужен и клиенту не виден.
Уведомления о событиях MAX приходят сотрудникам через уже работающий
бот сотрудников (`telegram-bot`) с кнопкой «Открыть заявку». Событие ответа,
которое некому показать, кроме автора, завершается без строк доставки, как и
в Telegram (общее правило `messaging.operator_event_outcome`).

### Публичная передача

Кнопка «Продолжить в MAX» отправляет POST с CSRF на свой адрес, который
выпускает одну ссылку и отвечает 303 на `https://max.ru/<bot>?start=<token>`.
Сырой токен есть только в заголовке `Location`. Страница успеха добавляет в
`form-action` ровно источник мессенджера этой заявки и только пока передача
предлагается; остальные страницы остаются с `form-action 'self'`. Ссылок на
заявку не больше трёх (сессия и триггер базы). Публичная роль базы вставляет
только токен ссылки `max` со своим доказательством и не имеет прав ни на одну
таблицу MAX.

### Разделение сервисов (упаковано в Stage C0)

| Сервис | Получает | Не получает |
| --- | --- | --- |
| `catalog-web` | `MAX_BOT_USERNAME` из `.env.public` | токен и секрет webhook: пусто в compose и в `config/settings/public.py` |
| `web` | `.env.max-webhook`: `MAX_WEBHOOK_ENABLED`, `MAX_WEBHOOK_SECRET` | `MAX_BOT_TOKEN`: пусто в compose (приёму webhook API не нужен) |
| `max-bot` (сервис с профилем, `run_max_bot`) | `.env.max`: `MAX_BOT_TOKEN`, `MAX_PUBLIC_WEBHOOK_URL`, `MAX_API_CA_FILE`, `MAX_API_CA_SHA256`; сертификат из `/etc/denstock/max` только для чтения | секрет webhook, токен Telegram, прокси |
| разовый `max_webhook subscribe --confirm` | запуск в контейнере `max-bot` с файлом секрета web, смонтированным только на эту команду | выполняется вручную и сразу завершается |
| `telegram-bot` | без новых переменных; токен и секрет MAX пусты | доставляет сотрудникам уведомления о MAX, поэтому выкатывается тем же выпуском |

Кнопку «Открыть заявку» в уведомлениях о MAX строит `telegram-bot` из своего
`TELEGRAM_INTERNAL_BASE_URL`; `max-bot` этот адрес не нужен.

### Сертификат API MAX

Проверка с production (Stage C0): `platform-api2.max.ru` доступен напрямую,
но сертификат выдан «Russian Trusted Sub CA», корень «Russian Trusted Root CA»
Министерства цифрового развития, которого нет в стандартных хранилищах. Клиент
MAX доверяет ровно файлу `MAX_API_CA_FILE` с закреплённым SHA-256; проверка
не отключается, системное хранилище и остальные клиенты не меняются,
переменные окружения прокси клиентом не читаются.

### Публичный маршрут webhook

Production обслуживает не Caddyfile из репозитория, а
`/etc/denstock/caddy/Caddyfile` (подключается неотслеживаемым overlay).
Его точная копия лежит в `deploy/caddy/Caddyfile.production.pre-max`,
кандидат в `deploy/caddy/Caddyfile.production`: на `pro-brp.ru` в `web` уходит
только `POST /customer-requests/max/webhook/` (тело до 64 КБ, `Host` web),
всё остальное по-прежнему в `catalog-web`. MAX подписывается на
`https://pro-brp.ru/customer-requests/max/webhook/` (порт 443, сертификат
Let's Encrypt этого хоста).

### Известное ограничение (найдено после выпуска)

Отмена или завершение заявки не закрывают её переписку: `change_request_status`
меняет только заявку, а выбор и запись сообщений клиента (`linked_conversations`,
`record_customer_message`, в Telegram так же) проверяют состояние переписки и
согласие, но не статус заявки. Поэтому отменённая или выполненная заявка
остаётся доступной для выбора и принимает новые сообщения клиента, которые
уходят сотрудникам. История не страдает; исправление запланировано отдельным
выпуском.

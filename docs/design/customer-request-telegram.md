# Telegram для заявок клиентов (V1: переписка через бота)

DenisStock остаётся единственным источником истины о заявке. Telegram не
хранит заказов: он добавляет идентичность чата клиента, историю переписки,
уведомления сотрудникам и доставку сообщений. Эксплуатация:
[docs/operations/telegram-bot.md](../operations/telegram-bot.md).

## Поток

1. Клиент отправляет заявку с «Telegram». В той же транзакции, что и заявка,
   создаются `TelegramConversation` (ожидает подключения),
   `TelegramOutboxEvent new_request` и одноразовая ссылка
   (`CustomerRequestMessengerLinkToken`, только SHA-256). Сети в этой
   транзакции нет: заявка не зависит от Telegram.
2. Страница успеха показывает «Продолжить в Telegram» с
   `https://t.me/<bot>?start=<token>`. Сырой токен есть только в подписанной
   cookie браузера клиента. Если имя бота не настроено, страница говорит, что
   Telegram недоступен, а заявка сохранена.
3. Клиент нажимает «Запустить». Бот (long polling) передаёт `/start <token>` в
   `consume_messenger_start`: строка токена блокируется, проверяется срок,
   использование, отзыв и отмена заявки, затем чат привязывается к переписке по
   числовому ID. Клиенту уходит подтверждение, сотрудникам событие
   `customer_linked`.
4. Текст клиента сохраняется в активную переписку его чата и рассылается
   сотрудникам. Сотрудник нажимает «Ответить», следующий его текст сохраняется
   как сообщение клиенту и доставляется ботом.

## Модели

- `TelegramConversation`: одна на заявку; `public_id` для кнопок, числовые
  chat/user ID клиента, снимок username только для показа.
- `TelegramCustomerChat`: какая из заявок чата получает следующее сообщение.
- `TelegramOperator`: пользователь DenisStock, числовой Telegram ID (уникален),
  роль, активность, состояние «отвечает на заявку».
- `TelegramMessage`: история; `telegram_update_id` уникален; для исходящих
  статус доставки, попытки, следующая попытка, последняя ошибка.
- `TelegramOutboxEvent`: событие для сотрудников с уникальным `dedupe_key`.
- `TelegramDelivery`: копия события одному сотруднику, уникальна по паре.
- `operations.TelegramBotRuntime`: смещение обновлений, аренда, сигнал жизни.
  Это не бизнес-данные: пульс бота не меняет business generation и отпечаток
  бэкапа.

`CustomerRequestMessengerContact` сохраняется для совместимости; ограничение
«один чат на одну заявку» снято, так как у клиента может быть несколько заявок.

## Гарантии

- Обновление и его номер фиксируются одной транзакцией.
- Сообщение клиенту отправляется не более одного раза: перед сетевым вызовом
  строка фиксируется как `sending`; после рестарта такие строки становятся
  `uncertain`, а не отправляются снова.
- Повторяются только однозначные отказы (сеть до отправки, 429, 5xx), с паузой
  до 15 минут и не более 8 попыток. 4xx становится `failed`.
- Один потребитель: advisory lock PostgreSQL, аренда в базе, ответ Telegram 409,
  отказ запуска при настроенном webhook.
- Авторизация сотрудника проверяется на каждом обновлении и каждой кнопке
  (активен оператор, активен пользователь, есть доступ к заявкам). Данные кнопок
  непрозрачны (`c:<uuid hex>`), проверяются на сервере. Клиент может выбрать
  только переписку, привязанную к его же чату.
- Отзыв согласия запрещает ответы и доставку клиенту; обезличивание стирает
  тексты переписки и идентичность чата.
- Токен бота есть только в окружении сервиса `telegram-bot`; публичный процесс
  его обнуляет; журналы вычищают строки вида токена.

## Webhook

Прежний endpoint `customer-requests/telegram/webhook/` сохранён для
совместимости и по умолчанию закрыт (нет секрета). V1 использует long polling:
новый публичный маршрут для Telegram не нужен.

## Вне V1

Фото и файлы клиентов: нужны приватное хранилище, лимиты размера и типов,
проверка содержимого и сроки хранения. Смена статуса заявки из бота не
делается: V1 только для общения.

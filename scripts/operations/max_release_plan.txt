MAX + Telegram release plan (production base {base}, candidate {candidate})
Every step stops on failure. No production mutation until all GO gates pass.
Commands run as root in /opt/denstock. Do not build on the production VPS.

A. Read-only gates
  1. Ensure the exact candidate commit is available to the release host and has
     production base {base} in its history. The initial RC c0922c94 is not the
     final SHA: production Turkey reverse-SSH egress fixes must be retained.
  2. python3 R preflight --expect-head {base} --candidate {candidate}
  3. docker compose exec -T web python manage.py shell < scripts/operations/release_baseline.py > /root/bots-before.txt
  4. `runtime_sha` is the running web image SHA, not repository HEAD. For this
     release it is 01a0b7eb4fb79b25bc6cbc7ae87ce4da8eb1bad6. Verify its image
     identity/source, then set PRE_APP_SHA to that verified value. Record each
     service image ID/selector separately; confirm no active writer/backup and
     MAX uncertain records remain untouched.
  5. Read-only: verify PostgreSQL, Caddy, Turkey reverse SSH, Telegram API
     getMe, MAX identity/getMe and `max_webhook status --require-subscribed`.
     Keep the existing production MAX token, webhook secret, CA, callback URL
     {PUBLIC_WEBHOOK_URL} and subscription. Do not rotate or re-register them.

B. Signed PRE backup: no rollout without all gates passing
  6. Verify the running web source against PRE_APP_SHA; do not substitute the
     repository checkout HEAD {base} or infer source from an unattested label.
  7. Under /run/lock/denstock-backup.lock run
     `docker compose exec -T -e DENSTOCK_APP_COMMIT="$PRE_APP_SHA" web python manage.py backup_all`
     without retention/pruning options.
  8. Verify the signature, manifest `app_commit=PRE_APP_SHA`, all hashes, DB/public/private
     media, isolated restore, and approved offsite upload/read-back of this
     exact run ID. Stop on any failure or insufficient disk.

C. Build and transfer
  9. After PRE is verified, `git checkout --detach {candidate}`; verify clean
     tree and release tooling.
 10. Build only the approved images on the build host, linux/amd64, using
     `release_image_identity.py build --sha {candidate} --services web,telegram-bot,max-bot`.
     Add catalog-web only if explicitly included in the approved component scope:
     the new public “Continue in MAX” button is served by catalog-web.
 11. Preserve old image IDs/tags. Transfer archives, verify archive SHA-256,
     load images and compare immutable image IDs, OCI revisions, source digest
     and embedded SHA before changing selectors.

D. Schema and bounded service rollout
 12. Read-only `migrate --plan`; proceed only if the entire pending plan is
     exactly customer_requests.0029 and .0030. Both are additive/compatible;
     do not run reverse migrations or broader deployment.
 13. Change only approved DENSTOCK_<SERVICE>_REVISION selectors. Keep the
     production Telegram proxy, Telegram offset, MAX secrets, webhook
     subscription, Caddyfile, database volumes and Turkey egress untouched.
 14. Run `release_image_identity.py verify --sha {candidate} --services
     web,telegram-bot,max-bot` before starting services. Start web first; its
     normal entrypoint applies only the verified pending migrations. Run
     `docker compose up -d --no-build --no-deps --wait web`; wait healthy and
     verify runtime identity.
 15. Replace telegram-bot with `docker compose --profile telegram-bot up -d
     --no-build --no-deps --wait telegram-bot`. Ensure the old polling process stopped,
     then verify one worker, heartbeat and read-only Telegram getMe through
     the existing Turkey proxy.
 16. Replace max-bot with `docker compose --profile max-bot up -d --no-build
     --no-deps --wait max-bot`. Verify runtime identity, `max_bot_health`, lease/heartbeat, API identity,
     `max_webhook status --require-subscribed`, and existing callback path.
     Never retry historical uncertain messages or send a production test.
 17. If catalog-web was approved, change only its selector, start it alone,
     and verify the runtime identity and public MAX handoff. Otherwise leave its
     image and configuration unchanged; public catalog MAX handoff remains out
     of this release.
 18. Run `R verify --candidate {candidate} --services web,telegram-bot,max-bot`
     (add catalog-web only if included); compare `/root/bots-before.txt` with a
     new read-only baseline. Only the release SHA, runtime SHA and migration
     count may differ. Check queues, uncertain records, errors, OOM, disk, RAM
     and every unrelated service.

E. Post-release evidence
 19. Without messaging customers, verify web/DB/catalog health, one Telegram
     poller and heartbeat, MAX webhook/API/heartbeat, unchanged Turkey egress,
     stable queue counts, no duplicate IDs and no new errors/OOM.
 20. After successful checks, create a signed POST backup using the same lock
     with `DENSTOCK_APP_COMMIT={candidate}`; verify and upload/read back without
     pruning. Preserve the PRE backup and rollback images.

ROLLBACK
  R1. Stop the affected new worker before restoring the exact old image ID and
      that service's previous selector. For Telegram, verify only one poller.
  R2. Roll back web only if required; keep additive migrations applied.
  R3. Leave MAX webhook subscription, Caddy, secrets and Turkey egress intact.
  R4. Never restore PostgreSQL for a code-only failure. Restore the signed PRE
      database/media only for proven data corruption or an unusable schema.

Scope gate: production components authorized by this task are web,
telegram-bot, max-bot and required migrations. catalog-web is a separate
component and is blocked until explicitly authorized. Production deployment
and any unrelated service update remain prohibited.
